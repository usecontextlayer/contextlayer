# Brainstorming ends in iterative implementation, not a plan

The `superpowers:brainstorming` skill's own flow terminates by writing an implementation plan. **Do not follow it there.** When brainstorming produces an agreed design or spec, stop at the spec — **never write an implementation plan.** A plan is speculative sequencing: it freezes a guess about the order and shape of the work *before* the work has taught you anything — the YAGNI error applied to process. The bills come due the same way: the plan is usually wrong exactly where it matters, and writing it only defers the first real feedback.

Instead, **implement iteratively** — one small vertical slice at a time, checking in between slices. Work in a **faux worktree**: preferably one the user has set up for you, or one you set up yourself with `setup-faux-worktree <existing_folder> <new_branch>`; when the work has landed, `close-faux-worktree <faux_folder>` tears the checkout down. Iterative implementation is not a nicety; it is *how the design gets finished*. The design agreed during brainstorming is a hypothesis — implementation is where its nuances surface, and slicing lets you and the user adapt together in contact with the real code instead of in the abstract.

**DURING IMPLEMENTATION, PAUSE THE MOMENT A JUDGMENT, TASTE, OR SCOPE DECISION APPEARS, AND HAND IT TO THE USER. NEVER MAKE A JUDGMENT, TASTE, OR SCOPE DECISION YOURSELF.** MECHANICAL, OBVIOUS-SCOPE CALLS YOU MAKE AND REPORT — BUT ANYTHING THAT IS A MATTER OF TASTE, A JUDGMENT CALL, OR A QUESTION OF SCOPE BELONGS TO THE USER. SURFACE IT AND WAIT. PAUSING TO ASK IS NEVER A FAILURE HERE; SILENTLY DECIDING IS.
