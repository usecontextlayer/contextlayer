A [slate](/core-concepts/slate) can expose tools to clients that support the **Model Context Protocol (MCP)**. A client discovers the tools, calls them with structured arguments, and receives their results through the slate's hosted endpoint:

```text
https://<name>.contextlayer.xyz/mcp
```

MCP tools do not require a React Router app or static files. They can share a slate with those parts, or be its only authored functionality.

A **View** is a browser interface authored as an MCP Apps resource. Tools and Views are independent: a tool can return text without a View, a View can build without a tool or app, and several tools can reference the same View.

<Note>
  View compilation and resource discovery are available. Delivering the built JavaScript and CSS inside an MCP host still requires resource CSP and asset-access support that is not implemented yet. Use text-only tools for a complete hosted workflow.
</Note>

<Note>
  MCP tools currently cannot use ContextLayer connections, databases, or secrets. Keep all three resource collections empty in an MCP declaration; declaring a resource fails the build. Apps and agents support these resources.
</Note>

## Tools

An MCP tool lives in `mcp/<name>/index.ts`, with its own declaration in `mcp/<name>/slate.json`. The module exports two things:

- `tool`: the definition clients discover, including a name, description, Zod `inputSchema`, and optional Zod `outputSchema`.
- `handler`: the function that receives validated arguments and returns an MCP tool result.

For example, this tool returns a supplied string as text. It does not need a View:

```ts mcp/echo/index.ts
import { z } from "zod"

export const tool = {
  name: "echo",
  description: "Echo a value back.",
  inputSchema: z.object({ value: z.string() }),
}

export function handler(args: unknown) {
  const { value } = args as z.infer<typeof tool.inputSchema>
  return { content: [{ type: "text" as const, text: value }] }
}
```

```json mcp/echo/slate.json
{
  "connections": {},
  "databases": {},
  "secrets": {}
}
```

ContextLayer validates a call against `inputSchema` before invoking the handler. The type assertion in this example describes that already-validated value to TypeScript.

MCP tools and app routes are separate entry points. Defining an app route does not create an MCP tool. Both can import shared modules from the slate when they need the same logic, but importing a module does not give an MCP tool access to the app's resources. For how these entry points fit beside agents, static files, and Views, see [How the parts work together](/core-concepts/slate#how-the-parts-work-together).

## Views

Put a View's HTML entry point at `mcp-ui/<name>/index.html`. It can load TypeScript or TSX and import browser-compatible components, utilities, and CSS from elsewhere in the slate. It does not need a React Router route. When used inside an MCP host, interaction belongs to the MCP Apps bridge.

Once a View exists, associate it with a tool through the tool definition's metadata:

```ts
_meta: { ui: { resourceUri: "ui://echo/index.html" } }
```

This URI identifies `mcp-ui/echo/index.html`. It is an MCP resource URI, not a browser URL. The generated manifest maps it to the built HTML served at `/mcp-ui/echo/`. A View is listed as a resource even when no tool references it.

The MCP Apps bridge supplies tool inputs and results and lets a View request further tool calls. A View must not receive ContextLayer credentials or depend on the app's browser session. Compiling browser assets does not grant them cross-origin access or bypass a private slate's viewing authorization.

## Build and serving

The SDK evaluates tool definitions during the build and writes their schemas and declarations into the generated `mcp.json` catalog. Each View contributes its HTML as an entry to the same Vite client build as any app. Vite follows those entries' dependency graphs and emits ordinary HTML, JavaScript chunks, and stylesheets, including shared and lazy-loaded modules. Existing app entries and static files remain part of that build.

The same build hooks run with or without React Router; there is no separate per-View build or single-file packaging. On the hosted slate, tool discovery reads the generated catalog, and each tool call runs the selected `handler` in the slate's Worker.

Build and deploy the slate to use its hosted `/mcp` endpoint. Local MCP invocation and View preview are not provided by the app's development server. [Expose MCP tools](/how-to/expose-mcp-tools) walks through a text tool, deployment, and authoring View build output.

## Connect a client

Add the hosted `/mcp` URL to your MCP client's server configuration. The client signs in with OAuth: a person approves access with their ContextLayer account, and the client receives a token scoped to that slate's MCP endpoint.

Every MCP request requires this token, including requests to public slates. The slate's viewing rule also applies. For a private slate, the signed-in person must be allowed to view it; making a slate public does not remove MCP authentication. After authorization, the client can discover and call the slate's tools. See [Owners and viewers](/core-concepts/owners-and-viewers).
