An **agent** is a named set of standing instructions and resource requirements inside a [slate](/core-concepts/slate). ContextLayer runs those instructions as hosted **jobs**. Each job receives a task prompt and has its own conversation and computer. A slate can contain agents without an app or static files.

| Concept | What you author or start | Example |
| --- | --- | --- |
| Agent | Instructions and resources kept in `agents/<name>/` | A `digest` agent that summarizes notes. |
| Job | One run of that agent with a task prompt | “Summarize the notes added today.” |
| Schedule | A recurring time and prompt for starting jobs | Start a weekly summary every Monday at 09:00 UTC. |

Start hosted jobs through the API or let a schedule start them. [Build an agent](/how-to/build-an-agent) walks through authoring the files and running a first job.

## An agent's files

| File | Purpose |
| --- | --- |
| `agents/<name>/instructions.md` | Standing instructions, given to every job |
| `agents/<name>/slate.json` | The resources the agent requires, in the same schema as the app's declaration |
| `agents/<name>/schedules/<schedule>.md` | Optional: a prompt to run on a schedule |

The agent's name is its directory name. Use the agents scaffold for a minimal `agents/agent/` directory, then rename it and author its instructions and resources. Select it with `init --scaffold-agents` or add it later with `scaffold agents`; CLI help describes both commands. The scaffold supplies source, not a working agent or model credential. Writing the same files directly has the same effect.

Every slate includes package and Vite/Cloudflare build tooling, even when it contains only agents. Keep that tooling and its lockfile when authoring an agent-only slate. Pushing `main` starts the normal deployment pipeline; jobs read instructions from the latest commit on `main`, while migrations and schedules are applied during successful deployment.

An agent uses only the resources in its own declaration; it does not inherit the app's requirements. The app and agents share a namespace per resource kind. If both declare the same database slug, they refer to the same logical database and must agree on its mode. They use the same stored database when that mode selects the same Owner. Different people's viewer-mode databases remain separate. [Resources](/core-concepts/resources) explains declarations and modes.

## Model and authentication

A hosted agent runs on an Anthropic model. Declare and supply one of these provider secrets:

| Secret | Authentication |
| --- | --- |
| `ANTHROPIC_API_KEY` | Anthropic API access. |
| `CLAUDE_CODE_OAUTH_TOKEN` | A Claude subscription. |

If both are declared, the API key takes precedence. The secret's `owner` or `viewer` mode selects who supplies the credential, independently of which model the agent uses.

The default model is `claude-haiku-4-5`. To choose another, declare an `ANTHROPIC_MODEL` secret and save a full Anthropic model ID as its value. A changed model applies to new jobs. See [Secrets](/core-concepts/resources/secrets).

## Jobs

When a job starts, ContextLayer reads the agent's definition, resolves its declared resources for the job's actor, and starts a fresh conversation and Linux computer. The **actor** is the person or app the job acts for. The resolved resources stay fixed for that job.

Jobs do not share conversations or computer files. They can share persistent resources: for example, a digest job can read the owner-mode notes database that the app writes to. A new job gets a fresh computer, but the database keeps its existing rows. Conversation and result records persist independently of the computer, so inspecting a completed job does not require its scratch files to remain available. For the wider relationship between agents, interfaces, and shared data, see [How the parts work together](/core-concepts/slate#how-the-parts-work-together).

Start a job with a prompt through the API: [Start an agent job with a prompt](https://docs.usecontextlayer.com/api-reference/agent-jobs/start-an-agent-job-with-a-prompt). A job you start acts for you. If the agent declares viewer-mode resources, your setup for them must be complete first.

Anyone who can view a private slate can start jobs and read results for their own jobs and jobs acting for the app. Managing the slate is required to inspect transcripts, usage, live execution, or schedules, and to abort or delete jobs. These operations can reveal agent instructions and private data.

Deleting a job releases its computer. It does not undo database writes or actions the job has already performed in connected services.

<Note>Public slates cannot run agent jobs yet.</Note>

## Schedules

A schedule is a Markdown file in `agents/<name>/schedules/`. Its YAML front matter sets `cron`, a five-field cron expression in UTC; its body is the prompt. The file name without `.md` is the schedule's name.

```markdown agents/digest/schedules/weekly.md
---
cron: "0 9 * * 1"
---
Summarize last week's notes.
```

This schedule starts a job every Monday at 09:00 UTC with “Summarize last week's notes.” as its prompt. The prompt supplies the task for that run; `instructions.md` still supplies the standing instructions.

Schedules are installed after each successful deployment. When a person first becomes a slate member, their schedules are installed after their databases have been provisioned and migrated. Each firing starts a fresh job using the latest commit on `main`, through the same preparation path as an API job.

Who a scheduled job acts for depends on the agent's own declaration:

- An agent that declares **no viewer-mode resources** is **app-scoped**: each scheduled run acts for the slate itself. This app actor does not require a UI app. An owner-mode shared-database digest can run once for the whole slate.
- An agent that declares **any viewer-mode resource** is **member-scoped**: each scheduled run acts for a particular [slate member](/core-concepts/owners-and-viewers#slate-members), with schedules installed for the members. A personal-inbox digest can run separately for each member.

Scope follows the agent's requirements, including its connections, databases, and secrets. The app's declaration does not determine an agent's scope.

## Tools a hosted agent gets

- **The computer.** `read`, `write`, `edit` and `bash` work on the job's Linux computer, which has no internet access. Files there are scratch space: they last only while the computer runs, and it stops after ten minutes without activity.
- **`database_query`.** Parameterized SQL against the agent's declared databases. Writes persist immediately and are shared with the app and with other jobs that use the same database.
- **Connection tools.** For each declared connection, the actions of its toolkit, named `<connection-slug>__<ACTION>`. They run with the account assigned to that connection; the agent never sees its credentials.

The agent uses **Code Mode** to discover connection tools and coordinate calls in a short script. Connection tools are available through Code Mode; computer tools and `database_query` can also be called directly. A Code Mode script reaches the job's tools without gaining general computer or network access. The computer's lack of internet access does not prevent authorized connection tools from calling their external services.

## Develop an agent

Edit the agent's ordinary source files in your checkout, then push `main` and test execution through hosted jobs. Supply and verify its hosted resource assignments and model credentials independently of any app's local development settings. A local agent execution workflow is not available yet; `pnpm dev` in the app starter develops the React Router app. See [Build an agent](/how-to/build-an-agent) for the hosted workflow.
