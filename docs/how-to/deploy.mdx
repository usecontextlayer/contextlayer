Deploy a slate by pushing its `main` branch to the ContextLayer Git remote. ContextLayer builds that commit, applies its database migrations, publishes its static assets and any Worker, and installs its agent schedules. Empty, static-only, agents-only, MCP-only, and app slates use the same build pipeline.

Work from the slate checkout created by `init`, which has `origin` set to the slate's repository. You need the saved CLI login configured during [Installation](/installation) and permission to manage the slate. There is no separate deploy command.

<Steps titleSize="h2">
  <Step title="Check the local changes">
    Run the checkout's type check and production build:

    ```sh
    pnpm typecheck
    pnpm build
    ```

    Every slate needs `package.json`, a build script, a committed `pnpm-lock.yaml`, and native Vite/Cloudflare configuration. Initialization supplies this foundation even when the slate has no authored parts. After integrating a scaffold that changes dependencies, run `pnpm install` and include the updated lockfile. Keep deployment output under `build/`; the Cloudflare Vite plugin writes the native deployment pointer under `.wrangler/deploy/`.

    Include any declarations, migrations, and generated database types that the code needs. Local success does not configure hosted accounts or copy local data; those are separate from the deployment.
  </Step>
  <Step title="Commit your changes">
    `init` already committed the checkout on `main`, including its lockfile. If you have not changed it, continue directly to the push. Otherwise, commit the files you want to deploy:

    ```sh
    git add .
    git commit
    ```
  </Step>
  <Step title="Push main">
    ```sh
    git push -u origin main
    ```

    Git authenticates the push with your saved CLI login. Only the slate's owning user or a member of its owning organization can push. Only a push to `main` starts a build; other branches do not deploy the slate.

    A successful push means the repository received the commit. Published app code, static assets, and MCP tools change when deployment succeeds. Hosted resource preparation reads declarations from `main` independently of publication; agent instructions also follow their [configuration refresh boundary](/core-concepts/slate/agents#when-configuration-changes). Keep pushed configuration compatible with the code and database schema still in use while deployment runs or if it fails.
  </Step>
  <Step title="Inspect the build and published revision">
    Use the CLI's CI entry point to list your slate's retained runs, their native execution states, and timing metadata. These reads use your normal ContextLayer login; you do not need Cloudflare credentials or a separate Cloudflare installation. Use CLI help for the supported CI listing and Worker inspection operations and paging options. Native CI help also describes operations that ContextLayer does not expose.

    Cloudflare defines the run statuses and retains the records. The listing does not include each run's source commit, step details, execution error text, or logs. Run status describes pipeline execution. Inspect the Worker's native script tags for `commit:<sha>` and compare that SHA with your pushed commit. ContextLayer sets this tag after deployment succeeds; it identifies the last successfully tagged deployment. Deployment and tagging are separate operations, so a deployment can succeed before a tag update fails. Neither the latest push nor a completed run alone confirms the published revision.

    Published-script metadata does not identify the revision that answered a particular HTTP request.
  </Step>
  <Step title="Open the hosted URL">
    After deployment succeeds, open the hosted URL printed by `init`. Its dashboard link is the management page; the hosted URL serves the slate's deployed content. A slate without a page at `/` can return 404 there after a successful deployment; an agents-only slate runs through the conversation API and schedules, and MCP clients use `/mcp`.

    New slates are private. Sign in with an account allowed to view the slate: its owning user or a member of its owning organization. If a coding agent is deploying for you, it should give you the hosted URL so you can open it in your browser.

    Check the behavior you changed through its surface: the app, static files, MCP tools, or hosted agent conversations. An app using the SDK's `Layout` shows the chrome for hosted resource setup. For a slate without that app interface, use the CLI or API to configure declared resources.
  </Step>
</Steps>

## What the pipeline does

The pipeline takes its source code, declarations, migrations, and schedules from the pushed commit, in this order:

1. **Prepare.** ContextLayer reads the commit's declarations and selects the databases to migrate.
2. **Build.** An isolated sandbox runs `pnpm install --frozen-lockfile` and `pnpm build`. There is no fallback that publishes source files when package or build configuration is missing.
3. **Migrate.** The commit's Kysely migrations run against the slate's owner-mode databases and every existing member's viewer-mode databases.
4. **Deploy.** Publish the compiled Worker and assets, or assets-only output, using the native build output. ContextLayer then sets the `commit:<sha>` script tag described above; a failed tag update fails this step.
5. **Schedules.** The schedules of the slate's agents are installed from the same commit.

<Warning>
  A failed migration stops the pipeline: the commit is not deployed and its schedules are not installed. The migration is not retried automatically, and SQL statements that ran before the failure can remain applied.
</Warning>

Migrations run while the previous deployment is still serving, so keep them compatible with that version until the new deployment completes. See [Add a database](/how-to/add-a-database).

## Configure hosted resources separately

Git carries committed source, declarations, migrations, and generated query types. It does not carry the local resources those files used during development:

| Local state | What to do for the hosted slate |
| --- | --- |
| Assignments in `.contextlayer/connections.json` | Assign connected accounts through the hosted chrome, CLI, or API. |
| Rows in `.contextlayer/databases` | Create data through the hosted app or hosted agent conversations; deployment applies the schema, not local rows. |
| Secret values in the local environment | Supply hosted values for the Owner selected by each secret's mode. |

See [Connect an account](/how-to/connect-an-account) and [Secrets](/core-concepts/resources/secrets) for hosted configuration.

## The hosted URL

The hosted URL is `https://<name>.contextlayer.xyz/`. `<name>` is the slate's name, which ContextLayer chose when it created the slate. Matching static files are served first; an app handles unmatched requests when present. In particular, `public/index.html` serves `/` ahead of an app's home route. Static files follow the slate's viewing permissions; their directory name does not make a private slate public.

The SDK's `Layout` mounts the chrome on app pages. Plain static HTML does not acquire that interface automatically. See [Use a slate](/how-to/use-a-slate) for viewing and resource setup.
