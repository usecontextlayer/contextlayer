title: "Deploy"
description: "Push main to build, migrate and deploy a slate, then open it at its hosted URL."
---

Deploy a slate by pushing its `main` branch to the ContextLayer Git remote. ContextLayer builds that commit, applies its database migrations, publishes the app and MCP tools, and installs its agent schedules.

Work from the slate checkout created by `init`, which has `origin` set to the slate's repository. You need the saved CLI login configured during [Installation](/installation) and permission to manage the slate. There is no separate deploy command.

<Steps titleSize="h2">
  <Step title="Check the local changes">
    If you changed the app, run the checkout's type check and production build:

    ```sh
    pnpm typecheck
    pnpm build
    ```

    Include any declarations, migrations, and generated database types that the code needs. Local success does not configure hosted accounts or copy local data; those are separate from the deployment.
  </Step>
  <Step title="Commit your changes">
    `init` already committed the starter on `main`. If you have not changed it, continue directly to the push. Otherwise, commit the files you want to deploy:

    ```sh
    git add .
    git commit
    ```
  </Step>
  <Step title="Push main">
    ```sh
    git push -u origin main
    ```

    Git authenticates the push with your saved CLI login. Only the slate's owning user or a member of its owning organization can push. Only a push to `main` starts a build; other branches do not deploy the slate.

    A successful push means the repository received the commit. The hosted app changes after the build, migrations, and publication succeed.
  </Step>
  <Step title="Inspect the build and published revision">
    Use the CLI's CI entry point to list your slate's retained runs, their native execution states, and timing metadata. These reads use your normal ContextLayer login; you do not need Cloudflare credentials or a separate Cloudflare installation. Use CLI help for the supported CI listing and Worker inspection operations and paging options. Native CI help also describes operations that ContextLayer does not expose.

    Cloudflare defines the run statuses and retains the records. The listing does not include each run's source commit, step details, execution error text, or logs. Run status describes pipeline execution; to confirm which source revision is published, inspect the Worker's commit tag and compare it with your pushed commit. Neither the latest push nor a completed run alone confirms the published revision.

    Published-script metadata does not identify the revision that answered a particular HTTP request.
  </Step>
  <Step title="Open the hosted URL">
    After deployment succeeds, open the hosted URL printed by `init`. Its dashboard link is the management page; the hosted URL is the running app.

    New slates are private. Sign in with an account allowed to view the slate: its owning user or a member of its owning organization. If a coding agent is deploying for you, it should give you the hosted URL so you can open it in your browser.

    Check the behavior you changed in the hosted app. Configure any newly declared hosted connections or viewer secrets through the chrome when prompted.
  </Step>
</Steps>

## What the pipeline does

The pipeline takes its source code, declarations, migrations, and schedules from the pushed commit, in this order:

1. **Prepare.** ContextLayer reads the commit's declarations and selects the databases to migrate.
2. **Build.** An isolated sandbox installs the committed dependencies and runs `pnpm build`.
3. **Migrate.** The commit's Kysely migrations run against the slate's owner-mode databases and every existing member's viewer-mode databases.
4. **Deploy.** The built app is published to the slate's hosted URL.
5. **Schedules.** The schedules of the slate's agents are installed from the same commit.

<Warning>
  A failed migration stops the pipeline: the commit is not deployed and its schedules are not installed. The migration is not retried automatically, and SQL statements that ran before the failure can remain applied.
</Warning>

Migrations run while the previous deployment is still serving, so keep them compatible with that version until the new deployment completes. See [Add a database](/how-to/add-a-database).

## Configure hosted resources separately

Git carries committed source, declarations, migrations, and generated query types. It does not carry the local resources those files used during development:

| Local state | What to do for the hosted slate |
| --- | --- |
| Assignments in `.contextlayer/connections.json` | Assign connected accounts through the hosted chrome, CLI, or API. |
| Rows in `.contextlayer/databases` | Use the hosted app to create hosted data; deployment applies the schema, not local rows. |
| Secret values in the local environment | Supply hosted values for the Owner selected by each secret's mode. |

See [Connect an account](/how-to/connect-an-account) and [Secrets](/core-concepts/resources/secrets) for hosted configuration.

## The hosted URL

The hosted URL is `https://<name>.contextlayer.xyz/`. `<name>` is the slate's name, which ContextLayer chose when it created the slate. On the hosted slate, the chrome appears above the app: the ContextLayer header that shows who is signed in and what the slate still needs to be set up. See [Use a slate](/how-to/use-a-slate).
