---
title: "Add a database"
description: "Declare a SQLite database, author its migrations with the Kysely CLI, generate its query types, and query it from a loader or action."
---

A slate keeps persistent data in declared SQLite databases. Each database has a slug, and its Kysely configuration, migrations and generated query types live under `databases/<slug>`. The starter's `notes` database is a complete example. This guide adds a second database, `tasks`. See [Databases](/core-concepts/resources/databases) for how databases fit into a slate.

Keep `pnpm dev` running from the checkout root while you work. The migration and type-generation commands use its local storage, which persists in the checkout's ignored `.contextlayer/databases`.

<Steps>
  <Step title="Declare the database">
    Add the slug under `databases` in `public/slate.json`:

    ```json public/slate.json
    {
      "connections": {},
      "databases": {
        "notes": { "mode": "owner" },
        "tasks": { "mode": "owner" }
      },
      "secrets": {}
    }
    ```

    The mode selects whose database the hosted slate uses. In owner mode the slate's Owner has one database that every user shares. In viewer mode each user has their own database for this slate.

    An agent that uses the same data declares the same slug in its `agents/<name>/slate.json`. Matching slugs select the same database and must declare the same mode.
  </Step>
  <Step title="Add its Kysely configuration">
    Each database has its own native Kysely CLI configuration:

    ```ts databases/tasks/kysely.config.ts
    import { databaseDialect } from "@usecontextlayer/sdk/database"
    import { defineConfig } from "kysely-ctl"

    export default defineConfig({
    	dialect: databaseDialect("tasks"),
    	migrations: { migrationFolder: "./migrations" },
    })
    ```

    The configuration selects only the slug. ContextLayer supplies the connection behind it: local storage during development, the hosted database during deployment.
  </Step>
  <Step title="Create a migration">
    ```sh
    pnpm exec kysely --config databases/tasks/kysely.config.ts migrate make create_tasks
    ```

    Edit the generated migration's `up(db)` and, optionally, `down(db)`, using native Kysely schema operations or `sql`:

    ```ts
    import type { Kysely } from "kysely"

    export async function up(db: Kysely<unknown>) {
    	await db.schema
    		.createTable("tasks")
    		.addColumn("id", "integer", (column) => column.primaryKey().autoIncrement().notNull())
    		.addColumn("title", "text", (column) => column.notNull())
    		.execute()
    }

    export async function down(db: Kysely<unknown>) {
    	await db.schema.dropTable("tasks").execute()
    }
    ```

    Kysely owns migration naming, ordering and the record of applied migrations. `pnpm exec kysely --help` lists its other operations.
  </Step>
  <Step title="Apply it and generate the query types">
    ```sh
    pnpm exec kysely --config databases/tasks/kysely.config.ts migrate latest
    pnpm db.codegen tasks
    ```

    `db.codegen` writes `databases/tasks/types.ts` from the migrated local database. Applying migrations and generating types are separate commands. Do not edit the generated types by hand.

    ```ts databases/tasks/types.ts
    export interface Tasks {
      id: Generated<number>;
      title: string;
    }

    export interface DB {
      tasks: Tasks;
    }
    ```

    Kysely does not run a migration again once it has been applied, so change the schema with a new migration rather than by editing an applied one.
  </Step>
  <Step title="Restart the development server">
    Restart `pnpm dev`. The app picks up declarations when the server starts, and startup applies each declared database's pending migrations before the app can query.
  </Step>
  <Step title="Query it from a loader or action">
    The SDK's `database<DB>(...)` returns a Kysely instance for a declared slug, typed by the generated `DB`:

    ```ts
    import { database, databasesContext } from "@usecontextlayer/sdk"
    import type { LoaderFunctionArgs } from "react-router"
    import type { DB } from "@/databases/tasks/types"

    export async function loader({ context }: LoaderFunctionArgs) {
    	const db = database<DB>(context.get(databasesContext), "tasks")
    	return db.selectFrom("tasks").selectAll().orderBy("id", "desc").execute()
    }
    ```

    Use `.returning()` to read inserted or updated rows. The database supplies no mutation counts or insert IDs: Kysely reports affected-row counts as `0n`, so they cannot tell you whether a write changed anything. SQL transactions are not supported. The starter's `app/routes/home.tsx` shows a loader and an action on `notes`.
  </Step>
  <Step title="Commit and push">
    Commit the migration and `databases/tasks/types.ts` together, then push to `main`. See [Deploy](/how-to/deploy).
  </Step>
</Steps>

## What the push does

Pushing `main` builds the commit, runs its migrations with the native Kysely CLI in an isolated sandbox, then deploys it. The migrations run against the slate's owner-mode databases and every existing member's viewer-mode databases. A new member's databases are initialized with the same migrations before first use.

A failed migration blocks the deployment. It is not retried, and nothing is rolled back: SQL statements that ran before the failure can remain applied. Migrations run while the previous deployment is still serving, so pushed migrations must stay compatible with it until the new deployment completes.
