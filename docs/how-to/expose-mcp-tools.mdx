title: "Expose MCP tools"
description: "Deploy a text tool without an app, connect an MCP client, and author shared browser code for View builds."
---

Add an `echo` tool to a slate, deploy it, and call it from a Model Context Protocol (MCP) client. The tool accepts a string and returns it as text. It works without a React Router app or a View.

After [CLI setup](/installation), create a slate with the minimal MCP scaffold:

```sh
npx @usecontextlayer/cli init my-mcp-slate --scaffold-mcp
cd my-mcp-slate
```

For an existing checkout, use `scaffold mcp` and integrate its complete proposal if it conflicts with your source; `npx @usecontextlayer/cli scaffold --help` explains that behavior. Keep any app handling when merging the Worker configuration. Scaffolding adds ordinary files and does not register another component.

Each tool lives under `mcp/`, and the hosted slate serves its tools at `/mcp`. The MCP scaffold includes the package/build configuration and Worker wiring, but its handler is empty. Replace that skeleton before calling it. Test tools after deployment; a local MCP invocation workflow is not available yet.

<Note>
  MCP tools cannot use resources yet. An MCP declaration's `connections`, `databases` and `secrets` must be empty, and the build fails otherwise. Resource execution is implemented only for the app and agents.
</Note>

## Add a tool

<Steps titleSize="h3">
  <Step title="Create the tool's declaration">
    Rename the scaffold's `mcp/tool/` directory to `mcp/echo/` and replace its declaration with the file below. Each tool has its own declaration; no app declaration is required for an MCP-only slate. This tool requires no resources:

    ```json mcp/echo/slate.json
    { "connections": {}, "databases": {}, "secrets": {} }
    ```
  </Step>
  <Step title="Write the tool">
    `mcp/<name>/index.ts` exports two things. `tool` is the native MCP tool definition, with a Zod `inputSchema` and an optional Zod `outputSchema`. `handler` runs each call and returns an MCP tool result.

    ```ts mcp/echo/index.ts
    import { z } from "zod"

    export const tool = {
      name: "echo",
      description: "Return the value it receives.",
      inputSchema: z.object({ value: z.string() }),
    }

    export function handler(args: unknown) {
      const { value } = args as z.infer<typeof tool.inputSchema>
      return { content: [{ type: "text" as const, text: value }] }
    }
    ```

    The slate's Worker validates the arguments against `inputSchema` before it calls `handler`. Both the app and MCP scaffolds' `workers/app.ts` pass every `mcp/*/index.ts` module to `createSlateWorker`; keep that wiring. The MCP-only Worker omits the optional React Router build handler.
  </Step>
  <Step title="Build and deploy">
    Run `pnpm build` to compile the Worker and MCP catalog. The same MCP build hooks run with or without an app, so a declaration or definition error is reported before you push. Commit the completed tool, configuration, and lockfile, then push `main` to deploy; see [Deploy](/how-to/deploy).
  </Step>
</Steps>

## Connect an MCP client

The slate's MCP endpoint is `https://<name>.contextlayer.xyz/mcp`. Replace `<name>` with the hosted slate name printed by `init`. ContextLayer registers this endpoint as an OAuth-protected resource when it creates the slate; you do not need to create a separate OAuth application for it.

<Steps titleSize="h3">
  <Step title="Add the endpoint to your client">
    Add `https://<name>.contextlayer.xyz/mcp` to your MCP client as a remote server.
  </Step>
  <Step title="Sign in and approve the client">
    Follow the client's OAuth sign-in flow, sign in with your ContextLayer account, and approve access. If a coding agent is setting up the client, a person completes this browser approval.

    The client discovers the authorization server through the slate's [OAuth resource metadata](/api-reference/slate-routing/get-oauth-metadata-for-a-slate-mcp-endpoint). ContextLayer identifies clients through their Client ID Metadata Document; this discovery is handled by the client.
  </Step>
  <Step title="Use the tools">
    Confirm that the client lists `echo`, then call it with:

    ```json
    { "value": "Hello from my slate" }
    ```

    The result should contain the text `Hello from my slate`. This completes the text-only tool workflow.

    The client's token is issued for this slate's `/mcp` endpoint with the `mcp:access` scope. It does not authorize another slate or the platform management API.
  </Step>
</Steps>

Every MCP connection signs in; a browser session does not authenticate `/mcp`. The slate's viewing rule still applies: a private slate admits its owning user and members of its owning organization.

## Build a View

A View begins with an HTML entry point at `mcp-ui/echo/index.html`. It can load TypeScript or TSX and import the same browser-compatible components, utilities, and stylesheets as other parts of the slate. Views build independently of tools and apps; you can associate a built View with a tool through its resource URI.

<Note>
  This section demonstrates View compilation and shared browser code. Rendering the resulting external JavaScript and CSS inside an MCP host still needs resource CSP and asset-access support that is not implemented yet. Adding a View does not bypass private-slate authorization.
</Note>

The example uses React and React DOM. The app scaffold supplies their dependencies, types, and JSX configuration. The MCP-only scaffold includes the runtime libraries; add their TypeScript types and set `compilerOptions.jsx` to `"react-jsx"` before using TSX there. The View uses an ordinary React entry point and does not require a React Router route.

### Include the View in your TypeScript project

The app scaffold's `tsconfig.cloudflare.json` already includes `mcp-ui/**/*` and `components/**/*`. The MCP scaffold's `tsconfig.json` includes `mcp-ui/**/*`; add `components/**/*` when placing shared components there. In another TypeScript setup, include both the View and shared component directories without removing existing entries.

The React example needs `compilerOptions.jsx` set to `"react-jsx"`. Its `@/` imports use the root alias below, together with `resolve.tsconfigPaths: true` in Vite. The app starter already configures both; see [Vite and Worker configuration](/reference/sdk#vite-and-worker-configuration).

```json tsconfig.json
{
  "compilerOptions": {
    "paths": {
      "@/*": ["./*"]
    }
  }
}
```

Merge these settings into your existing configuration. Including the View files lets TypeScript check them and lets Vite associate their imports with the project's path aliases.

### Write a shared component

Put presentation code in a component that both the app and the View can import:

```tsx components/echo-card.tsx
export function EchoCard({ value }: { value: string }) {
  return (
    <section>
      <h1>Echo</h1>
      <p>{value}</p>
    </section>
  )
}
```

Shared browser code can import other components, utilities and CSS normally. Keep server-only modules, Worker bindings and request-scoped loaders out of these imports; pass the data a component needs through its props.

### Load the View's TypeScript entry

Create the HTML page with a mount point and a module script:

```html mcp-ui/echo/index.html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>Echo</title>
  </head>
  <body>
    <div id="root"></div>
    <script type="module" src="./main.tsx"></script>
  </body>
</html>
```

Then mount the shared component from the View's entry module:

```tsx mcp-ui/echo/main.tsx
import { createRoot } from "react-dom/client"
import { EchoCard } from "@/components/echo-card"

createRoot(document.getElementById("root")!).render(
  <EchoCard value="Hello from the View" />
)
```

An existing app route can import and render that same component:

```tsx
import { EchoCard } from "@/components/echo-card"

export default function ExamplePage() {
  return <EchoCard value="Hello from the app" />
}
```

The View and app share source code, but run in separate browser contexts. Vite follows each entry's imports during compilation; you do not need to copy the component into `mcp-ui/` or publish it as a separate package.

### Associate the View with the tool

Add this property to the exported `tool` definition:

```ts
_meta: { ui: { resourceUri: "ui://echo/index.html" } }
```

The resource URI identifies the matching HTML entry point. The generated catalog maps `ui://echo/index.html` to the built HTML at `/mcp-ui/echo/`. Several tools can reference the same View, and the View is built even when no tool references it. Run `pnpm build` after adding or changing View source.

This example passes a fixed value to demonstrate shared UI. To display actual tool inputs or results, or request another tool call, use the client's MCP Apps bridge from the View. The client supplies the tool data through that bridge; it does not give the View ContextLayer credentials or the app's browser session. See [MCP Views](/core-concepts/slate/mcp#views) for the relationship between a tool, its resource URI, and its View.

## What the SDK builds

During the build, the SDK's Vite integration evaluates each `mcp/<name>/index.ts`, validates its `slate.json`, and converts its Zod schemas to JSON Schema. It writes tool definitions and View resource paths into a generated `mcp.json` manifest among the slate's assets.

Each View's HTML is an entry in the same Vite client compilation as any app entries. Vite follows shared imports, stylesheets, and dynamic imports and emits ordinary HTML, JavaScript chunks, and CSS. It does not inline everything into a single HTML file or run a separate build per View. `public/` files join that asset output through Vite's normal copying. The [MCP concept guide](/core-concepts/slate/mcp#views) explains resource identity and the current host-delivery boundary.

ContextLayer reads the deployed manifest to list the slate's tools and serve its Views. Tool discovery does not import your authored modules. Each actual tool call runs your `handler` in the slate's Worker.
