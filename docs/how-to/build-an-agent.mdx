---
title: "Build an agent"
description: "Write an agent, deploy it, submit work to a conversation, inspect its answer, and put it on a schedule."
---

Build a `digest` agent that reads the starter app's `notes` database, summarizes it in a hosted conversation, and runs on a daily schedule. You will write its standing instructions, declare its resources, supply model credentials, and submit a prompt through the API.

This example uses a private slate created with the app starter, `init --scaffold-app`, as in the [Quickstart](/quickstart). Work from its checkout and use an account that can manage the slate so you can configure its owner-mode secret and inspect the conversation. [Agents](/core-concepts/slate/agents) explains agent instances, conversations, and submissions.

Agents themselves do not require an app. For an agent-only slate, select `init --scaffold-agents` or add the minimal source with `scaffold agents`, then author its instructions and resources. That scaffold supplies `agents/agent/`; rename it for your agent. Keep the slate's package/build tooling and lockfile. The notes workflow below deliberately shares the app starter's database and migrations.

An agent-only slate that declares a database must also supply its [Kysely configuration and authored migrations](/core-concepts/resources/databases#migrations-and-types) under `databases/<slug>/`, along with the dependencies needed to run them. The minimal agents scaffold does not supply a database example. Verify its schema and queries through hosted deployment and agent execution.

<Steps titleSize="h2">
  <Step title="Write the agent">
    Create `agents/digest/` and add the two files below. The directory name, `digest`, becomes the agent's name.

    `instructions.md` holds the agent's standing instructions. The prompt you send arrives as separate user input. See [When configuration changes](/core-concepts/slate/agents#when-configuration-changes) for when edited instructions take effect across conversations.

    ```markdown agents/digest/instructions.md
    You summarize the notes in the `notes` table of the `notes` database. Each row stores its note text in `body`. Read them with the `database_query` tool and reply in two or three sentences.
    ```

    `slate.json` is the agent's declaration: the resources it needs. It uses the same schema as `app/slate.json` when an app is present. `connections` is required; `databases` and `secrets` are optional.

    Before declaring the model credential, choose an Anthropic API key or a Claude subscription token. If a coding agent is following this guide, it must ask you which you use and wait for your answer before writing the secret declaration. Hosted agents support these credential declarations:

    - `ANTHROPIC_API_KEY`: an Anthropic API key. If both are declared, this one is used.
    - `CLAUDE_CODE_OAUTH_TOKEN`: a Claude subscription token.

    The example below uses `ANTHROPIC_API_KEY`. For a Claude subscription, use `CLAUDE_CODE_OAUTH_TOKEN` in its place.

    ```json agents/digest/slate.json
    {
      "connections": {},
      "databases": { "notes": { "mode": "owner" } },
      "secrets": { "ANTHROPIC_API_KEY": { "mode": "owner" } }
    }
    ```

    The starter app also declares `notes` in owner mode, so the app and this agent use the same hosted database. The provider secret belongs to the slate's Owner and supplies hosted model authentication.

    Repeated resource names must agree across declarations: all use the same mode, and repeated connections use the same toolkit. An agent gets only its own declared resources; it does not inherit the app's declaration.

    Every directory under `agents/` needs a `slate.json`, even one that declares nothing: `{ "connections": {} }`.
  </Step>
  <Step title="Supply model credentials">
    If you chose a Claude subscription, first run `claude setup-token` in your own terminal and complete its sign-in to create the token. See `claude setup-token --help` for the command's usage.

    Save your chosen credential under its declared name for the slate's Owner with the CLI's `secrets set` command. It targets your personal Owner by default; choose the organization explicitly if the slate belongs to one. Run `npx @usecontextlayer/cli secrets set --help` for the input and Owner-selection syntax.

    <Note>
      A sandboxed or non-interactive environment may refuse `claude setup-token` or `secrets set`. If either command is refused or needs interaction, a coding agent must ask you to run that step in your own terminal and wait for you to confirm it succeeded before continuing. Supply the credential directly to `secrets set` in that terminal.
    </Note>

    The secret's mode decides whose value the agent uses. In owner mode the slate's Owner saves one value and the agent uses it for every actor. In viewer mode each person saves their own, and the agent uses the value of the person it acts for. See [Secrets](/core-concepts/resources/secrets).

    This walkthrough uses the default model. To select another, follow [Model and authentication](/core-concepts/slate/agents#model-and-authentication) before creating the conversation.
  </Step>
  <Step title="Deploy by pushing to main">
    Commit the agent and push `main`:

    ```sh
    git add agents
    git commit
    git push
    ```

    Wait for the deployment to succeed so the hosted `notes` database has its migrations applied. Pushed agent configuration can take effect before deployment finishes: the runtime refreshes from `main` when it opens and before accepting new input, including in existing conversations. See [When configuration changes](/core-concepts/slate/agents#when-configuration-changes) for the shared configuration's lifetime and [Deploy](/how-to/deploy) for checking publication and schedule installation.
  </Step>
  <Step title="Start a conversation and read its answer">
    Hosted conversations run through the platform API, and only on private slates. Use [the API CLI](/how-to/use-the-platform-api) with your saved login. Running it from your checkout still uses hosted resources; it does not run the agent against local files or databases.

    Open the deployed notes app and add a few notes for the agent to summarize. Notes created during local development stay in the local database and are not present in the hosted database.

    Inspect the operation, then create a conversation:

    ```sh
    npx @usecontextlayer/cli api createAgentConversation --describe
    npx @usecontextlayer/cli api createAgentConversation \
      --params '{"target":"<slate-id-or-hostname>","name":"digest","actor":"user"}'
    ```

    Keep the numeric conversation ID in `data.id`. Creation gives you a conversation without sending a prompt. In the following examples, replace `123` with that returned ID, then submit the task:

    ```sh
    npx @usecontextlayer/cli api submitAgentInput \
      --params '{"target":"<slate-id-or-hostname>","name":"digest","actor":"user","conversationId":123}' \
      --json '{"content":"Summarize the notes."}'
    ```

    This returns a native submission record after the input is accepted, without waiting for the answer. Keep its `data.id` as the submission ID and `data.conversationId` as the conversation ID. Work continues after your request ends. Replace `456` below with the returned submission ID and check its status:

    ```sh
    npx @usecontextlayer/cli api getAgentSubmission \
      --params '{"target":"<slate-id-or-hostname>","name":"digest","actor":"user","submissionId":456}'
    ```

    The read returns the current status without waiting. Check again while it is `queued` or `placed`. A `done` input submission contains `data.answer`, the exact entry ID containing its answer. An `unanswered` submission instead reports its native reason and any detail; do not treat that as a successful answer.

    Replace both instances of `789` with `data.answer` to read that entry:

    ```sh
    npx @usecontextlayer/cli api listAgentEntries \
      --params '{"target":"<slate-id-or-hostname>","name":"digest","actor":"user","conversationId":123,"minEntryId":789,"maxEntryId":789,"limit":1}'
    ```

    Read the assistant message's text blocks under `data.items[0].model` and check that they summarize the notes you added. The entry ID ties this answer to your submission even if more work has since reached the conversation.

    To ask a follow-up, call `submitAgentInput` again with conversation `123` and new content. To begin with separate history, call `createAgentConversation` again. Both conversations share this agent instance's computer and connection-tool working context.

    You can return later by listing conversations and inspecting the selected one:

    ```sh
    npx @usecontextlayer/cli api listAgentConversations \
      --params '{"target":"<slate-id-or-hostname>","name":"digest","actor":"user","limit":20}'
    npx @usecontextlayer/cli api getAgentConversation \
      --params '{"target":"<slate-id-or-hostname>","name":"digest","actor":"user","conversationId":123}'
    npx @usecontextlayer/cli api listAgentEntries \
      --params '{"target":"<slate-id-or-hostname>","name":"digest","actor":"user","conversationId":123,"order":"ascending","limit":50}'
    ```

    The conversation view includes recent entries and current native documents, including usage and execution state. Entry listing reads history page by page. If a page returns `data.next`, JSON-encode that unchanged object as the next request's `cursor` parameter, preserving the same scan and actor. Use each operation's `--describe` for its complete native contract. The directory includes Pi's root, created at runtime startup without submitting a task, and any task-owned child conversations; it is not just a list of manual requests.

    Conversation, submission, and provisioned-schedule operations require an actor in `--params`, which the CLI places in the URL path. Use `"actor":"user"` for this walkthrough's manual conversations, including create and submit. Keep it with every ID and cursor you save: the same native ID can exist in another instance. See [Address an agent instance](/core-concepts/slate/agents#address-an-agent-instance) before reading app-scoped work.

    Use the account with management permission chosen at the start of this walkthrough to read answer text and inspect schedules. [Who can do what](/core-concepts/owners-and-viewers#who-can-do-what) distinguishes these reads from operations that need only viewing permission. The API does not expose stopping or deleting work.
  </Step>
  <Step title="Schedule it">
    A schedule is a Markdown file in the agent's `schedules` directory. Its YAML front matter sets `cron`, and its body is the prompt each firing sends.

    ```markdown agents/digest/schedules/daily.md
    ---
    cron: "0 9 * * *"
    ---
    Summarize the notes in two or three sentences.
    ```

    `cron` takes five fields and is read in UTC. This one fires at 09:00 UTC every day. The file name without `.md` is the schedule's name.

    Commit `agents/digest/schedules/daily.md`, push `main`, and wait for that deployment to succeed before checking the installed schedule.

    Schedules come from Git. When a push to `main` deploys successfully, ContextLayer replaces the agent's schedules with the files in that commit. Delete a file and push, and that deployment removes its schedule. [List an agent's provisioned schedules](/api-reference/agents/list-an-agents-provisioned-schedules) and [Get a provisioned agent schedule](/api-reference/agents/get-a-provisioned-agent-schedule) show what is installed.

    Each firing creates a fresh conversation in the existing agent instance and submits the installed prompt as its input. Preparation uses the latest instructions and resources from `main`; the schedule does not pin the revision that installed it. This `digest` has no viewer-mode resources, so it runs once for the slate using the app actor. [Schedules](/core-concepts/slate/agents#schedules) explains how adding a viewer-mode requirement changes scheduled execution to run for each slate member.

    Use `"actor":"app"` in `--params` when listing or reading this owner-only agent's provisioned schedules, and check that the list includes `daily`. For an agent with member-scoped schedules, use `"actor":"user"` to inspect your own installed schedules. A list for an actor with no installed schedules is empty. For this owner-only agent, use `listAgentConversations` with `"actor":"app"` to find scheduled conversations. Their input entries have kind `slate.schedule`, with the authored name in `data.schedule` and native schedule ID in `data.scheduleId`. Removing the schedule leaves that history intact.
  </Step>
</Steps>

## What the hosted agent can use

See [Tools a hosted agent gets](/core-concepts/slate/agents#tools-a-hosted-agent-gets) when writing instructions that use the computer, databases, or connected services. Keep anything that must last in a declared database; the computer's files are scratch space.

To add a connected service to this agent, declare the connection, push it, and assign an account before creating a conversation or submitting input. Every declared connection must have an assignment. Connect an account with the CLI's `accounts add` command and assign it with the `connections` command; each command's `--help` shows how. [Connect an account](/how-to/connect-an-account) walks through the setup.

## Continue developing

Edit the agent's instructions and declaration in the checkout, push `main`, and submit input to verify each change. Use an existing conversation to continue its context or create a fresh one for separate history; create a new conversation to pick up a changed model selection. Keep app development data separate: notes written by `pnpm dev` stay in local storage and are not available to the hosted agent.

A local agent execution workflow is not available yet. Test the deployed database, saved provider credential, connected accounts, and scheduling through hosted conversations.
