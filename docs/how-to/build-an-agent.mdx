---
title: "Build an agent"
description: "Write an agent, deploy it, run it as a hosted job, inspect what it did, and put it on a schedule."
---

Build a `digest` agent that reads the starter app's `notes` database, summarizes it in a hosted job, and runs on a daily schedule. You will write its standing instructions, declare its resources, supply model credentials, and start a job through the API.

Start with a private slate created with `init`, as in the [Quickstart](/quickstart), and work from its checkout. Use an account that can manage the slate so you can configure its owner-mode secret and inspect the job. [Agents](/core-concepts/slate/agents) explains the distinction between an agent definition and each job that runs it.

<Steps titleSize="h2">
  <Step title="Write the agent">
    Create `agents/digest/` and add the two files below. The directory name, `digest`, becomes the agent's name.

    `instructions.md` holds the agent's standing instructions. Every hosted job of this agent runs with them. The prompt you send arrives as a separate user message.

    ```markdown agents/digest/instructions.md
    You summarize the notes in the `notes` table of the `notes` database. Each row stores its note text in `body`. Read them with the `database_query` tool and reply in two or three sentences.
    ```

    `slate.json` is the agent's declaration: the resources it needs. It uses the same schema as the app's `public/slate.json`. `connections` is required; `databases` and `secrets` are optional.

    Before declaring the model credential, choose an Anthropic API key or a Claude subscription token. If a coding agent is following this guide, it must ask you which you use and wait for your answer before writing the secret declaration. Hosted agents support these credential declarations:

    - `ANTHROPIC_API_KEY`: an Anthropic API key. If both are declared, this one is used.
    - `CLAUDE_CODE_OAUTH_TOKEN`: a Claude subscription token.

    The example below uses `ANTHROPIC_API_KEY`. For a Claude subscription, use `CLAUDE_CODE_OAUTH_TOKEN` in its place.

    ```json agents/digest/slate.json
    {
      "connections": {},
      "databases": { "notes": { "mode": "owner" } },
      "secrets": { "ANTHROPIC_API_KEY": { "mode": "owner" } }
    }
    ```

    The starter app also declares `notes` in owner mode, so the app and this agent use the same hosted database. The provider secret belongs to the slate's Owner and supplies hosted model authentication.

    Repeated resource names must agree across declarations: all use the same mode, and repeated connections use the same toolkit. An agent gets only its own declared resources; it does not inherit the app's declaration.

    Every directory under `agents/` needs a `slate.json`, even one that declares nothing: `{ "connections": {} }`.
  </Step>
  <Step title="Supply model credentials">
    If you chose a Claude subscription, first run `claude setup-token` in your own terminal and complete its sign-in to create the token. See `claude setup-token --help` for the command's usage.

    Save your chosen credential under its declared name for the slate's Owner with the CLI's `secrets set` command. It targets your personal Owner by default; choose the organization explicitly if the slate belongs to one. Run `npx @usecontextlayer/cli secrets set --help` for the input and Owner-selection syntax.

    <Note>
      A sandboxed or non-interactive environment may refuse `claude setup-token` or `secrets set`. If either command is refused or needs interaction, a coding agent must ask you to run that step in your own terminal and wait for you to confirm it succeeded before continuing. Supply the credential directly to `secrets set` in that terminal.
    </Note>

    The secret's mode decides whose value a job uses. In owner mode the slate's Owner saves one value and every job uses it. In viewer mode each person saves their own, and a job uses the value of the person it acts for. See [Secrets](/core-concepts/resources/secrets).

    Jobs use `claude-haiku-4-5` unless the agent declares `ANTHROPIC_MODEL` under `secrets`. To choose the model, declare `ANTHROPIC_MODEL` with a mode and save a full Anthropic model ID as its value, the same way as the key. Once declared, the value is required. A changed value applies to jobs started after the change.
  </Step>
  <Step title="Deploy by pushing to main">
    Commit the agent and push `main`:

    ```sh
    git add agents
    git commit
    git push
    ```

    Hosted jobs read the agent from the latest commit on `main`, so a pushed change to `instructions.md` or `slate.json` applies to the next job. Database migrations and schedules take effect only when the pushed commit builds and deploys successfully. See [Deploy](/how-to/deploy).
  </Step>
  <Step title="Start a hosted job and inspect it">
    Hosted jobs start through the platform API, and only on private slates. Use [the API CLI](/how-to/use-the-platform-api) with your saved login to invoke its operations. The CLI's `agent` command runs an agent on your own machine; `npx @usecontextlayer/cli agent --help` describes it.

    Open the deployed notes app and add a few notes for the agent to summarize. Notes created during local development stay in the local database and are not present in the hosted database.

    Inspect [Start an agent job with a prompt](/api-reference/agent-jobs/start-an-agent-job-with-a-prompt), then send the prompt:

    ```sh
    npx @usecontextlayer/cli api startAgentJob --describe
    npx @usecontextlayer/cli api startAgentJob \
      --params '{"target":"<slate-id-or-hostname>","name":"digest"}' \
      --json '{"prompt":"Summarize the notes."}'
    ```

    Keep `data.job.id` for the requests below. The start request returns after the job is accepted for execution; it does not wait for the answer.

    Start by checking its [current operation](/api-reference/agent-jobs/get-an-agent-jobs-current-operation), then [wait for the operation result](/api-reference/agent-jobs/wait-for-an-agent-jobs-operation-result):

    ```sh
    npx @usecontextlayer/cli api getAgentJobOperation \
      --params '{"target":"<slate-id-or-hostname>","name":"digest","id":"<job-id>"}'
    npx @usecontextlayer/cli api getAgentJobResult \
      --params '{"target":"<slate-id-or-hostname>","name":"digest","id":"<job-id>"}'
    ```

    Read the answer in `data.text` and check that it summarizes the notes you added. Each job starts a fresh conversation; start a new job for another task.

    To read the model and tool messages, enumerate the job's sessions, then select a returned session ID:

    ```sh
    npx @usecontextlayer/cli api listAgentJobSessions \
      --params '{"target":"<slate-id-or-hostname>","name":"digest","id":"<job-id>"}'
    npx @usecontextlayer/cli api getAgentJobMessages \
      --params '{"target":"<slate-id-or-hostname>","name":"digest","id":"<job-id>","session":"<session-id>"}'
    ```

    For more detail, use these inspection operations:

    | Question | API operation |
    | --- | --- |
    | Who did this job act for, and what started it? | [Get its catalog entry](/api-reference/agent-jobs/get-an-agent-jobs-catalog-entry). |
    | What other jobs can I see? | [List the agent's jobs](/api-reference/agent-jobs/list-an-agents-jobs-available-to-the-caller), newest first. |
    | What did the model and tools do? | [List execution sessions](/api-reference/agent-jobs/list-the-execution-sessions-within-an-agent-job), then [read a session's active transcript](/api-reference/agent-jobs/read-the-active-transcript-of-an-agent-job-session). |
    | What model and tool usage was recorded? | [Get job usage](/api-reference/agent-jobs/get-model-and-tool-usage-for-an-agent-job). |
    | What is running now? | [Inspect live execution](/api-reference/agent-jobs/inspect-an-agent-jobs-live-execution-state). |

    Private-slate viewers can start jobs and read results for their own jobs and app-actor jobs. Detailed transcripts, usage, live inspection, schedule inspection, aborting, and deletion require slate management permission.

    Results and transcripts stay available after the job finishes. [Abort an agent job's pending operation](/api-reference/agent-jobs/abort-an-agent-jobs-pending-operation) stops it and keeps its records. [Delete an agent job and its execution state](/api-reference/agent-jobs/delete-an-agent-job-and-its-execution-state) removes the job and releases its computer. Deleting a job does not delete rows it wrote to a database or undo what its tools did elsewhere.
  </Step>
  <Step title="Schedule it">
    A schedule is a Markdown file in the agent's `schedules` directory. Its YAML front matter sets `cron`, and its body is the prompt each firing sends.

    ```markdown agents/digest/schedules/daily.md
    ---
    cron: "0 9 * * *"
    ---
    Summarize the notes in two or three sentences.
    ```

    `cron` takes five fields and is read in UTC. This one fires at 09:00 UTC every day. The file name without `.md` is the schedule's name.

    Commit `agents/digest/schedules/daily.md`, push `main`, and wait for that deployment to succeed before checking the installed schedule.

    Schedules come from Git. When a push to `main` deploys successfully, ContextLayer replaces the agent's schedules with the files in that commit. Delete a file and push, and that deployment removes its schedule. [List an agent's provisioned schedules](/api-reference/agents/list-an-agents-provisioned-schedules) and [Get a provisioned agent schedule](/api-reference/agents/get-a-provisioned-agent-schedule) show what is installed.

    Each firing starts a fresh hosted job with the file's body as its prompt, using the agent's instructions and resources from the latest commit on `main`. Who the job acts for follows the agent's declaration:

    - An agent with no viewer-mode resources, like `digest`, runs one job for the app at each firing.
    - An agent with any viewer-mode connection, database or secret runs one job for each slate member at each firing, using that member's viewer-mode resources. A person becomes a slate member when they complete the slate's setup; ContextLayer then migrates their viewer-mode databases and installs the agent's schedules for them in the background.

    Check that the provisioned schedule list includes `daily`. Scheduled jobs appear in the agent's job list under that schedule name. You now have a deployed agent, a verified manual result, and a recurring daily run.
  </Step>
</Steps>

## What the hosted agent can use

Each hosted job gets a fresh Linux computer and these tools:

- **Coding tools.** `read`, `write`, `edit` and `bash` work on the job's computer. The computer has no internet access. Its files are scratch space: no other job sees them, and they last only as long as the job's computer. Keep anything that must last in a database.
- **`database_query`.** Runs parameterized SQL against a database the agent declares. Writes persist immediately and are visible to the app and to other jobs that use the same database. The database's tables come from its migrations under `databases/<slug>`, which ContextLayer applies when the slate deploys.
- **Connection tools.** For each connection the agent declares, the job gets that service's actions from Composio, bound to the account assigned to the connection and named `<slug>__<ACTION>` after the connection's slug. A job does not start until every connection the agent declares has an assigned account. Connect an account with the CLI's `accounts add` command and, after you push, assign it with the `connections` command; each command's `--help` shows how.

The model is not offered connection tools directly. It finds them through Code Mode, which searches and describes the job's tools, and calls them from short scripts. Those scripts run in a sandbox that reaches only the job's own tools, including `database_query` and the coding tools. The model can also call `database_query` and coding tools directly.

## Try it locally

To test the authored instructions against your local notes, run this from the checkout:

```sh
npx @usecontextlayer/cli agent local run digest "Summarize the notes."
```

This uses the Claude Agent SDK, your own Claude authentication, and the checkout's local database. It starts the local development server and runs in the checkout; it does not create a hosted job or test the hosted provider secret. The declared hosted model settings do not configure this local runtime.

Use a hosted job to verify the deployed database, the saved provider credential, and hosted scheduling. Use a local run while developing instructions against local data.
