# Architecture

The repository contains nine packages; `@usecontextlayer/cli` and `@usecontextlayer/sdk` are public and the others are private:

- `cli` — Published as `@usecontextlayer/cli`; Commander-based `ctx` executable, bundled with tsdown; its version comes from its package manifest, and `init` delegates project creation to the official `create-cloudflare@latest` React Router scaffold.
- `sdk` — Public `@usecontextlayer/sdk` integration: shared React Router document Layout, Tools interface and React Router context, app request handling, local auxiliary Worker, and Vite integration. Subpath exports keep React UI, Vite/Node imports, and Worker runtime imports separate.
- `db-infra` — Postgres/Kysely connections, migrations, and ephemeral database helpers.
- `shared` — Authentication, token handling, test helpers, and Sentry event capping.
- `twilio` — Twilio Functions for founder call routing and answer screening.
- `platform` — Cloudflare Workers application: an Artifacts Git proxy under `/git`, OpenAPI endpoints under `/api`, and the React Router dashboard under `/dashboard`.

- `build` — Cloudflare Worker using `@cloudflare/ci` and Workflows to build commits pushed to Artifacts in isolated Sandbox runners.

- `dispatcher` — Cloudflare Worker that resolves public hostnames through the platform API and invokes the WfP Worker named by AppID.

- `auth` — Worker that owns viewer sign-in on the user-code domain.

## Multiple consumers

Almost every user-facing platform capability is exposed through OpenAPI so the web dashboard, CLI, and a future MCP consumer share the same product operations. Zod owns their input and output contracts. A shared domain function owns each operation’s business logic, authorization, and database calls; API handlers adapt it to HTTP and React Router loaders/actions invoke it directly in-process. UI components own presentation and interaction. This is a standing design rule, not a claim that every future CLI command or MCP surface exists today. Better Auth owns its native authentication protocols; product APIs consume the resulting verified identity.

## Security boundary: trusted services and authored apps — principles

These principles define the security boundary the system must uphold; they are requirements, not assertions that every protection is implemented today.

Treat web, platform, auth, and dispatcher as trusted ContextLayer services, and authored browser code and user Workers as untrusted. The same boundary must apply in hosted apps and local development. Serving ContextLayer UI inside an authored app must not grant that app trusted authority.

Web and platform management APIs must require native web sessions or explicitly authorized CLI credentials and must reject viewer-cookie authentication. Viewer-cookie acceptance must be explicit and limited to platform app resolution, platform tool execution, and web's private-organization membership fact endpoint. General profile and organization reads must require native web or CLI credentials. Viewer credentials must not contain reusable management credentials or permit replay as a native web session; rejecting a cookie name alone does not establish that separation.

Hosted authored apps should receive only explicitly delegated runtime capabilities bound to the canonical app and viewer. Local authored apps should receive only runtime capabilities bound to their selected local resources, with personal-account authority derived from the verified developer. A tool-execution capability must authorize only its permitted runtime operation, without granting account creation, connection selection, general organization access, or arbitrary authenticated API forwarding. Trusted services must hold credentials and enforce authorization; user code should receive only the capability and its permitted result. Platform should own app authorization decisions, and dispatcher should consume those decisions and transport requests without duplicating policy.

Untrusted browser code and user Workers must never receive reusable ContextLayer management credentials. Fetching authored content, including `/slate.json`, must not carry web session cookies or CLI access tokens, including across redirects. Private content must still require viewing authorization without disclosing the caller's management credential. Trusted auth must own viewer-session changes; authored responses must not create, replace, or clear ContextLayer authentication cookies.

Account selection and other privileged chrome operations must run on a trusted browser origin. Shadow DOM isolates styles, not JavaScript authority. An authenticated same-origin relay available to chrome is equally available to authored page scripts and must not expose management operations. Cross-origin frame messages must validate the sending origin and frame and carry only the intended presentation interaction, such as resizing; they must not expose credentials or become an authenticated API bridge. Chrome system requests should run independently of the authored app's React Router loaders and user Worker and enter neither app-request nor tool-execution clips metering. Billing policy should remain owned by the existing metering paths.

Local development must preserve the same boundary. A saved CLI credential must remain in trusted local tooling and its auxiliary Worker and must not be exposed to authored browser or Worker code. Browser origins serving local apps must not gain credentialed web/platform API access through blanket localhost trust. HttpOnly, cookie domains, and CORS should support the boundary without replacing the separation of authority.

## Authority model — principles

Authority means the operations and resources a verified caller or delegated runtime capability is permitted to use. The system must establish that authority at a trusted preparation boundary and carry its scoped result into execution. Interfaces and domain signatures must exclude inputs that would let a caller substitute a different credential Owner, declaration source, or binding. Reshape existing platform interfaces when necessary to remove those choices; do not preserve an ambiguous local-or-hosted execution operation and compensate with provenance flags or permission branches.

Personal-account discovery and execution must derive their resource Owner from the verified caller's user identity. Neither HTTP requests nor execution-facing domain callers may supply an Owner, organization, or declaration that changes this derivation. A requested account ID selects an account within that personal scope; it must never select the identity or confer account authority. App access, subscription, and usage context must remain separate from credential ownership.

Hosted preparation must own coherent pushed declaration selection, consumer selection, resource Owner derivation, and production assignment resolution under the canonical authorized app and run actor. A caller may request an operation through the delegated runtime interface, but must not replace its declaration, selected Owner, or resolved assignment. Pure collection and consumer selection remain shared functions; trusted preparation owns the I/O and authorization rather than making each downstream consumer reread declarations or decide authority independently.

Common provider execution should receive an already scoped native Composio session plus the tool and arguments. Session creation belongs to the trusted personal or hosted preparation path, which fixes identity, declared toolkit, and account pinning before execution. Provider execution has no responsibility for choosing app, viewer, developer, or resource Owner. Account ownership enforcement remains at the provider boundary. A low-level session helper must not become a public execution operation accepting an arbitrary Owner.

Native authentication route composition must keep personal-account operations under native web or authorized CLI authentication and exclude viewer cookies. Published runtime delegation retains its limited app/viewer authority; it must not authenticate personal-account management operations. Explicit Owner-management operations are separate and enforce their own Owner authorization. This structure must exclude local declarations from hosted authority, local bindings from production assignment selection, caller-selected credential Owners from personal execution, and runtime viewer credentials from management authentication.

## Platform and web: ownership and dataflow

Web owns Better Auth users, sessions, organizations, and organization memberships. Platform owns app membership as the separate app-to-user relationship. Platform owns apps and their authorization. Platform stores the owning user or organization ID, without copying web's identity or membership records. A browser session cookie is a signed opaque session identifier; platform does not extract identity from it or verify it with another session secret.

For trusted dashboard requests, platform forwards the user's native Cookie header to web's `/api/auth/get-session` endpoint and uses the verified user returned by Better Auth. CLI requests retain their scoped bearer access tokens. The request's verified identity and credential flow through the Hono boundary into shared domain functions and dashboard React Router loaders. Web's `/api/me` owns the current-user profile contract: `{ id, name, image }`, with nullable image and no response caching. It accepts authorized CLI bearer tokens and native web cookies. `ctx whoami` calls web directly using the origin of `CTX_AUTH_ISSUER`; platform does not expose or proxy that endpoint. Trusted chrome should read the profile inside its own frame; authored SDK/runtime code should expose no profile-read capability.

Required authentication has one Hono middleware implementation. Protected API and Git routes respond with 401 when identity is absent. Dashboard routes enable the sign-in response: an unauthenticated GET that prefers HTML through Hono's native `accepts` helper redirects to web's `/auth/sign-in`, passing the requested dashboard URL as Better Auth UI's `redirectTo`. The existing UI supplies it as Better Auth's social `callbackURL`; web owns authentication and trusted-origin validation. Requests that do not prefer HTML retain 401. `Accept` selects the response behavior; request `Content-Type` describes the body. Platform reuses the web cookie after sign-in. Production uses web’s native Better Auth cross-subdomain cookie on `usecontextlayer.com` and trusts the platform sign-in return origin.

CSRF protection follows identity verification and uses the verified credential kind. Cookie and viewer-session authenticated form mutations must pass Hono's native Origin or Sec-Fetch-Site checks. Verified bearer requests do not require browser origin metadata. Requests without verified identity reach the existing authentication boundary and its sign-in response or 401 challenge.

For management requests, when platform needs user-scoped web facts such as organization memberships, it forwards the same user's authorized native web cookie or CLI access token. Web authenticates the caller and returns authoritative facts through its authenticated endpoint; platform applies its own app rules to those facts. These requests do not use a machine-to-machine credential. Better Auth owns credential verification and session revocation; platform owns the resulting app-access decision.

## Resource configuration and execution — principles

These are architectural requirements for local development and production. Implementation decisions, progress, and verification belong in the ExecPlan; recording a requirement here does not assert that its implementation is complete.

`Slate` means one consumer's authored resource declaration; `Resources` means the collected requirements with consumer metadata. A consumer is the app or a named agent. A binding selects the concrete resource used to satisfy a requirement; a connection assignment is the platform-stored connection binding keyed by app, Owner, and slug. `Owner` is the canonical user-or-organization identity that owns an app or resource; `owner` and `viewer` are declaration modes for selecting a resource Owner in hosted execution. A run actor is the app or user a job acts for, independently of resource ownership. An app member is an explicitly established app-to-user relationship; an organization member has a separate web-owned organization membership. Keep these concepts distinct in configuration and execution.

One shared declaration model must feed all consumers. public/slate.json and agents/{name}/slate.json use exactly the same Slate schema and form one app-wide namespace per resource kind. A repeated name denotes the same resource: connection declarations must agree on mode and toolkit, and folder/secret declarations must agree on mode. Central collection and validation must retain which app or agent requires each resource. Configuration uses the whole collection; execution uses the shared pure resourcesForConsumer selector for the app or named agent.

Local inputs must be applied at the local construction boundary before consumer selection. Resources must already reflect the current folder's validated declarations; local connection bindings, environment-supplied secrets, and developer-local folder directories must be assembled there as well, before runtime consumers receive them. Resources remains the collected requirements value; resolved bindings and secret values are execution inputs, not authored requirements. Consumers must not reread local files or environment variables, apply local overrides, or look up production assignments after selection. Shared schemas, collection, selection, and provider primitives should serve both environments; environment-specific I/O and authority belong at their respective boundaries.

Local connections must always use the signed-in developer's personal accounts, regardless of app ownership or the declaration's viewer/owner mode. Platform must derive that personal Owner from verified authentication and independently authorize the narrowly requested toolkit/account before provider work. Neither a local declaration nor an account ID grants access to another user or organization's accounts. Save development resource-name-to-account-ID bindings in ignored configuration in the app folder; do not read or write production assignments to resolve or save local choices. Composio retains provider credentials.

Local secret values must come exclusively from developer-local environment variables. Local folders must be developer-local directories managed by local tooling under the app's .contextlayer directory. Resolving a folder's local path is configuration; granting a runtime filesystem access to that directory is a separate capability responsibility. Neither a declared folder nor its resolved path establishes filesystem access. Local resolution must never use platform vault values, hosted folders, or production configuration as a fallback. Local declaration evaluation and development configuration remain on the developer's machine; pushing authored Slates does not publish development bindings or environment values. Chrome must be disabled in local development through native Vite development detection; local configuration uses the CLI identity.

Production resource resolution must derive the canonical Owner from the pushed declaration and authorized actor: viewer selects the acting user's user Owner, and owner selects the app's owning user or organization. Platform owns production connection assignments; production secret references select the existing Owner/name vault model; folder ownership follows the declaration. Owner authorization must precede account management or vault management. Public visibility grants viewing only, while the owning user or an owning-organization member has app management permission independently of visibility. Published runtime delegation may permit an authorized viewer to execute an app's owner-mode requirement without granting general Owner account or vault management. Local personal-account execution must preserve a separate authorization path from that published delegation.

## Platform storage and request flow

Hosted declaration consumers must share one coherent latest-`main` repository snapshot, read through native Artifacts by canonical AppID and validated with the shared Slate schema. The declaration reader receives no caller credentials; platform authorization precedes its use. Repository declaration reads must bypass authored Workers, public dispatch, and clips metering, keeping credentials inside trusted services. App configuration, tool execution, agent preparation, and publication registration must consume this common declaration boundary. API and scheduled agent runs are hosted executions even when their caller is a developer; neither may read that developer's local declarations, bindings, or environment.

Developer resource configuration must use only the current app folder's declarations. Local tooling reads public/slate.json and agents/{name}/slate.json, validates them with the same Slate schema, and collects Resources locally, without supplementing requirements from pushed or deployed state. Platform must never accept caller-supplied local Slates or Resources as declaration authority for resource listing, assignment, or execution, including from app owners. Local tooling composes local requirements with independently authorized account metadata; platform must answer only narrowly scoped connected-account discovery and execution requests for that local workflow. Hosted CLI targets, chrome, and dashboard use the coherent pushed snapshot and platform-owned production configuration.

The dashboard uses shadcn/ui with the `base-nova` preset and standard Tailwind layout utilities.

Platform separates page routes from asset URLs: React Router's basename is `/dashboard/`, while Vite uses its default `/` asset base. Cloudflare's native selective `assets.run_worker_first` sends `/api/*`, `/git/*`, and `/dashboard/*` through the Worker, including dashboard data requests. Scripts, CSS, and fonts use native asset serving outside those routes; production bundles live under `/assets/`. This configuration belongs only to platform. User-app requests retain the existing dispatcher authorization flow.

App visibility is platform configuration stored in the non-null text column `app.visibility`, separate from ownership and the authored Slate. `appVisibilitySchema` validates `public` or `private` in code, and `DEFAULT_APP_VISIBILITY = "private"` supplies the creation default; migration 004 independently backfills existing rows to private. There is no PostgreSQL visibility check or persistent default. Database app rows are parsed into the app schema before returning app-bearing domain results. `PATCH /api/apps/{target}` accepts `{visibility: "public" | "private"}` for an AppID or public hostname. Its shared `updateAppVisibility` function enforces app management permission for the owning user or owning-organization members, writes only visibility, and returns the saved app. Public viewing grants no management permission.

Hono middleware creates a request-scoped Postgres.js/Kysely connection from validated Worker bindings and passes through the native Artifacts binding. Route groups select identity verification: app resolution and tool execution accept viewer cookies as well as native web/CLI credentials; other APIs, Git, and dashboard use only native web/CLI credentials. The middleware stores the optional `AuthIdentity`; protected groups require it before running. API handlers and React Router loaders share these through their framework contexts; `waitUntil` closes the database after the handler finishes. The Cloudflare Vite plugin runs development in workerd and builds the Worker plus client assets. The platform's `app` table contains `id` (UUID primary key, generated by Postgres), `public_hostname` (text with a unique index), and nullable text `owner_user_id` and `owner_organization_id` columns. PostgreSQL's `app_exactly_one_owner` constraint requires exactly one owner. App identity is immutable; the public hostname is independent. Package-owned Kysely migrations and Kanel-generated models follow the retained `db-infra` patterns, using a separate logical database on the shared local Postgres instance.

Local platform development and integration Workers must use remote Cloudflare resources isolated from production. Native Wrangler environments and framework configuration select bindings before requests run; runtime callers must not select namespaces or override this boundary.

`POST /api/apps` requires authorized CLI bearer or native web-cookie authentication and passes the verified identity, auth issuer, and validated creation input into `createApp()`. The shared domain function resolves an optional `organization_slug` against the caller's authoritative organization records before any writes; an absent membership returns 404. Omission selects the verified user. With the resulting typed user-or-organization `Owner`, it generates a friendly adjective/color/animal hostname, inserts a private app, and creates an Artifacts repository named by its UUID. Better Auth in web owns user identities and organization memberships; platform stores their IDs, with no cross-database foreign keys or copied memberships. The agreed viewing rule allows anybody for public apps, the owning user for private personal apps, or members of the owning organization for private organization apps; the platform resolution endpoint and app connection/tool route groups enforce this rule, with Git source access and management restricted to the owning-user or owning-organization-member rule regardless of visibility. Organization membership checks use that app's owning organization regardless of the session's selected workspace. `ctx init` requires the saved login before scaffolding, sends the optional organization slug and its access token to creation, and sets `/git/<app-id>` as the project's remote. `GET /api/apps` and the dashboard loader call the shared `listApps()` operation, which returns only apps manageable by the verified caller and their latest main-branch Artifacts commit. Commit hashes remain Cloudflare-owned data. Zod defines API contracts, with OpenAPI at `/api/openapi.json`.

`GET /api/apps/resolve?hostname=<public-hostname>&pathname=<incoming-path>` inherits optional identity verification and viewing authorization through Hono middleware. `resolveAppForViewing()` looks up the unique `app.public_hostname` and delegates to `authorizeAppViewing()` using the validated canonical app and already-retrieved membership facts. The viewing and management predicates are pure; the domain operation owns membership I/O. Public viewing allows anybody; private viewing requires the owning user or membership in the owning organization. Web owns the authoritative `{id, slug, name}` organization records used for membership checks and organization-slug resolution. Platform obtains those facts through trusted service calls; a viewer credential does not grant direct access to web's organization API. Successful resolution returns the immutable AppID and canonical Owner; required sign-in returns 401, denied viewing returns 403, and an unassigned hostname returns 404. Platform owns the mapping and authorization decision; dispatcher consumes the result for every hosted-app path.

Public hostname assignment rejects subdomains in the hardcoded reserved list in `packages/platform/app/apps.schema.ts`. `local` is reserved because it selects the current checkout in the CLI. `auth` is reserved for the auth-forwarding worker at `auth.contextlayer.xyz`. Neither can be an app subdomain.

Git clients use the immutable `/git/<app-id>` endpoint. The Git route group inherits identity verification and required authentication. `getGitAccess` resolves the app and calls `authorizeAppManagement` before obtaining any repository-scoped Artifacts credentials. Only the owning user or members of the owning organization may clone, pull, or push, including public apps. The Git service determines read versus write credentials: upload-pack reads and receive-pack writes, including their GET discovery requests. Hono's proxy helper forwards protocol traffic; Artifacts credentials stay server-side. Pushes do not create app records.

## App forking, membership, and resource ownership

Git-powered forking must be a core capability of the app model. Users must be able to take an existing application as a starting point and independently adapt its code and behavior while preserving its source lineage. The platform must support forking, app membership, and resource ownership as orthogonal concepts that compose. Shared applications and independently customized applications must both fit the same domain model.

Forking combined with AI must enable customized applications to continue receiving upstream improvements. Git must preserve the upstream relationship and shared history so changes can be identified and merged; AI should help resolve conflicts and adapt upstream changes to the fork's customized code while preserving the intent of its customizations. This is why forking is central to the app model: users should be able to make an app their own and continue benefiting from fixes, features, and improvements to the application they started from. Independent customization and continued upstream evolution must be supported together.

| Concept | Responsibility |
| --- | --- |
| Forking | Independent control over an application's code and behavior, with Git lineage and AI-assisted integration of upstream improvements. |
| App membership | The relationship between an application and the people who use it. |
| Resource ownership | Ownership of credentials, service accounts, and documents, with access governed by resource authorization and bindings. |

Forking must use Git to create an independently customizable application while preserving source ancestry. A fork must have its own app identity and repository, with its own ownership and membership context. Its Owner may be the same as the source app's Owner or a different user or organization. A fork must support one or many app members, just as any other app does. Git lineage must describe the relationship between codebases; it must not determine app membership or resource access.

App membership must allow multiple people to use the same application without requiring separate code forks. Member-specific resources should support personal state within a shared application. Independent changes to application code should be expressed through forking rather than through membership. Forking must not replace membership, and membership must not prevent forking.

Resource ownership must remain independent of code lineage and app membership. Credentials and service accounts must belong to their user-or-organization Owner independently of any app; document folders must retain their declared ownership and authorized bindings. Apps should be able to share authorized resources without sharing control of their code. A code fork must not itself copy credentials, transfer ownership of documents, or grant access to the source app's resources. Resource access must follow the platform's authorization and resource bindings.

Forks and shared applications must use the same resource-selection and execution semantics. An agent's unattended scope must continue to derive from its own actor-dependent requirements, independently of whether its app is a fork or how many members use it. Forking, membership, and resource sharing should let people choose independent code customization, shared application use, and shared resources without making any one choice determine the others.

## Owner-owned shared secrets

Shared secrets belong to the canonical user-or-organization `Owner`, independently of app ownership. `PUT` and `DELETE /api/secrets/{type}/{owner_id}/{name}` accept `user` or `org` at the HTTP boundary and return only `{ owner, name }`. `ownerParamsSchema` in `packages/platform/app/owner.schema.ts` validates Owner path parameters and converts the HTTP type into the canonical Owner type; secret-specific contracts live in `secrets.schema.ts`. `setSharedSecret` and `dropSharedSecret` call the shared `authorizeOwner` in `owner.server.ts` before Doppler I/O. A personal Owner must match the verified caller; an organization Owner requires membership supplied by web through the existing credential-forwarding flow. Connections reuse that same authorization. No app lookup or subscription is involved in managing an Owner's secrets.

Doppler owns platform vault storage; the [development guide](DEVELOPING.md#shared-secret-management-verification) owns vault configuration for development and production platform environments. That platform-development vault is separate from authored-app local development, whose secrets must come exclusively from developer-local environment variables. Platform generates `OWNER_<USER|ORGANIZATION>_<uppercase UTF-8 hex Owner ID>_<name>`; clients cannot select provider keys or configs. The vault project/config and its scoped read/write service token are platform configuration (`CTX_CUSTOMER_CREDENTIALS_DOPPLER_PROJECT`, `CTX_CUSTOMER_CREDENTIALS_DOPPLER_CONFIG`, and `CTX_CUSTOMER_CREDENTIALS_DOPPLER_TOKEN`), validated together in `env.ts` when an authorized secret operation runs. Other platform operations do not require it. The platform token covers the config, so platform authorization enforces Owner isolation. Provider responses are not returned or logged; failures expose only operation/status. For hosted execution, Slate secret names and modes resolve to canonical Owner/name references. Internal `loadSharedSecret` retrieves the literal Doppler `value.raw` for trusted execution; it exposes no plaintext HTTP operation.

The CLI's `owner.ts` resolves the personal Owner through `/api/me` or an organization slug through web's authoritative organization endpoint, shared by secret and connection management. It keeps the canonical Owner until `ownerPath` serializes the API path. `secrets.ts` calls the platform secret API with that Owner and the existing login. Clack's native password prompt masks values; `--stdin` bypasses prompting and preserves the exact UTF-8 input. Cancellation ends before submission. CLI output contains only Owner/name, and the CLI never receives the vault token.

## Authored agents

An app can contain named agents at `agents/<name>/instructions.md`. The app's existing Git push publishes their standing instructions into its Artifacts repository. `GET /api/apps/{target}/agents/{name}` returns `{ commit, instructions }` from the latest commit on `main`, pinning the file read to that commit. `getAgent` in `packages/platform/app/agents.server.ts` applies the same owner/owning-organization-member source permission as Git, including for public apps, then calls the shared native Artifacts reader. The endpoint follows the existing authenticated app boundary and Zod/OpenAPI contract. Reading the definition is independent of the app's build or deployment; the repository remains its source.

Hosted execution separates the authorized trigger, prepared run, and native execution. The trigger supplies a canonical app, explicit app/user actor, and user prompt. Preparation resolves declared resources to canonical Owners and connection assignments before background execution. The prepared run carries agent instructions and source revision, resource references, and the actor; caller credentials and secret values stay out of persisted configuration. An app actor has no person against whom viewer resources can resolve. Source inspection follows app management authorization; manually requested jobs follow private-app viewing authorization independently of membership.

A stable native Think instance is addressed by app, agent, and actor. Each job has its own submission UUID within that instance. Resource configuration belongs to the shared instance; queued jobs may use resources configured by a later submission. Creation and retrieval use the same native instance name through the Agents SDK. Think owns the durable queue, execution lifecycle, status, conversation, and saved assistant messages. API and scheduled runs share preparation, submission, and result retrieval. Job details expose `{ id, instance_name, source, status, result, error? }`, with `source: api | schedule`; native messages remain the result store rather than being copied into a platform ledger.

The hosted Think instance owns its Linux sandbox. Platform prepares the Artifacts-backed Git checkout at `/shared`; the agent uses Bash and ordinary Git to edit, commit, and push documents. Pushed Git content survives sandbox replacement, while Think retains conversation state independently. Platform instructions distinguish shared persisted work from scratch files. System context combines runtime, platform, and authored instructions; each job's task remains a separate user message.

Hosted interactive tool calls and hosted agent MCP share connection-session creation. The validated consumer declaration supplies the toolkit, the assignment supplies the account ID, and the canonical resource Owner supplies Composio's session identity. Composio owns external credentials and API calls; Think owns MCP connection readiness and tool conversion. MCP authentication remains in the trusted Worker. Model credentials are loaded from the selected Owner's secret store directly into the trusted provider, without entering persisted run configuration, prompts, or documents.

Scheduled publication extends the existing Artifacts push → native CIWorkflow build → app deployment flow through a trusted build-to-platform service binding. After deployment succeeds, the callback passes only app identity. Registration consumes the shared reader's discovered agent tree references and reads schedule files from those immutable trees; the event's build commit does not select declarations. Schedule payloads carry app and agent identity, schedule name, and user prompt. Each firing prepares execution from the latest coherent snapshot, as API jobs do. Authored schedules live at `agents/<name>/schedules/<prompt>.md`: YAML frontmatter declares canonical five-field UTC cron, and the Markdown body is the scheduled user prompt. The Agents SDK owns parsing and persistent cron recurrence; Cloudflare Durable Object alarms wake the named instance. The callback uses the same execution and result primitives as API jobs. Authored schedule registration must preserve Think's own queued-turn schedules.

Local execution belongs to the CLI's `packages/cli/agents.ts`. From the app root, `ctx agent local run <name> <prompt>` reads that checkout's `agents/<name>/instructions.md` and invokes Claude Agent SDK with the app root as its working directory. The native `claude_code` system preset supplies runtime instructions; its appended text contains platform instructions followed by the authored file. The task is a separate SDK `prompt`. Explicit `settingSources: []` disables automatic user/project settings and CLAUDE.md loading, while native managed policies still apply. The command prints the successful final result and surfaces SDK failures. It uses native Claude authentication and does not contact the platform. The SDK is loaded only for agent execution and remains an external runtime dependency so its matching Claude executable can resolve normally.

### App membership and unattended execution

App membership must record which existing users use which apps. An app member is the relationship `(app_id, user_id)`; web must own the person's identity. Membership and unattended execution must remain separate domain concepts: membership supplies people, while each agent's own resource requirements determine its unattended execution scope. An app may have members with no unattended agents, only app-scoped agents, or a mixture of app-scoped and member-scoped agents. Agent requirement changes must not change membership.

Membership must be established through explicit joining or app creation. Creating an app must automatically join its individual creator in the same database transaction, including when the app belongs to an organization. Other organization members must join explicitly. Joining an app must enable its member-scoped unattended work to act for that member using the declared resources. Viewing or opening an app must not create membership. Joining must be the single enablement action; no separate unattended-work opt-in or enablement setting is required.

Platform must store membership in `app_member` with `(app_id, user_id)` as its primary key, an app foreign key with cascading deletion, and the web-owned user ID. `POST /api/apps/{target}/join` must require native web or CLI authentication and existing app-viewing permission, reject public apps, and return `{ app_id, user_id }`. Repeated joining must return the same relationship. The shared `joinApp` operation must own membership insertion and be reused by app creation inside its transaction. The CLI must call this operation through the API with the saved login, resolving an app target through existing app-target handling. Membership creation must not itself trigger a job.

An agent requiring any `viewer` resource must be member-scoped for unattended execution. An agent requiring zero `viewer` resources must be app-scoped. This derivation must consider all actor-dependent requirements, including connections, secrets, and folders. Unattended scope must be derived from requirements rather than independently configured or stored as a separate execution-target setting.

| Concept | Meaning |
| --- | --- |
| Unattended scope | Derived from the agent's requirements: `app` or `member`. |
| Run actor | The concrete app or app member that one run acts for. |
| Resource mode | `owner` selects the app's owning user or organization; `viewer` selects the acting member's user Owner. |

App-scoped unattended execution must run once for the app, with the app itself as actor and no acting person or invented system user. Member-scoped unattended execution must run for app members, with each run acting for a particular member. Explicitly joined membership must supply the actors for member-scoped execution and must carry no agent scope setting. Joining determines who participates; the agent's requirements determine its unattended scope.

Hosted resource ownership must remain orthogonal to unattended execution scope. Hosted resource resolution must select the app's owning user or organization for `owner` mode and the acting member's user Owner for `viewer` mode. A member-scoped agent may read a member's Gmail, use the organization's model credential, and write to that member's app-specific priorities folder. An app-scoped run has no member against whom a `viewer` resource could resolve; deriving scope from requirements excludes that incompatible combination.

The derivation must use the agent's own requirements, independently of the app's interactive requirements. An app may use `viewer` resources while its unattended agent requires only `owner` resources and runs once for the app. Unattended scope must not determine interactive app identity or redefine manually requested job behavior.

```text
Agent requirements → unattended scope
  app    → one run acting for the app
  member → app membership supplies members → runs acting for particular members

Run actor + resource declaration → selected resource
```

## Build pipeline

Artifacts push events in `contextlayer-prod` start the `contextlayer-build` Workflow. `packages/build/index.ts` subclasses the SDK’s `CIWorkflow` with a build runner (`pnpm install --frozen-lockfile && pnpm build`) followed by a chained deployment runner. The SDK checks out the event’s commit, captures logs and status, and retains the workspace snapshot in the `contextlayer-build-backups` R2 bucket. The official Sandbox image supplies the runtime; the package Dockerfile adds the workspace’s pnpm version.

The deployment runner restores the successful build workspace and invokes Wrangler to deploy the Worker and static assets into the `contextlayer-prod` dispatch namespace, using the Artifacts repository name (AppID) as the Worker name. Only this runner opts into the SDK’s `cloudflareCredentials` capability, backed by the `CF_TOKEN` Worker secret. Operators inspect both steps in Cloudflare’s Workflows dashboard. ContextLayer’s app dashboard does not expose build status yet. The Artifacts push trigger and resource bindings belong together in the build Worker's Wrangler configuration.

## Worker deployment and secrets

Cloudflare Workers Builds owns repository-driven deployment of platform, dispatcher, auth, and build. This is separate from the build Worker's authored-app publication pipeline. All four Workers must use the same repository-root build/deploy workflow. Doppler owns centrally managed deployment secret values; each Worker's effective Wrangler configuration owns its required secret names through native `secrets.required`, including an explicit empty list when no secrets are needed. The shared deployment workflow connects these owners and must not maintain another secret allowlist.

The config-scoped read-only Doppler bootstrap token and private registry credential stay in the Workers Builds environment. Deployment selects only the Worker’s declared runtime secrets and supplies them alongside code through native Wrangler deployment; Cloudflare holds deployed copies, while Doppler remains their source. The build Worker's snapshot credentials and authored-app deployment credential follow this same delivery boundary. Its authored-app build runner must never receive the deployment credential; only the chained deployment runner may request that capability.

## Viewer organization membership

Web owns sessions and organization membership; platform owns app visibility and access policy. Private organization viewing first validates the viewer session with Better Auth, then calls web’s `GET /api/viewer/organizations/:organizationId/membership` with the viewer cookie and the canonical app’s owning organization ID. Web validates the session, reuses its existing membership query, and returns only `{isMember}` with no response caching. Native web and CLI callers continue using `/api/platform/organizations`. Platform’s `resolveAppForViewing` selects the appropriate read and passes `isOwnerOrganizationMember` into the shared pure viewing/management rule. The app-resolution and runtime-tool routes share this flow. App listing still retrieves the organization list once and derives the membership fact per app. No memberships are copied into platform or the viewer cookie, and the existing session/logout lifecycle is unchanged.

## Hosted-app routing

`packages/dispatcher` owns the wildcard Worker route `*.contextlayer.xyz/*`. It asks platform to resolve the incoming hostname and authorize viewing for every request, including `/slate.json`. Runtime authority is bound to the app and viewer; the viewer credential does not grant general platform API access. On success, dispatcher invokes the Worker returned by `APPS.get(id, {props})`; on required sign-in it redirects to auth's `/start` with the original request URL as `return_to`; other failures pass through. Dispatcher must remove ContextLayer authentication credentials before invoking authored code. Request-scoped RPC props must expose only the explicitly delegated capabilities. Authored responses must not create, replace, or clear ContextLayer authentication cookies. `APPS` binds the WfP dispatch namespace. Platform owns identity-based app authorization, hostname mapping, visibility, and membership decisions; dispatcher has no database, mapping cache, or duplicate authorization policy.

The platform is deployed at `https://slate.usecontextlayer.com` with Neon Postgres configured through Doppler `platform/prod`. The dispatcher’s `CTX_PLATFORM_URL` points to that address; it no longer depends on a local server or tunnel. Wrangler builds and deploys the Workers.

### Cross-site chrome authentication — principles

The header must run in a separate document on a trusted origin: `slate.usecontextlayer.com`, `frame.usecontextlayer.com`, or `usecontextlayer.com`. Private app entry should leave the header authenticated as the same viewer automatically, without an additional popup sign-in step. The frame's session flow must work across the site boundary to `contextlayer.xyz` while preserving isolation from the authored parent.

Better Auth should own identity verification and session revocation. The frame should authenticate directly with the native web session, and web logout must invalidate its authentication. Native session cookies must use Secure, HttpOnly, and SameSite=None in every environment. Credentials must remain in trusted documents and services; the authored parent must receive neither credentials nor profile/connection data. Browser third-party-cookie policy must be respected; cookie attributes and CSP must not be treated as a way to override it.

CSP should restrict frame ancestors to intended HTTPS authored-app hosts. Local development must not embed chrome. The frame should forbid object embeds and base-URL changes. Frame forms must submit to the trusted platform origin; CSP must also permit https://connect.composio.dev and https://dashboard.composio.dev so the platform's native connection-authorization form can follow Composio's Connect Link redirects to its connection page. Cookie-authenticated form mutations must reject cross-site submissions through the framework's native CSRF protection. Better Auth's origin checks must remain enabled, and authored origins must not gain credentialed CORS access to web or platform.

### Viewer sign-in boundary — principles

Web's Better Auth should own the user's identity and web session, and auth should own viewer sign-in on the user-code domain. Viewer sign-in must identify the same user without copying a reusable web session credential into the authored-app domain. Viewer authority must be limited to viewing and explicitly delegated app runtime operations and must not authenticate web/platform management requests.

Platform should own public/private viewing authorization and apply the same visibility rule to `/slate.json`. Dispatcher should ask platform for that decision and supply only app/viewer-bound capabilities to authored code. Private viewing and declaration retrieval must preserve the security boundary above: authentication must stay in trusted services, and authored requests, responses, and redirects must not expose management credentials or control viewer-session changes.

### Local tools

This section defines the agreed tool-call contract and its ownership boundaries. Future authoring-agent skills should reference it. Local and hosted execution must share the authored Tools interface and provider primitives, with configuration and authorization composed at their respective trusted entrypoints.

Apps declare connection requirements in `public/slate.json`, keyed by slug, and call `tools.call(slug, toolSlug, args)`. Trusted execution resolves the slug within that consumer's requirements. Local tooling selects the developer's saved local account binding; hosted execution selects the pushed declaration's canonical Owner and production assignment. Bindings store connected-account IDs, never provider credentials. Composio owns provider credentials, refresh, and tool execution.

```ts
await tools.call("work-email", "GMAIL_FETCH_EMAILS", { max_results: 5 });
```

`@usecontextlayer/sdk/vite` owns Vite integration and delegates current-folder resource I/O and saved-login access to CLI-owned local tooling. Development startup must assemble validated app/agent requirements, ignored local connection bindings, environment-supplied secrets, and developer-local folder directories before runtime consumers receive their selected resources. Git origin may identify the app for existing app access/billing concerns; it must not select pushed requirements or production bindings for local resolution. The access token remains in the trusted auxiliary Worker, with no credential exposure to authored code or refresh token copied into the Worker. Exact binding transport and environment-variable mapping belong in implementation decisions.

The shared `tools-worker` subpath owns separate typed `Tools` and `LocalTools` WorkerEntrypoint classes with shared HTTP result/error handling. Dispatcher re-exports hosted Tools; SDK bundles LocalTools and exports it as Tools through `@usecontextlayer/sdk/local`. Each entrypoint must establish its own authentication and request contract before shared transport. The pure shared tools contract owns the HTTP tool-result schema used by both platform OpenAPI and Worker response parsing; response consumers must not maintain separate copies or import Worker entrypoints to obtain the schema. The SDK owns the Tools interface/React Router context and local binding configuration. `@usecontextlayer/sdk/worker` exports `createApp`, which owns the React Router request handler and selects the local Tools binding or production `ctx.props.tools`. The app supplies its virtual server-build import and Vite mode/development values. Generated files contain thin wiring; ContextLayer runtime and Vite behavior live in packages. The Gmail page remains an example, not the default application.

During local development, the Cloudflare Vite plugin runs the React Router app and a development-only auxiliary Tools Worker. A native RPC service binding supplies the Tools handle, which the app entrypoint puts into React Router context. The trusted local Tools boundary must resolve the connection slug and declared toolkit from the assembled local configuration, then request concrete personal-account execution with the selected account, toolkit, tool, and arguments. Platform must authenticate and independently authorize that personal-account operation; local requirements must not be sent as platform declaration authority. Provider execution retains the existing result/error contract. Exact HTTP routing must preserve existing app access and billing policy rather than silently changing it.

The hosted entrypoint receives its Tools handle through dispatcher-supplied `ctx.props.tools`. The trusted Tools entrypoint binds the platform-resolved AppID and authenticated viewer to the request-scoped capability. Platform verifies the delegated authority and resolves the pushed declaration's viewer or app Owner assignment before execution. Cloudflare scopes the RPC handle to the current request; the app cannot read its underlying props or substitute another app or viewer. The local and hosted paths should reuse the shared Tools interface and provider execution primitives while preserving their distinct authorization sources. Accepting a runtime capability does not make the viewer cookie a management API credential. Composition stays at the trusted entrypoint, and the local auxiliary Worker and its token binding are excluded from production builds.

## Key contract: app resource requirements

The author owns `<APP_DIR>/public/slate.json`, served at `/slate.json` by the framework's native static-asset handling. It declares the interactive app's resource requirements; `agents/{name}/slate.json` declares each agent's requirements using exactly the same shared schema. Vite serves the app's local file during development and includes it in the production assets, so each deployment carries its own requirements. Do not add a custom resource route, a copied root Slate, or a separate requirements store.

The Slate contains a `connections` object keyed by the slug used in `tools.call(slug, toolSlug, args)`. Each connection declares its Composio `toolkit` and `mode` (`viewer` or `owner`). Named `folders` and `secrets` objects declare the same modes; missing maps mean no requirements of that kind. In production, `viewer` selects the acting user’s user Owner and `owner` selects the app’s owning user or organization. Local development retains those authored modes for publication but uses the developer-local sources defined above. New apps start with empty `connections` and `secrets` objects. `@usecontextlayer/shared/slate` owns the Zod Slate contract and mode vocabulary; CLI, SDK, and platform use it. For example:

```json
{
  "connections": {
    "work-email": {
      "toolkit": "gmail",
      "mode": "viewer"
    }
  }
}
```

Named resources form one app-wide namespace across consumer Slates. Shared `collectAppResources` accepts `{ app: Slate, agents: Record<string, Slate> }` and returns the explicit `Resources` type: the same named connection, folder, and secret maps as `Slate`, with consumer metadata on each requirement. Repeated connection requirements must agree on mode and toolkit; repeated folder and secret requirements must agree on mode. Conflicts raise validation errors, with no file precedence or inheritance. The pure `resourcesForConsumer(resources, consumer)` function returns a filtered `Resources` value for `{ type: "app" }` or `{ type: "agent", name }`, retaining requirement and consumer metadata without reading files or applying overrides. Configuration uses the full collection and execution uses this selector; authored Slates remain unmodified. Folder requirements declare ownership selection; concrete repository/path configuration and mounting belong to resource resolution.

Platform's `readAppDeclarations` owns the repository declaration boundary. It uses the native Artifacts binding and a disposable repository handle, resolves `main` once, discovers agent directories through that commit's Git trees, and reads `public/slate.json` plus each `agents/{name}/slate.json` using the resolved commit hash. Each file passes through the same shared Slate schema before collection. The result contains the commit, discovered agent tree references, original consumer Slates, and collected resources; the hash establishes a coherent read rather than a deployment pointer. The reader accepts no caller credentials, resolves no resource bindings or secret values, and creates no instances or jobs. Hosted declaration selection must always use this reader rather than caller-supplied Resources. Downstream operations receive plain Resources: configuration uses the complete collection and execution selects its consumer through `resourcesForConsumer`. The immutable commit stays in the repository reader's result for instruction and publication coherence; configuration consumers need no source or commit flag.

Local tooling reads every app/agent Slate in the current folder and collects Resources locally. Callers inspecting a running app can fetch its static `/slate.json` under viewing authorization, but that deployed asset must not become a second authoritative hosted declaration source. Hosted operations select requirements from the coherent repository snapshot. Production connection requirements select assignments stored by `(app_id, owner_type, owner_id, slug)` in platform Postgres; production secret declarations reference `(Owner, name)` in the existing Doppler vault and need no assignment record; folder declarations select ownership mode without defining a repository/path binding. Parsing and collection contain no account IDs, resource bindings, or secret values. Trusted configuration assembly supplies the selected environment's bindings before handing them to runtime consumers.

**Load-bearing security invariant:** platform must derive Composio's session `user_id` from the authorized canonical credential Owner, never from a caller-supplied connected-account ID. ## Owner-scoped connection assignment storage

`app_connection_assignment` stores choices using `(app_id, owner_type, owner_id, slug)` as its composite primary key. `app_id` is a UUID foreign key to `app.id` with `ON DELETE CASCADE`; the other columns and `connection_id` are non-null text. `owner_type` is `user` or `organization`, matching the canonical `Owner`. `slug` is the declared connection slug and `connection_id` is Composio’s connected-account ID. Toolkit and mode remain in the Slate. Migration 006 renames the former `user_id` column to `owner_id`, preserves existing assignments as user Owners, and changes the primary key; Kanel generates the resulting types. Apply it before deploying this code. Downgrading refuses organization assignments because the previous schema cannot represent them.

Production assignment must load its requirement from the coherent pushed declaration, resolve its mode through `getCredentialOwner`, and use the existing Postgres upsert. Viewer assignment requires app viewing permission; owner assignment requires app management permission from the owning user or owning-organization membership. Public viewing alone grants no ownership authority. Development account selection must save only ignored local bindings and must never change `app_connection_assignment`, even when the developer is also a production viewer or app Owner. Provider-account authorization remains independent of saving an account ID.

The production assignment key identifies app, Owner, and resource; local development must remain isolated through its separate local binding storage rather than introducing an environment dimension into production assignments.

## App-owner billing access

Web’s native Better Auth/Polar integration owns individual and team customer creation, checkout and billing management. Platform receives `customer.state_changed` directly at `POST /api/polar/webhooks`; Polar’s SDK verifies the signature using the required `POLAR_WEBHOOK_SECRET`. `saveCustomerState` upserts the complete native state and event timestamp in `polar_customer_state`, keyed by Polar customer UUID with a unique nullable `external_id`. That external ID matches `app.owner_user_id` or `app.owner_organization_id`. Polar’s merchant `organization_id` is unrelated to our organization ownership. Kanel generates the JSON column with the native SDK Customer State type.

The existing viewing policy still owns public/private and membership authorization. After it succeeds, one `requireAppSubscription` middleware calls `checkAppSubscription` on runtime hostname resolution and actual tool execution. It reads the owner’s saved state and allows a nonempty `active_subscriptions` array; missing or empty state yields 402. Free counts. Dispatcher forwards the actual incoming pathname so exactly `/slate.json` can retain ordinary authorization without requiring billing. It forwards 402 through its existing failure path. Hosted Tools use the app-scoped execution endpoint. Local Tools must use narrowly authorized personal-account execution while preserving existing app subscription and usage policy; distinct request routing must not change billing semantics. Local page rendering itself does not go through hosted dispatch. App creation/listing, dashboard, Git and connection configuration do not require a subscription. Usage metering follows execution: dispatcher records recognised dynamic GETs (1 clip) and POST/PUT/PATCH/DELETE requests (3 clips), while the platform tool API records returned executions (1 clip). The shared `app-usage` module converts the canonical `{ id, owner }` and event name into native Polar ingestion, with `metadata.clips` and `metadata.user_code_worker_id`. Best-effort classification for these methods recognises HTML, JSON (including application `+json`), React Router `text/x-script`, plain text, CSV, XML, NDJSON, event streams and redirects. JavaScript, CSS, image, font and WebAssembly responses and exact `/slate.json` produce no usage events. No SDK-side reporting or route instrumentation is required; rates and canonical owner attribution stay in trusted Workers. Polar’s existing Clips meter aggregates all three event types and owns allowances and prices.
