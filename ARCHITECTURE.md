# Architecture

The repository contains nine packages; `@usecontextlayer/cli` and `@usecontextlayer/sdk` are public and the others are private:

- `cli` — Published as `@usecontextlayer/cli`; Commander-based `ctx` executable, bundled with tsdown; its version comes from its package manifest, and `init` delegates project creation to the official `create-cloudflare@latest` React Router scaffold.
- `sdk` — Public `@usecontextlayer/sdk` integration: shared React Router document Layout, Tools interface and React Router context, app request handling, local auxiliary Worker, and Vite integration. Subpath exports keep React UI, Vite/Node imports, and Worker runtime imports separate.
- `db-infra` — Postgres/Kysely connections, migrations, and ephemeral database helpers.
- `shared` — Authentication, token handling, test helpers, and Sentry event capping.
- `twilio` — Twilio Functions for founder call routing and answer screening.
- `platform` — Cloudflare Workers application: an Artifacts Git proxy under `/git`, OpenAPI endpoints under `/api`, and the React Router dashboard under `/dashboard`.

- `build` — Cloudflare Worker using `@cloudflare/ci` and Workflows to build commits pushed to Artifacts in isolated Sandbox runners.

- `dispatcher` — Cloudflare Worker that resolves public hostnames through the platform API and invokes the WfP Worker named by AppID.

- `auth` — Worker that owns viewer sign-in on the user-code domain.

## Multiple consumers

Almost every user-facing platform capability is exposed through OpenAPI so the web dashboard, CLI, and a future MCP consumer share the same product operations. Zod owns their input and output contracts. A shared domain function owns each operation’s business logic, authorization, and database calls; API handlers adapt it to HTTP and React Router loaders/actions invoke it directly in-process. UI components own presentation and interaction. This is a standing design rule, not a claim that every future CLI command or MCP surface exists today. Better Auth owns its native authentication protocols; product APIs consume the resulting verified identity.

## Security boundary: trusted services and authored apps — principles

These principles define the security boundary the system must uphold; they are requirements, not assertions that every protection is implemented today.

Treat web, platform, auth, and dispatcher as trusted ContextLayer services, and authored browser code and user Workers as untrusted. The same boundary must apply in hosted apps and local development. Serving ContextLayer UI inside an authored app must not grant that app trusted authority.

Web and platform management APIs must require native web sessions or explicitly authorized CLI credentials and must reject viewer-cookie authentication. Viewer-cookie acceptance must be explicit and limited to platform app resolution, platform tool execution, and web's private-organization membership fact endpoint. General profile and organization reads must require native web or CLI credentials. Viewer credentials must not contain reusable management credentials or permit replay as a native web session; rejecting a cookie name alone does not establish that separation.

Authored apps should receive only explicitly delegated runtime capabilities bound to the canonical app and viewer. A tool-execution capability must authorize only its app-scoped operation, without granting account creation, connection selection, general organization access, or arbitrary authenticated API forwarding. Trusted services must hold credentials and enforce authorization; user code should receive only the capability and its permitted result. Platform should own app authorization decisions, and dispatcher should consume those decisions and transport requests without duplicating policy.

Untrusted browser code and user Workers must never receive reusable management credentials. Fetching authored content, including `/slate.json`, must not carry web session cookies or CLI access tokens, including across redirects. Private content must still require viewing authorization without disclosing the caller's management credential. Trusted auth must own viewer-session changes; authored responses must not create, replace, or clear ContextLayer authentication cookies.

Account selection and other privileged chrome operations must run on a trusted browser origin. Shadow DOM isolates styles, not JavaScript authority. An authenticated same-origin relay available to chrome is equally available to authored page scripts and must not expose management operations. Cross-origin frame messages must validate the sending origin and frame and carry only the intended presentation interaction, such as resizing; they must not expose credentials or become an authenticated API bridge. Chrome system requests should run independently of the authored app's React Router loaders and user Worker and enter neither app-request nor tool-execution clips metering. Billing policy should remain owned by the existing metering paths.

Local development must preserve the same boundary. A saved CLI credential must remain in trusted local tooling and its auxiliary Worker and must not be exposed to authored browser or Worker code. Browser origins serving local apps must not gain credentialed web/platform API access through blanket localhost trust. HttpOnly, cookie domains, and CORS should support the boundary without replacing the separation of authority.

## Platform and web: ownership and dataflow

Web owns Better Auth users, sessions, organizations, and memberships. Platform owns apps and their authorization. Platform stores the owning user or organization ID, without copying web's identity or membership records. A browser session cookie is a signed opaque session identifier; platform does not extract identity from it or verify it with another session secret.

For trusted dashboard requests, platform forwards the user's native Cookie header to web's `/api/auth/get-session` endpoint and uses the verified user returned by Better Auth. CLI requests retain their scoped bearer access tokens. The request's verified identity and credential flow through the Hono boundary into shared domain functions and dashboard React Router loaders. Web's `/api/me` owns the current-user profile contract: `{ id, name, image }`, with nullable image and no response caching. It accepts authorized CLI bearer tokens and native web cookies. `ctx whoami` calls web directly using the origin of `CTX_AUTH_ISSUER`; platform does not expose or proxy that endpoint. A safe profile can be an explicitly delegated runtime result without granting its recipient access to web's authenticated APIs.

Required authentication has one Hono middleware implementation. API and Git routes respond with 401 when identity is absent. Dashboard routes enable the sign-in response: an unauthenticated GET that prefers HTML through Hono's native `accepts` helper redirects to web's `/auth/sign-in`, passing the requested dashboard URL as Better Auth UI's `redirectTo`. The existing UI supplies it as Better Auth's social `callbackURL`; web owns authentication and trusted-origin validation. Requests that do not prefer HTML retain 401. `Accept` selects the response behavior; request `Content-Type` describes the body. Platform reuses the web cookie after sign-in. Local dashboard access, logout, and the return-after-sign-in flow have browser acceptance. Production uses web’s native Better Auth cross-subdomain cookie on `usecontextlayer.com` and trusts the platform sign-in return origin. Production rollout verification is pending.

For management requests, when platform needs user-scoped web facts such as organization memberships, it forwards the same user's authorized native web cookie or CLI access token. Web authenticates the caller and returns authoritative facts through its authenticated endpoint; platform applies its own app rules to those facts. These requests do not use a machine-to-machine credential. Better Auth owns credential verification and session revocation; platform owns the resulting app-access decision.

## Platform storage and request flow

Platform reads deployed app manifests through its native APPS dispatch-namespace binding, selecting the user Worker by canonical AppID. The manifest reader receives the App and binding, not caller identity or credentials, and sends a fresh GET for /slate.json with no Cookie, Authorization, or runtime-capability props. Redirects are not followed. Existing platform authorization precedes the read, so private apps do not require forwarding a caller credential into authored code. The reader validates with shared/slate and returns one { manifest, source } snapshot, where source is local or deployed. Connections and Tools consume that same snapshot rather than fetching requirements inside their domain functions; source preserves the app-management requirement for local substitution. Agent-run preparation uses the same deployed reader. This internal read bypasses public dispatch and clips metering.

The dashboard uses shadcn/ui with the `base-nova` preset and standard Tailwind layout utilities.

Platform separates page routes from asset URLs: React Router's basename is `/dashboard/`, while Vite uses its default `/` asset base. Cloudflare's native selective `assets.run_worker_first` sends `/api/*`, `/git/*`, and `/dashboard/*` through the Worker, including dashboard data requests. Scripts, CSS, and fonts use native asset serving outside those routes; production bundles live under `/assets/`. This configuration belongs only to platform. User-app requests retain the existing dispatcher authorization flow.

App visibility is platform configuration stored in the non-null text column `app.visibility`, separate from ownership and the authored manifest. `appVisibilitySchema` validates `public` or `private` in code, and `DEFAULT_APP_VISIBILITY = "private"` supplies the creation default; migration 004 independently backfills existing rows to private. There is no PostgreSQL visibility check or persistent default. Database app rows are parsed into the app schema before returning app-bearing domain results. Visibility storage, platform hostname-resolution authorization, dispatcher enforcement, and viewing authorization for app connection listing, viewer assignment, and tool execution are implemented. `PATCH /api/apps/{target}` accepts `{visibility: "public" | "private"}` for an AppID or public hostname. Its shared `updateAppVisibility` function enforces owner/member management permission, writes only visibility, and returns the saved app. Public viewing grants no management permission. Each dashboard row composes the existing shadcn Dropdown Menu radio items and Button without modifying their component files. A React Router fetcher submits the selection to the shared route action, which validates the same visibility contract, resolves the canonical app through the existing viewing boundary, and calls updateAppVisibility directly. Native action revalidation reloads the saved value; the control is disabled while saving.

Hono middleware creates a request-scoped Postgres.js/Kysely connection from validated Worker bindings and passes through the native Artifacts binding. Route groups select identity verification: app resolution and tool execution accept viewer cookies as well as native web/CLI credentials; other APIs, Git, and dashboard use only native web/CLI credentials. The middleware stores the optional `AuthIdentity`; protected groups require it before running. API handlers and React Router loaders share these through their framework contexts; `waitUntil` closes the database after the handler finishes. The Cloudflare Vite plugin runs development in workerd and builds the Worker plus client assets. The platform's `app` table contains `id` (UUID primary key, generated by Postgres), `public_hostname` (text with a unique index), and nullable text `owner_user_id` and `owner_organization_id` columns. PostgreSQL's `app_exactly_one_owner` constraint requires exactly one owner. App identity is immutable; the public hostname is independent. Package-owned Kysely migrations and Kanel-generated models follow the retained `db-infra` patterns, using a separate logical database on the shared local Postgres instance.

`POST /api/apps` requires authorized CLI bearer or native web-cookie authentication and passes the verified identity, auth issuer, and validated creation input into `createApp()`. The shared domain function resolves an optional `organization_slug` against the caller's authoritative organization records before any writes; an absent membership returns 404. Omission selects the verified user. With the resulting typed user-or-organization `Owner`, it generates a friendly adjective/color/animal hostname, inserts a private app, and creates an Artifacts repository named by its UUID. Better Auth in web owns user identities and organization memberships; platform stores their IDs, with no cross-database foreign keys or copied memberships. The agreed viewing rule allows anybody for public apps, the owning user for private personal apps, or members of the owning organization for private organization apps; the platform resolution endpoint and app connection/tool route groups enforce this rule, with Git source access and management restricted to the same owner/member rule regardless of visibility. Membership uses that app's owning organization regardless of the session's selected workspace. `ctx init` requires the saved login before scaffolding, sends the optional organization slug and its access token to creation, and sets `/git/<app-id>` as the project's remote. `GET /api/apps` and the dashboard loader call the shared `listApps()` operation, which returns only apps manageable by the verified caller and their latest main-branch Artifacts commit. Commit hashes remain Cloudflare-owned data; the dashboard displays seven characters. Zod defines API contracts, with OpenAPI at `/api/openapi.json`.

`GET /api/apps/resolve?hostname=<public-hostname>&pathname=<incoming-path>` inherits optional identity verification and viewing authorization through Hono middleware. `resolveAppForViewing()` looks up the unique `app.public_hostname` and delegates to `authorizeAppViewing()` using the validated canonical app and already-retrieved membership facts. The viewing and management predicates are pure; the domain operation owns membership I/O. Public viewing allows anybody; private viewing requires the owning user or membership in the owning organization. Web owns the authoritative `{id, slug, name}` organization records used for membership checks and organization-slug resolution. Platform obtains those facts through trusted service calls; a viewer credential does not grant direct access to web's organization API. Successful resolution returns `{ "id": "<app-id>" }`; required sign-in returns 401, denied viewing returns 403, and an unassigned hostname returns 404. Platform owns the mapping and authorization decision; dispatcher consumes the result for every hosted-app path.

Public hostname assignment rejects subdomains in the hardcoded reserved list in `packages/platform/app/apps.schema.ts`. `local` is reserved because it selects the current checkout in the CLI. `auth` is reserved for the auth-forwarding worker at `auth.contextlayer.xyz`. Neither can be an app subdomain.

Git clients use the immutable `/git/<app-id>` endpoint. The Git route group inherits identity verification and required authentication. `getGitAccess` resolves the app and calls `authorizeAppManagement` before obtaining any repository-scoped Artifacts credentials. Only the owning user or members of the owning organization may clone, pull, or push, including public apps. The Git service determines read versus write credentials: upload-pack reads and receive-pack writes, including their GET discovery requests. Hono's proxy helper forwards protocol traffic; Artifacts credentials stay server-side. Pushes do not create app records.

## Owner-owned shared secrets

Shared secrets belong to the canonical user-or-organization `Owner`, independently of app ownership. `PUT` and `DELETE /api/secrets/{type}/{owner_id}/{name}` accept `user` or `org` at the HTTP boundary and return only `{ owner, name }`. `ownerParamsSchema` in `packages/platform/app/owner.schema.ts` validates Owner path parameters and converts the HTTP type into the canonical Owner type; secret-specific contracts live in `secrets.schema.ts`. `setSharedSecret` and `dropSharedSecret` call the shared `authorizeOwner` in `owner.server.ts` before Doppler I/O. A personal Owner must match the verified caller; an organization Owner requires membership supplied by web through the existing credential-forwarding flow. Connections reuse that same authorization. No app lookup or subscription is involved in managing an Owner's secrets.

Doppler owns storage; the [development guide](DEVELOPING.md#shared-secret-management-verification) owns local and production vault configuration. Platform generates `OWNER_<USER|ORGANIZATION>_<uppercase UTF-8 hex Owner ID>_<name>`; clients cannot select provider keys or configs. The vault project/config and its scoped read/write service token are platform configuration (`CTX_CUSTOMER_CREDENTIALS_DOPPLER_PROJECT`, `CTX_CUSTOMER_CREDENTIALS_DOPPLER_CONFIG`, and `CTX_CUSTOMER_CREDENTIALS_DOPPLER_TOKEN`), validated together in `env.ts` when an authorized secret operation runs. Other platform operations do not require it. The platform token covers the config, so platform authorization enforces Owner isolation. Provider responses are not returned or logged; failures expose only operation/status. App manifests declare Owner/name references. Internal `loadSharedSecret` retrieves the literal Doppler `value.raw` for trusted execution; it exposes no plaintext HTTP operation.

The CLI's `owner.ts` resolves the personal Owner through `/api/me` or an organization slug through web's authoritative organization endpoint, shared by secret and connection management. It keeps the canonical Owner until `ownerPath` serializes the API path. `secrets.ts` calls the platform secret API with that Owner and the existing login. Clack's native password prompt masks values; `--stdin` bypasses prompting and preserves the exact UTF-8 input. Cancellation ends before submission. CLI output contains only Owner/name, and the CLI never receives the vault token.

## Authored agents

An app can contain named agents at `agents/<name>/instructions.md`. The app's existing Git push publishes their standing instructions into its Artifacts repository. `GET /api/apps/{target}/agents/{name}` returns `{ commit, instructions }` from the latest commit on `main`, pinning the file read to that commit. `getAgent` in `packages/platform/app/agents.server.ts` applies the same owner/owning-organization-member source permission as Git, including for public apps, then calls the shared native Artifacts reader. The endpoint follows the existing authenticated app boundary and Zod/OpenAPI contract. Reading the definition is independent of the app's build or deployment; the repository remains its source.

Hosted-run preparation also lives in `agents.server.ts`. `getAgentRun` accepts an authenticated app-and-caller `AppAccess` already authorized for viewing, reads the published instructions through the same pinned source reader, and loads the deployed requirements through `getAppManifest`. It calls the pure `prepareAgentRun` operation to produce the `agentRunSchema` contract: app ID, acting-user ID, agent name/instructions/commit, separate task prompt, secret names mapped to canonical Owners through `getCredentialOwner`, and declared connection slugs mapped to selected Owner/account references through shared `resolveAppConnection`. Assignments are resolved while the verified caller is available, before background execution. Only these explicit fields enter the run; caller credentials and secret values are absent. This is internal preparation reused by hosted job start. Source inspection remains management-only. `startAgentRun` invokes a fresh native `AppAgent` Durable Object through the Agents SDK, using its name as the submission ID. The object persists the prepared run with native `configure` and accepts the task through `submitMessages`, returning before inference completes. Think owns the durable queue, execution lifecycle, and submission ledger. `getAgentJob` inspects the named object, verifies the stored app ID and agent name, and reads native submission status plus the persisted assistant message using `messageId`. The object returns a serializable `AgentJob`: `{ id, status, result, error? }`, with nullable assistant text and native Think status/error values. Think retains the full message; the API does not copy it into another store. `agent-runtime.ts` extends Cloudflare Think, using a real Linux sandbox attached to that same Durable Object through native `ctx.container`. A single `bash` tool runs commands in `/shared`; native `beforeTurn.activeTools` selects it alongside Composio MCP tools, and `workspaceBash = false` disables just-bash. The object creates account-scoped Composio sessions through shared `createConnectionSession` and registers each through native `addMcpServer` before submitting the task. Think owns connection readiness, restoration, and MCP-to-model tool conversion; the MCP authentication headers remain in the trusted Worker. The HTTP tools endpoint uses the same account/session selection with `session.execute`. Composio owns service credentials and external API calls in both cases. Wrangler’s `durable_object` container policy supplies the Debian image with Bash, Git, and CA certificates. On first turn, the platform starts the container and clones the one-off hardcoded Artifacts repository `agent-shared-2026-10-05-91fc24d8` into `/shared`. A one-hour repo-scoped write token is kept in Git’s standard credential store inside the sandbox; the Git remote itself contains no credential. The model owns ordinary Git stage/commit/push. Platform instructions explain that shared work becomes durable only after a successful push to `origin/main`; other filesystem paths are scratch. A later job starts a fresh sandbox and clones those saved documents. This is the agreed single-folder base case, without folder declarations or `app_user`. System context combines native runtime, platform, and published instructions; the task is a separate user message. `beforeTurn` loads the declared Owner’s `ANTHROPIC_API_KEY` through `loadSharedSecret` and supplies an Anthropic Haiku model directly, keeping credentials out of persisted run configuration, messages, and workspace files. The earlier just-bash implementation proved Haiku execution with published instructions and all eight native workspace tools in local workerd. Two real Haiku API jobs have also verified the Linux path: the first committed and pushed a shared document, and the second, in a different sandbox, read it, edited it, and pushed a follow-up. Native remote Git readback verified both saved documents and their commit ancestry. The provider requests an uncompressed response stream through its native `headers` option, and Think uses its native twenty-step budget. Native background submissions provide durable execution and result storage without a separate Workflow or job table. Real Haiku background completion and identical status/assistant-message retrieval after a native Worker reload have been verified locally. `POST /api/apps/{target}/agents/{name}/jobs` accepts `{ prompt }` and returns HTTP 202; `GET /api/apps/{target}/agents/{name}/jobs/{id}` returns HTTP 200 with status/result. Shared `startAgentJob` composes preparation and submission, while `getAgentJob` owns inspection. Both routes inherit existing native authentication and central `requireAppViewing`. Any viewer of a private app can start and inspect its jobs, regardless of the initiating user. One removable jobs-group condition temporarily returns 403 for public apps. Think's native lifecycle hooks are selected for agent billing; its policy and implementation remain outstanding.

Local execution belongs to the CLI's `packages/cli/agents.ts`. From the app root, `ctx agent local run <name> <prompt>` reads that checkout's `agents/<name>/instructions.md` and invokes Claude Agent SDK with the app root as its working directory. The native `claude_code` system preset supplies runtime instructions; its appended text contains platform instructions followed by the authored file. The task is a separate SDK `prompt`. Explicit `settingSources: []` disables automatic user/project settings and CLAUDE.md loading, while native managed policies still apply. The command prints the successful final result and surfaces SDK failures. It uses native Claude authentication and does not contact the platform. The SDK is loaded only for agent execution and remains an external runtime dependency so its matching Claude executable can resolve normally.

## Build pipeline

Artifacts push events in `contextlayer-dev` start the `contextlayer-build` Workflow. `packages/build/index.ts` subclasses the SDK’s `CIWorkflow` with a build runner (`pnpm install --frozen-lockfile && pnpm build`) followed by a chained deployment runner. The SDK checks out the event’s commit, captures logs and status, and retains the workspace snapshot in the `contextlayer-build-backups` R2 bucket. The official Sandbox image supplies the runtime; the package Dockerfile adds the workspace’s pnpm version.

The deployment runner restores the successful build workspace and invokes Wrangler to deploy the Worker and static assets into the `contextlayer-dev` dispatch namespace, using the Artifacts repository name (AppID) as the Worker name. Only this runner opts into the SDK’s `cloudflareCredentials` capability, backed by the `CF_TOKEN` Worker secret. Operators inspect both steps in Cloudflare’s Workflows dashboard. ContextLayer’s app dashboard does not expose build status yet. The build Worker uses Wrangler configuration and deployment as an approved exception to `cf`, whose new configuration does not yet support Artifacts event triggers.

## Viewer organization membership

Web owns sessions and organization membership; platform owns app visibility and access policy. Private organization viewing first validates the viewer session with Better Auth, then calls web’s `GET /api/viewer/organizations/:organizationId/membership` with the viewer cookie and the canonical app’s owning organization ID. Web validates the session, reuses its existing membership query, and returns only `{isMember}` with no response caching. Native web and CLI callers continue using `/api/platform/organizations`. Platform’s `resolveAppForViewing` selects the appropriate read and passes `isOwnerOrganizationMember` into the shared pure viewing/management rule. The app-resolution and runtime-tool routes share this flow. App listing still retrieves the organization list once and derives the membership fact per app. No memberships are copied into platform or the viewer cookie, and the existing session/logout lifecycle is unchanged.

## Hosted-app routing

`packages/dispatcher` owns the wildcard Worker route `*.contextlayer.xyz/*`. It asks platform to resolve the incoming hostname and authorize viewing for every request, including `/slate.json`. Runtime authority is bound to the app and viewer; the viewer credential does not grant general platform API access. On success, dispatcher invokes the Worker returned by `APPS.get(id, {props})`; on required sign-in it redirects to auth's `/start` with the original request URL as `return_to`; other failures pass through. Dispatcher must remove ContextLayer authentication credentials before invoking authored code. Request-scoped RPC props must expose only the explicitly delegated capabilities. Authored responses must not create, replace, or clear ContextLayer authentication cookies. `APPS` binds the WfP dispatch namespace. Platform owns identity-based app authorization, hostname mapping, visibility, and membership decisions; dispatcher has no database, mapping cache, or duplicate authorization policy.

The platform is deployed at `https://slate.usecontextlayer.com` with Neon Postgres configured through Doppler `platform/prod`. The dispatcher’s `CTX_PLATFORM_URL` points to that address; it no longer depends on a local server or tunnel. Existing local app records were intentionally not migrated. Wrangler builds and deploys the Workers.

## App tool calls and local development — agreed contract

### User-app Layout

The CLI template's `app/root.tsx` re-exports only Layout from `@usecontextlayer/sdk/react`. This React Router document Layout renders native metadata/links/scripts/scroll restoration, a full-width iframe before the authored children, and the authored root component or error boundary. The app retains its routes, stylesheet, and independent Tailwind/shadcn defaults. Platform serves the header and connection tray at `/dashboard/chrome/apps/:target` on `slate.usecontextlayer.com`; chrome assets and styling belong to platform's existing frontend build. The SDK has no chrome stylesheet, ShadowRoot, or system-data loader.

The thin, full-width header retains its wordmark, connected-services count, viewer identity, and inline JSON tray. The entire connected-services section toggles the tray. A ResizeObserver in the frame sends only its natural height to the parent; Layout validates the message shape, expected origin, and frame window before resizing so app content moves down. Platform validates the target and applies the existing viewing policy, reads the credential-free manifest through APPS, calls listAppConnections in-process, and reads the profile from web. These system reads bypass authored loaders, Workers, and clips metering. In development, native Vite defines expose only the AppID, platform URL, and validated manifest snapshot to Layout; the CLI access token stays in the auxiliary Worker. Browser chrome uses the browser login independently of the CLI login.

### Cross-site chrome authentication — principles

The header must run in a separate document on a trusted origin: `slate.usecontextlayer.com`, `frame.usecontextlayer.com`, or `usecontextlayer.com`. Private app entry should leave the header authenticated as the same viewer automatically, without an additional popup sign-in step. The frame's session flow must work across the site boundary to `contextlayer.xyz` while preserving isolation from the authored parent.

Better Auth should own identity verification and session revocation. Web logout must invalidate the frame's authentication. Any frame credential must remain in the trusted document and services; the authored parent must receive neither credentials nor profile/connection data. Cookie settings and embedding policy must preserve this boundary. CSP should restrict who can embed the frame; it must not be treated as a way to enable cross-site cookie delivery. The session flow must not depend on weakening web's normal cookie security.

### Viewer sign-in boundary — principles

Web's Better Auth should own the user's identity and web session, and auth should own viewer sign-in on the user-code domain. Viewer sign-in must identify the same user without copying a reusable web session credential into the authored-app domain. Viewer authority must be limited to viewing and explicitly delegated app runtime operations and must not authenticate web/platform management requests.

Platform should own public/private viewing authorization and apply the same visibility rule to `/slate.json`. Dispatcher should ask platform for that decision and supply only app/viewer-bound capabilities to authored code. Private viewing and manifest retrieval must preserve the security boundary above: authentication must stay in trusted services, and authored requests, responses, and redirects must not expose management credentials or control viewer-session changes.

### Local tools

This section is the source of truth for the tool-call contract and its ownership boundaries. Future authoring-agent skills should reference it. The reusable package and `ctx init` integration implement the local React Router/Composio path described here.

Apps declare connection requirements in `public/slate.json`, keyed by slug, and call `tools.call(slug, toolSlug, args)`. ContextLayer resolves the slug to a Composio Platform connected account using the manifest-selected `(app_id, owner_type, owner_id, slug)` in platform Postgres. The assignment stores the connected-account ID, never provider credentials. Composio owns provider credentials, refresh, and tool execution. Viewer and app Owner assignments use the same storage and resolution path.

```ts
await tools.call("work-email", "GMAIL_FETCH_EMAILS", { max_results: 5 });
```

`@usecontextlayer/sdk/vite` exports the `contextlayer` Vite integration. During development it calls CLI-owned `getLocalToolsBindings`: Node reads the AppID from Git origin, validates the checkout manifest, and obtains a current access token through the saved CLI login. The helper returns native binding `props` containing the AppID, typed access-token credential, and parsed manifest, plus `vars` containing only `CTX_PLATFORM_URL`. Vite configures the local Tools service binding with those props; it does not expose the credential to authored code or copy the refresh token into the Worker. Restart development when the token expires or the manifest changes.

The shared `tools-worker` subpath owns one `Tools extends WorkerEntrypoint` implementation and its HTTP response validation. Dispatcher re-exports it; SDK bundles and re-exports it through `@usecontextlayer/sdk/local`. The SDK owns the Tools interface/React Router context and local binding configuration. `@usecontextlayer/sdk/worker` exports `createApp`, which owns the React Router request handler and selects the local Tools binding or production `ctx.props.tools`. The app supplies its virtual server-build import and Vite mode/development values. Generated files contain thin wiring; ContextLayer runtime and Vite behavior live in packages. The Gmail page remains an example, not the default application. The former For You adapter and consumer-key configuration have been removed from source; the legacy @usecontextlayer/tools v0.11.3 package retains the old behavior. New apps use @usecontextlayer/sdk.

During local development, the Cloudflare Vite plugin runs the React Router app and a development-only auxiliary Tools Worker under `pnpm dev`. A native RPC service binding supplies the Tools handle, which the app entrypoint puts into React Router context. The Tools Worker calls the platform's authenticated execution endpoint with the connection slug, tool name, and arguments. The platform resolves the assigned connection and executes through Composio. The loader receives `{data, logId}`; a reported Composio error throws with its log ID.

The hosted entrypoint receives its Tools handle through dispatcher-supplied `ctx.props.tools`. The trusted Tools entrypoint binds the platform-resolved AppID and authenticated viewer to the request-scoped capability. Platform verifies the delegated authority and resolves the manifest-selected viewer or app Owner's assignment before execution. Cloudflare scopes the RPC handle to the current request; the app cannot read its underlying props or substitute another app or viewer. Local and hosted callers use the same Tools WorkerEntrypoint, configured with `{ appId, credential, manifest? }` in native `ctx.props`, and share the platform execution domain function; accepting a runtime capability does not make the viewer cookie a management API credential. The composition difference stays at the entrypoint, and the local auxiliary Worker and its token binding are excluded from production builds.

## Key contract: app credential requirements

The author owns `<APP_DIR>/public/slate.json`, served at `/slate.json` by the framework's native static-asset handling. This is the single source of the app's connection and secret requirements. Vite serves the local file during development and includes it in the production assets, so each deployment carries its own requirements. Do not add a custom resource route, a copied root manifest, or a separate requirements store.

The manifest contains a `connections` object keyed by the slug used in `tools.call(slug, toolSlug, args)`. Each connection declares its Composio `toolkit` and `mode` (`viewer` or `owner`). A `secrets` object uses secret names as keys and declares the same modes. `viewer` selects the acting user’s user Owner; `owner` selects the app’s owning user or organization. New apps start with empty `connections` and `secrets` objects. `@usecontextlayer/shared/slate` owns the Zod manifest contract and mode vocabulary; CLI, SDK, and platform use it. For example:

```json
{
  "connections": {
    "work-email": {
      "toolkit": "gmail",
      "mode": "viewer"
    }
  }
}
```

Local tooling reads the checkout's `public/slate.json`; callers inspecting a running app fetch `/slate.json` from that app's origin under the app's viewing authorization. Deployed requirements come from the deployed app, not the latest Git commit. Consumers validate the manifest with the shared Zod contract. Connection requirements select assignments stored by `(app_id, owner_type, owner_id, slug)` in platform Postgres. Secret declarations directly reference `(Owner, name)` in the existing Doppler vault and need no assignment record. Missing `secrets` means no secret requirements; the old individual/shared mode values are rejected. Trusted hosted execution consumes those references as described under authored agents; external service-account and Artifacts folder access are later stories.

## Chrome profile reads

The trusted platform iframe reads the web-owned safe profile `{ id, name, image }` with its native session identity. Profile data stays inside the frame. The SDK and dispatcher expose no Viewer capability or profile context to authored code.

## CLI authentication

The CLI login implementation uses OAuth device authorization through web's existing Better Auth OAuth provider. The user approves a code at web's `/device` page; `openid-client` handles device requests, polling, and refresh. Tokens target `urn:ctx:platform` with `ctx:access`. The CLI stores tokens in `~/.contextlayer/auth.json` and `ctx whoami` calls web's `/api/me` directly, where web's existing authentication boundary verifies the access token's signature, issuer, audience, expiry, subject, and scope using Better Auth's native resource client. App creation and personal connection operations require authentication. Hostname resolution and app connection/tool operations enforce app viewing authorization; Git source access and dashboard listing also require authentication and the owner/member management rule. The device extension requires web schema migration and a registered public OAuth client before use. Local and production end-to-end verification passed: the user approved the device code, the CLI saved its tokens, and `ctx whoami` authenticated successfully against `/api/me`. Production uses issuer `https://www.usecontextlayer.com/api/auth` and platform `https://slate.usecontextlayer.com`. CLI authentication is included in npm releases starting with 0.12.0.

After successful login, the CLI registers its Git credential helper in the OS user's global Git configuration, scoped to `<CTX_PLATFORM_URL>/git`. Configuration stores the actual Node and CLI executable paths, not tokens. Git owns URL matching and HTTP authentication; `ctx git-credential` supplies native Bearer credentials by calling the existing `getAccessToken()` implementation, including refresh. The existing auth file remains the only credential store. Registration belongs to login so clone works before a checkout exists; init only sets the repository's immutable remote.

App listing and Git source access use the same `authorizeAppManagement` operation as private viewing. Public visibility only bypasses that rule for viewing. The API app catalog and dashboard inherit required authentication; the API handler and React Router loader call the same `listApps` operation with the verified identity and configured auth issuer. It retrieves organization memberships once per listing, then filters apps through the shared pure management rule before reading Artifacts commits. Dashboard loaders receive identity and configuration through native React Router context. Browser sign-in wiring and the visibility dropdown remain a later slice.

## Composio Platform connections

Owner-level connection management uses authenticated `GET` and `POST /api/connections/{type}/{owner_id}`, with `user` or `org` in the HTTP path. The CLI uses the same `resolveOwner` and `ownerPath` as secrets; command help owns personal/organization selection. The shared `listConnections` and `authorizeConnection` operations receive the canonical Owner and verified caller, enforce `authorizeOwner` before provider work, and use that Owner's ID for native Composio account listing or session creation. Listing follows Composio pagination and returns only ID, toolkit, alias, display name, and status, validated with Zod. Authorization calls `session.authorize(toolkit)` and returns the hosted link; the member completing OAuth manages the account for the selected Owner. Composio owns credentials, refresh, and the private account's OAuth lifecycle. There is no separate Composio user mapping: account setup, listing, and manifest-selected execution use the same Owner ID. Organization members can manage the organization's accounts through the existing membership rule. The previous user-only `/api/connections` endpoint is replaced. The project key is a platform Worker secret supplied by Doppler `platform/prod`, never a CLI credential. This supports Composio Platform only; existing For You connections are not imported. App assignment and Platform tool execution are implemented below.

## App-scoped connection listing

`ctx connections <target> list` accepts an AppID, public hostname, or `local`. One authenticated OpenAPI operation, `POST /api/apps/{target}/connections/list`, inherits app viewing authorization and delegates requirement resolution to `listAppConnections` with the canonical authorized app. With an empty JSON body it fetches the registered app’s deployed `/slate.json`. With a `manifest` body it validates and uses those requirements for this request only. Local CLI mode must run from the app root. It reads `public/slate.json` relative to the current directory, extracts the AppID from origin’s `/git/<app-id>` URL, and submits both using the saved user login. It does not search parent directories or add an AppID to the manifest. The Git remote supplies an identifier; inherited app viewing middleware authorizes its canonical app before listing, assignment writes, or tool execution. It requires no local dev server and does not persist the supplied manifest. AppID and hostname targets use the deployed manifest. The response contains the app and each requirement’s slug, toolkit, mode, and connection_id; assignments are read from `app_connection_assignment` for the viewer and app Owner, then joined according to each requirement’s mode; unassigned requirements return null. Owner-level account listing and authorization remain separate from app requirement listing.

The CLI owns local file/Git I/O and HTTP presentation. The API boundary validates the target into either `{ id }` or `{ public_hostname }` and validates any supplied manifest with Zod. Inherited middleware passes the normalized target into `resolveAppForViewing`, which performs one app lookup and calls the shared viewing rule. App operations inherit required authentication and viewing authorization; the tool-execution group additionally permits the viewer cookie while the other app operations require native web or CLI credentials. The handler passes the resulting `AppAccess`—the canonical app paired with its verified `AuthIdentity`—into the domain operation, which owns the deployed-manifest fetch and returns structured requirements. Private manifest retrieval requires viewing authorization without forwarding the caller's management credential into authored content. Local requirements are request-scoped input, never a replacement for deployed requirements.

## Owner-scoped connection assignment storage

`app_connection_assignment` stores choices using `(app_id, owner_type, owner_id, slug)` as its composite primary key. `app_id` is a UUID foreign key to `app.id` with `ON DELETE CASCADE`; the other columns and `connection_id` are non-null text. `owner_type` is `user` or `organization`, matching the canonical `Owner`. `slug` is the manifest connection key and `connection_id` is Composio’s connected-account ID. Toolkit and mode remain in the manifest. Migration 006 renames the former `user_id` column to `owner_id`, preserves existing assignments as user Owners, and changes the primary key; Kanel generates the resulting types. Apply it before deploying this code. Downgrading refuses organization assignments because the previous schema cannot represent them.

The existing assignment operation loads the declared requirement, resolves its mode through `getCredentialOwner`, and uses native Postgres upsert. Viewer assignment requires app viewing permission; owner assignment requires the existing app-management rule (owning user or owning-organization membership). Local CLI assignment reads the checkout manifest and passes it with the AppID from Git origin. Substituting a local manifest for assignment or execution requires app management, so ordinary viewers cannot author a declaration that selects the app Owner’s account. Provider-account ownership and toolkit-compatibility validation retain their existing scope; requirement existence is now necessary to choose its Owner.

Migration 002 is applied to production Neon. The deployed assignment/listing API was verified by assigning the demo app’s work-email requirement and reading the same stored connection through local, AppID, and public-hostname targets. CLI changes are available in the local build; no npm release has been cut.

### Platform tool execution

`POST /api/apps/{target}/tools/call` accepts `{slug, tool, arguments}` with an optional local `manifest`. It inherits authentication, app viewing, and subscription access. The platform loads the requirement through the same manifest operation used by connection listing and assignment. `resolveAppConnection` selects its canonical Owner and looks up that Owner’s assignment; `callTool` calls shared `createConnectionSession` with the selected Owner and assigned account. That operation selects the account's toolkit and creates the native Composio session used by both HTTP execution and hosted-agent MCP. It preserves Composio’s `{data, error, logId}` response. Missing requirements or assignments return 404, and forbidden configuration or manifest substitution returns 403. Ordinary hosted viewers can execute an authored owner-mode requirement through the app viewing boundary without acquiring permission to configure that Owner’s connections or manage its vault. Viewer-mode execution remains scoped to that viewer’s accounts. The Composio project key remains on the platform. Hosted runtime authority is explicitly delegated to the canonical app and viewer; a viewer credential grants no general API access.

Local loader integration uses the development-only Vite startup helper and Tools Worker described above. Its access token is a startup snapshot; no continuously refreshing local authentication service is involved.

### Dashboard account controls

The dashboard account menu uses Better Auth’s browser client and Better Auth UI’s session/multi-session hooks against web’s configured auth issuer. Web owns session listing, switching, and sign-out; these native auth operations do not acquire parallel platform endpoints. A component-owned QueryClient keeps server renders isolated. Better Auth UI refreshes session queries after switching. After Better Auth confirms an account switch, React Router navigates to Personal with history replacement and loads the new user’s authorized app list. Add account returns through web’s existing sign-in page. UI primitives use shadcn base-nova and Font Awesome Slab.

The dashboard uses `/dashboard/personal/apps` and `/dashboard/org/<organization-slug>/apps`; `/dashboard` redirects to Personal. The switcher presents Personal and organization names as plain text with consistent row spacing, without avatars or settings actions. Its choices come directly from web through Better Auth UI’s organization-list hook. The server resolves an organization slug against web’s authenticated `/api/platform/organizations` response using the caller’s existing credential, then uses the stable organization ID to query apps. The shared `ownerSchema` and derived `Owner` in `shared/lib/app-usage.ts` are the canonical user-or-organization ownership shape, re-exported by platform’s `app/owner.ts` used by app creation and listing. The authenticated creation operation accepts an optional `organization_slug`; its domain function resolves membership through web before choosing that organization’s stable ID or the verified user’s ID and writing the app. The dashboard’s `OwnerDetails` derives from it and includes schema-derived organization name/slug metadata; Personal is the verified user’s owner variant, never a null organization. No active-organization session mutation occurs, so tabs may select different workspaces. The app-list API accepts optional `owner_user_id` or `owner_organization_id` query parameters for non-browser consumers; omitting both lists all manageable apps. Zod rejects supplying both, and the handler converts the validated query to `Owner` or the listing’s all variant. Both the API and loader call the same `listApps` function with a typed filter and independent management authorization.

## App-owner billing access

Web’s native Better Auth/Polar integration owns individual and team customer creation, checkout and billing management. Platform receives `customer.state_changed` directly at `POST /api/polar/webhooks`; Polar’s SDK verifies the signature using the required `POLAR_WEBHOOK_SECRET`. `saveCustomerState` upserts the complete native state and event timestamp in `polar_customer_state`, keyed by Polar customer UUID with a unique nullable `external_id`. That external ID matches `app.owner_user_id` or `app.owner_organization_id`. Polar’s merchant `organization_id` is unrelated to our organization ownership. Kanel generates the JSON column with the native SDK Customer State type.

The existing viewing policy still owns public/private and membership authorization. After it succeeds, one `requireAppSubscription` middleware calls `checkAppSubscription` on runtime hostname resolution and actual tool execution. It reads the owner’s saved state and allows a nonempty `active_subscriptions` array; missing or empty state yields 402. Free counts. Dispatcher forwards the actual incoming pathname so exactly `/slate.json` can retain ordinary authorization without requiring billing. It forwards 402 through its existing failure path. Hosted and local Tools both call the gated platform endpoint; local page rendering itself does not go through hosted dispatch. App creation/listing, dashboard, Git and connection configuration do not require a subscription. Initialize existing owners from Polar’s native Customer State API before enforcement; no request-time API fallback or membership mirror is introduced. Usage metering follows execution: dispatcher records recognised dynamic GETs (1 clip) and POST/PUT/PATCH/DELETE requests (3 clips), while the platform tool API records returned executions (1 clip). The shared `app-usage` module converts the canonical `{ id, owner }` and event name into native Polar ingestion, with `metadata.clips` and `metadata.user_code_worker_id`. Resolution supplies its owner through the shared Zod contract; platform converts its loaded app through `getAppOwner`. Both boundaries use native `waitUntil` and return without awaiting Polar. Best-effort classification for these methods recognises HTML, JSON (including application `+json`), React Router `text/x-script`, plain text, CSV, XML, NDJSON, event streams and redirects. JavaScript, CSS, image, font and WebAssembly responses and exact `/slate.json` produce no usage events. Response headers are app-controlled, so this is the user-approved normal-traffic heuristic, not an unbypassable distinction between static and dynamic responses. No SDK-side reporting or route instrumentation is required; rates and canonical owner attribution stay in trusted Workers. Polar’s existing Clips meter aggregates all three event types and owns allowances and prices.

The trusted platform frame calls `listAppConnections` directly with the authorized app, verified browser identity, and validated manifest.
