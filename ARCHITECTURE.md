# Architecture

The repository contains nine packages; `@usecontextlayer/cli` and `@usecontextlayer/sdk` are public and the others are private:

- `cli` — Published as `@usecontextlayer/cli`; Commander-based `ctx` executable, bundled with tsdown; its version comes from its package manifest, and `init` delegates project creation to the official `create-cloudflare@latest` React Router scaffold.
- `sdk` — Public `@usecontextlayer/sdk` integration: shared React Router document Layout, Tools/Viewer interfaces and React Router contexts, app request handling, local auxiliary Worker, and Vite integration. Subpath exports keep React UI, Vite/Node imports, and Worker runtime imports separate.
- `db-infra` — Postgres/Kysely connections, migrations, and ephemeral database helpers.
- `shared` — Authentication, token handling, test helpers, and Sentry event capping.
- `twilio` — Twilio Functions for founder call routing and answer screening.
- `platform` — Cloudflare Workers application: an Artifacts Git proxy under `/git`, OpenAPI endpoints under `/api`, and the React Router dashboard under `/dashboard`.

- `build` — Cloudflare Worker using `@cloudflare/ci` and Workflows to build commits pushed to Artifacts in isolated Sandbox runners.

- `dispatcher` — Cloudflare Worker that resolves public hostnames through the platform API and invokes the WfP Worker named by AppID.

- `auth` — Worker that exchanges a Better Auth one-time token and reuses the web session on the user-code domain.

## Multiple consumers

Almost every user-facing platform capability is exposed through OpenAPI so the web dashboard, CLI, and a future MCP consumer share the same product operations. Zod owns their input and output contracts. A shared domain function owns each operation’s business logic, authorization, and database calls; API handlers adapt it to HTTP and React Router loaders/actions invoke it directly in-process. UI components own presentation and interaction. This is a standing design rule, not a claim that every future CLI command or MCP surface exists today. Better Auth owns its native authentication protocols; product APIs consume the resulting verified identity.

## Platform and web: ownership and dataflow

Web owns Better Auth users, sessions, organizations, and memberships. Platform owns apps and their authorization. Platform stores the owning user or organization ID, without copying web's identity or membership records. A browser session cookie is a signed opaque session identifier; platform does not extract identity from it or verify it with another session secret.

For browser requests, platform forwards the user's native Cookie header to web's `/api/auth/get-session` endpoint and uses the verified user returned by Better Auth. CLI requests retain their scoped bearer access tokens. The request's verified identity and credential flow through the existing Hono boundary into shared domain functions and React Router loaders. Web's `/api/me` owns the current-user profile contract: `{ id, name, image }`, with nullable image and no response caching. It accepts existing CLI bearer tokens, viewer cookies, and native web cookies through web's existing authentication boundary. `ctx whoami` calls web directly using the origin of `CTX_AUTH_ISSUER`; platform does not expose or proxy that endpoint. The request-scoped Viewer capability calls this web-owned read directly, keeping credentials outside authored code. Its contract returns { id, name, image } or null for anonymous viewers. Capability wiring and the installed local loader are verified; the header renders the safe profile through the SDK root loader. Hosted WfP verification remains pending.

Required authentication has one Hono middleware implementation. API and Git routes respond with 401 when identity is absent. Dashboard routes enable the sign-in response: an unauthenticated GET that prefers HTML through Hono's native `accepts` helper redirects to web's `/auth/sign-in`, passing the requested dashboard URL as Better Auth UI's `redirectTo`. The existing UI supplies it as Better Auth's social `callbackURL`; web owns authentication and trusted-origin validation. Requests that do not prefer HTML retain 401. `Accept` selects the response behavior; request `Content-Type` describes the body. Platform reuses the web cookie after sign-in. Local dashboard access, logout, and the return-after-sign-in flow have browser acceptance. Production uses web’s native Better Auth cross-subdomain cookie on `usecontextlayer.com` and trusts the platform sign-in return origin. Production rollout verification is pending.

When platform needs user-scoped web facts, such as organization memberships, it forwards the same user's credential: the browser cookie or CLI access token. Web authenticates the caller and returns authoritative facts through its authenticated endpoint; platform applies its own app rules to those facts. These requests do not use a machine-to-machine credential. Better Auth owns credential verification and session revocation; platform owns the resulting app-access decision.

## Platform storage and request flow

The dashboard uses shadcn/ui with the `base-nova` preset and standard Tailwind layout utilities.

Platform separates page routes from asset URLs: React Router's basename is `/dashboard/`, while Vite uses its default `/` asset base. Cloudflare's native selective `assets.run_worker_first` sends `/api/*`, `/git/*`, and `/dashboard/*` through the Worker, including dashboard data requests. Scripts, CSS, and fonts use native asset serving outside those routes; production bundles live under `/assets/`. This configuration belongs only to platform. User-app requests retain the existing dispatcher authorization flow.

App visibility is platform configuration stored in the non-null text column `app.visibility`, separate from ownership and the authored manifest. `appVisibilitySchema` validates `public` or `private` in code, and `DEFAULT_APP_VISIBILITY = "private"` supplies the creation default; migration 004 independently backfills existing rows to private. There is no PostgreSQL visibility check or persistent default. Database app rows are parsed into the app schema before returning app-bearing domain results. Visibility storage, platform hostname-resolution authorization, dispatcher enforcement, and viewing authorization for app connection listing, viewer assignment, and tool execution are implemented. `PATCH /api/apps/{target}` accepts `{visibility: "public" | "private"}` for an AppID or public hostname. Its shared `updateAppVisibility` function enforces owner/member management permission, writes only visibility, and returns the saved app. Public viewing grants no management permission. Each dashboard row composes the existing shadcn Dropdown Menu radio items and Button without modifying their component files. A React Router fetcher submits the selection to the shared route action, which validates the same visibility contract, resolves the canonical app through the existing viewing boundary, and calls updateAppVisibility directly. Native action revalidation reloads the saved value; the control is disabled while saving.

Hono middleware creates a request-scoped Postgres.js/Kysely connection from validated Worker bindings and passes through the native Artifacts binding. Server-wide identity middleware verifies the caller once and stores only the optional `AuthIdentity`; protected route groups require it before running. API handlers and React Router loaders share these through their framework contexts; `waitUntil` closes the database after the handler finishes. The Cloudflare Vite plugin runs development in workerd and builds the Worker plus client assets. The platform's `app` table contains `id` (UUID primary key, generated by Postgres), `public_hostname` (text with a unique index), and nullable text `owner_user_id` and `owner_organization_id` columns. PostgreSQL's `app_exactly_one_owner` constraint requires exactly one owner. App identity is immutable; the public hostname is independent. Package-owned Kysely migrations and Kanel-generated models follow the retained `db-infra` patterns, using a separate logical database on the shared local Postgres instance.

`POST /api/apps` requires the existing CLI bearer, viewer-cookie, or native web-cookie authentication and passes the verified identity, auth issuer, and validated creation input into `createApp()`. The shared domain function resolves an optional `organization_slug` against the caller's authoritative organization records before any writes; an absent membership returns 404. Omission selects the verified user. With the resulting typed user-or-organization `Owner`, it generates a friendly adjective/color/animal hostname, inserts a private app, and creates an Artifacts repository named by its UUID. Better Auth in web owns user identities and organization memberships; platform stores their IDs, with no cross-database foreign keys or copied memberships. The agreed viewing rule allows anybody for public apps, the owning user for private personal apps, or members of the owning organization for private organization apps; the platform resolution endpoint and app connection/tool route groups enforce this rule, with Git source access and management restricted to the same owner/member rule regardless of visibility. Membership uses that app's owning organization regardless of the session's selected workspace. `ctx init` requires the saved login before scaffolding, sends the optional organization slug and its access token to creation, and sets `/git/<app-id>` as the project's remote. `GET /api/apps` and the dashboard loader call the shared `listApps()` operation, which returns only apps manageable by the verified caller and their latest main-branch Artifacts commit. Commit hashes remain Cloudflare-owned data; the dashboard displays seven characters. Zod defines API contracts, with OpenAPI at `/api/openapi.json`.

`GET /api/apps/resolve?hostname=<public-hostname>&pathname=<incoming-path>` inherits optional identity verification and viewing authorization through Hono middleware. `resolveAppForViewing()` looks up the unique `app.public_hostname` and delegates to `authorizeAppViewing()` using the validated canonical app and already-retrieved membership facts. The viewing and management predicates are pure; the domain operation owns membership I/O. Public viewing allows anybody; private viewing requires the owning user or membership in the owning organization. Platform reads `{id, slug, name}` organization records from web’s authenticated `/api/platform/organizations` endpoint, forwarding the existing credential. The same validated records supply membership checks and organization-slug resolution. Successful resolution returns `{ "id": "<app-id>" }`; required sign-in returns 401, denied viewing returns 403, and an unassigned hostname returns 404. Platform owns the mapping and authorization decision; dispatcher consumes the result for every hosted-app path.

Public hostname assignment rejects subdomains in the hardcoded reserved list in `packages/platform/app/apps.schema.ts`. `local` is reserved because it selects the current checkout in the CLI. `auth` is reserved for the auth-forwarding worker at `auth.contextlayer.xyz`. Neither can be an app subdomain.

Git clients use the immutable `/git/<app-id>` endpoint. The Git route group inherits identity verification and required authentication. `getGitAccess` resolves the app and calls `authorizeAppManagement` before obtaining any repository-scoped Artifacts credentials. Only the owning user or members of the owning organization may clone, pull, or push, including public apps. The Git service determines read versus write credentials: upload-pack reads and receive-pack writes, including their GET discovery requests. Hono's proxy helper forwards protocol traffic; Artifacts credentials stay server-side. Pushes do not create app records.

## Owner-owned shared secrets

Shared secrets belong to the canonical user-or-organization `Owner`, independently of app ownership. `PUT` and `DELETE /api/secrets/{type}/{owner_id}/{name}` accept `user` or `org` at the HTTP boundary and return only `{ owner, name }`. `ownerParamsSchema` in `packages/platform/app/owner.schema.ts` validates Owner path parameters and converts the HTTP type into the canonical Owner type; secret-specific contracts live in `secrets.schema.ts`. `setSharedSecret` and `dropSharedSecret` call the shared `authorizeOwner` in `owner.server.ts` before Doppler I/O. A personal Owner must match the verified caller; an organization Owner requires membership supplied by web through the existing credential-forwarding flow. Connections reuse that same authorization. No app lookup or subscription is involved in managing an Owner's secrets.

Doppler owns storage; the [development guide](DEVELOPING.md#shared-secret-management-verification) owns local and production vault configuration. Platform generates `OWNER_<USER|ORGANIZATION>_<uppercase UTF-8 hex Owner ID>_<name>`; clients cannot select provider keys or configs. The vault project/config and its scoped read/write service token are platform configuration (`CTX_CUSTOMER_CREDENTIALS_DOPPLER_PROJECT`, `CTX_CUSTOMER_CREDENTIALS_DOPPLER_CONFIG`, and `CTX_CUSTOMER_CREDENTIALS_DOPPLER_TOKEN`), validated together in `env.ts` when an authorized secret operation runs. Other platform operations do not require it. The platform token covers the config, so platform authorization enforces Owner isolation. Provider responses are not returned or logged; failures expose only operation/status. App manifests declare Owner/name references; internal runtime loading remains unimplemented.

The CLI's `owner.ts` resolves the personal Owner through `/api/me` or an organization slug through web's authoritative organization endpoint, shared by secret and connection management. It keeps the canonical Owner until `ownerPath` serializes the API path. `secrets.ts` calls the platform secret API with that Owner and the existing login. Clack's native password prompt masks values; `--stdin` bypasses prompting and preserves the exact UTF-8 input. Cancellation ends before submission. CLI output contains only Owner/name, and the CLI never receives the vault token.

## Authored agents

An app can contain named agents at `agents/<name>/instructions.md`. The app's existing Git push publishes their standing instructions into its Artifacts repository. `GET /api/apps/{target}/agents/{name}` returns `{ commit, instructions }` from the latest commit on `main`, pinning the file read to that commit. `getAgent` in `packages/platform/app/agents.server.ts` applies the same owner/owning-organization-member source permission as Git, including for public apps, then calls the shared native Artifacts reader. The endpoint follows the existing authenticated app boundary and Zod/OpenAPI contract. Reading the definition is independent of the app's build or deployment; the repository remains its source.

Hosted-run preparation also lives in `agents.server.ts`. `getAgentRun` accepts an authenticated app-and-caller `AppAccess` already authorized for viewing, reads the published instructions through the same pinned source reader, and loads the deployed requirements through `getAppManifest`. It calls the pure `prepareAgentRun` operation to produce the `agentRunSchema` contract: app ID, acting-user ID, agent name/instructions/commit, separate task prompt, and secret names mapped to canonical Owners through `getCredentialOwner`. Only these explicit fields enter the run; caller credentials and secret values are absent. This is internal preparation for hosted execution, with no new HTTP route. Source inspection remains management-only. Secret loading, sandbox execution, and Workflow orchestration are not yet implemented.

Local execution belongs to the CLI's `packages/cli/agents.ts`. From the app root, `ctx agent local run <name> <prompt>` reads that checkout's `agents/<name>/instructions.md` and invokes Claude Agent SDK with the app root as its working directory. The native `claude_code` system preset supplies runtime instructions; its appended text contains platform instructions followed by the authored file. The task is a separate SDK `prompt`. Explicit `settingSources: []` disables automatic user/project settings and CLAUDE.md loading, while native managed policies still apply. The command prints the successful final result and surfaces SDK failures. It uses native Claude authentication and does not contact the platform. The SDK is loaded only for agent execution and remains an external runtime dependency so its matching Claude executable can resolve normally.

## Build pipeline

Artifacts push events in `contextlayer-dev` start the `contextlayer-build` Workflow. `packages/build/index.ts` subclasses the SDK’s `CIWorkflow` with a build runner (`pnpm install --frozen-lockfile && pnpm build`) followed by a chained deployment runner. The SDK checks out the event’s commit, captures logs and status, and retains the workspace snapshot in the `contextlayer-build-backups` R2 bucket. The official Sandbox image supplies the runtime; the package Dockerfile adds the workspace’s pnpm version.

The deployment runner restores the successful build workspace and invokes Wrangler to deploy the Worker and static assets into the `contextlayer-dev` dispatch namespace, using the Artifacts repository name (AppID) as the Worker name. Only this runner opts into the SDK’s `cloudflareCredentials` capability, backed by the `CF_TOKEN` Worker secret. Operators inspect both steps in Cloudflare’s Workflows dashboard. ContextLayer’s app dashboard does not expose build status yet. The build Worker uses Wrangler configuration and deployment as an approved exception to `cf`, whose new configuration does not yet support Artifacts event triggers.

## Hosted-app routing

`packages/dispatcher` owns the wildcard Worker route `*.contextlayer.xyz/*`. It forwards the incoming hostname, Authorization header, and viewer cookie to the platform's `/api/apps/resolve` endpoint for every request, including `/slate.json`. On 200 it validates the returned UUID and invokes the Worker returned by `APPS.get(id, {props})`; on 401 it redirects to auth's `/start` with the original request URL as `return_to`; other failures pass through. Authorization and the viewer cookie are removed before authored code receives the request. Requests carrying a viewer cookie receive `props.tools`, a native RPC capability configured with the resolved AppID and viewer session token; other requests receive empty props. `APPS` binds the `contextlayer-dev` WfP dispatch namespace. The platform owns identity, mapping, visibility, and membership decisions; dispatcher has no database, mapping cache, or session-verification logic. The shared Better Auth sign-in flow was previously verified in production; this authorization change awaits broader verification and deployment.

The platform is deployed at `https://slate.usecontextlayer.com` with Neon Postgres configured through Doppler `platform/prod`. The dispatcher’s `CTX_PLATFORM_URL` points to that address; it no longer depends on a local server or tunnel. Existing local app records were intentionally not migrated. Wrangler builds and deploys the Workers.

## App tool calls and local development — agreed contract

### User-app Layout

The CLI template's `app/root.tsx` re-exports `Layout` from `@usecontextlayer/sdk/react`. This package-owned React Router root Layout renders the HTML document, native metadata/links/scripts/scroll restoration, ContextLayer chrome, and the authored root component or error boundary as its children. The app retains its routes, root component, error boundary, stylesheet, and font links. The thin, full-width header expands an inline settings panel, moving the app content down. One shadcn Base UI Collapsible owns the header trigger, open state, accessibility, and panel lifecycle. Header and panel render into one native ShadowRoot through a React portal after hydration, preserving the surrounding React context. Vite's native `?inline` import processes the SDK stylesheet without injecting it into the authored page; the panel remains inside that ShadowRoot in normal document flow. The app has independent Tailwind and shadcn base-nova defaults. The lowercase wordmark uses the existing Fugaz One font through the native browser Font Loading API. Browser connection selection is not implemented yet.

Chrome is compiled into both server and browser bundles through normal framework imports. No dispatcher HTML injection or build-time enforcement is used. Authors can remove the Layout, losing the account-selection UI when that capability is implemented; saved assignments remain platform data. The selected next dataflow extends the existing request-scoped Cloudflare RPC pattern for connection operations, with credentials kept outside authored code; that extension is not part of the initial Layout slice.

### Viewer sign-in boundary

`packages/auth` owns `auth.contextlayer.xyz/start` and `/callback`, using Hono for HTTP and cookies. `/start` keeps random state and the validated app return URL in a ten-minute host-only HttpOnly `__Host-ctx_handoff` cookie, then redirects to web's `/viewer/sign-in`. Web uses the existing Better Auth sign-in page if necessary and generates a native one-time token tied to the current session. It redirects only to the configured auth callback. Auth verifies the browser's state and exchanges the token server-side through `/api/auth/one-time-token/verify`. It stores the returned session token in `__Secure-ctx_viewer`, with `Domain=contextlayer.xyz`, HttpOnly, Secure, SameSite=Lax, and the session's expiry. These are two domain-specific cookies referring to one Better Auth session, not two independently managed sessions.

Dispatcher forwards the existing viewer credential to platform for hostname resolution; platform verifies it through web's `/api/auth/get-session` using the existing bearer plugin. Web owns session validation and renewal; no session cache, database, JWT signing secret, or viewer OAuth client is needed in auth or dispatcher. Logging out on web invalidates this same session, so the next private app request requires sign-in. Public apps allow anonymous viewing. `/slate.json` follows the same app visibility rule, and platform forwards the requesting user's existing credential when reading a deployed manifest. Credentials are stripped before authored code receives the request. Shared connection credentials remain unimplemented.

Platform’s protected APIs also accept `__Secure-ctx_viewer`. The API boundary extracts either the CLI bearer token or the viewer cookie; `auth.server.ts` verifies CLI JWTs through web’s JWKS and viewer sessions through web’s `/api/auth/get-session` using its bearer plugin. An explicit bearer token takes precedence. Both return the same `{id}` identity to the existing domain operations. Invalid or absent credentials return 401; session lookup failures remain errors. There is no new session store, credential exchange, or authentication cache. The cookie belongs to `contextlayer.xyz`, so the browser does not automatically send it to `slate.usecontextlayer.com`; the dispatcher’s Tools entrypoint forwards it server-side.

### Local tools

This section is the source of truth for the tool-call contract and its ownership boundaries. Future authoring-agent skills should reference it. The reusable package and `ctx init` integration implement the local React Router/Composio path described here.

Apps declare connection requirements in `public/slate.json`, keyed by slug, and call `tools.call(slug, toolSlug, args)`. ContextLayer resolves the slug to a Composio Platform connected account using the manifest-selected `(app_id, owner_type, owner_id, slug)` in platform Postgres. The assignment stores the connected-account ID, never provider credentials. Composio owns provider credentials, refresh, and tool execution. Viewer and app Owner assignments use the same storage and resolution path.

```ts
await tools.call("work-email", "GMAIL_FETCH_EMAILS", { max_results: 5 });
```

`@usecontextlayer/sdk/vite` exports the `contextlayer` Vite integration. It configures the Cloudflare plugin and calls the CLI-owned `getLocalToolsBindings` from `@usecontextlayer/cli/vite` only during development: Node reads the AppID from Git origin and obtains a current access token through the same saved-login implementation used by CLI commands. It returns `CTX_APP_ID`, `CTX_PLATFORM_URL`, `CTX_AUTH_ISSUER`, and `CTX_ACCESS_TOKEN`, and a validated `CTX_APP_MANIFEST` startup snapshot for the auxiliary Worker's programmatic bindings. It does not copy the refresh token into the Worker. Restart `pnpm dev` when the access token expires or the manifest changes. Generated apps install `@usecontextlayer/sdk`; no separate auth package or middleware is involved.

The `@usecontextlayer/sdk` package owns the local Tools Worker, binding and response validation, and Tools interface/React Router context. `@usecontextlayer/sdk/worker` exports `createApp`, which owns the React Router request handler and selects the local Tools binding or production `ctx.props.tools`. The app supplies its virtual server-build import and Vite mode/development values. Generated files contain thin wiring; ContextLayer runtime and Vite behavior live in packages. The Gmail page remains an example, not the default application. The former For You adapter and consumer-key configuration have been removed from source; the legacy @usecontextlayer/tools v0.11.3 package retains the old behavior. New apps use @usecontextlayer/sdk.

During local development, the Cloudflare Vite plugin runs the React Router app and a development-only auxiliary Tools Worker under `pnpm dev`. A native RPC service binding supplies the Tools handle, which the app entrypoint puts into React Router context. The Tools Worker calls the platform's authenticated execution endpoint with the connection slug, tool name, and arguments. The platform resolves the assigned connection and executes through Composio. The loader receives `{data, logId}`; a reported Composio error throws with its log ID.

The hosted entrypoint receives its Tools handle through dispatcher-supplied `ctx.props.tools`. The dispatcher exports a `Tools` WorkerEntrypoint whose private props contain AppID and the viewer session token. It calls the same platform execution API as the local Tools Worker, supplying the viewer cookie instead of a CLI access token. Platform verifies the user and resolves the manifest-selected `(app_id, owner_type, owner_id, slug)` assignment. Cloudflare scopes the RPC handle to the current request; the app cannot read its underlying props. The composition difference stays at the entrypoint, and the local auxiliary Worker and its token binding are excluded from production builds.

## Key contract: app credential requirements

The author owns `<APP_DIR>/public/slate.json`, served at `/slate.json` by the framework's native static-asset handling. This is the single source of the app's connection and secret requirements. Vite serves the local file during development and includes it in the production assets, so each deployment carries its own requirements. Do not add a custom resource route, a copied root manifest, or a separate requirements store.

The manifest contains a `connections` object keyed by the slug used in `tools.call(slug, toolSlug, args)`. Each connection declares its Composio `toolkit` and `mode` (`viewer` or `owner`). A `secrets` object uses secret names as keys and declares the same modes. `viewer` selects the acting user’s user Owner; `owner` selects the app’s owning user or organization. New apps start with empty `connections` and `secrets` objects. `@usecontextlayer/shared/slate` owns the Zod manifest contract and mode vocabulary; CLI, SDK, and platform use it. For example:

```json
{
  "connections": {
    "work-email": {
      "toolkit": "gmail",
      "mode": "viewer"
    }
  }
}
```

Local tooling reads the checkout's `public/slate.json`; callers inspecting a running app fetch `/slate.json` from that app's origin under the app's viewing authorization. Deployed requirements come from the deployed app, not the latest Git commit. Consumers validate the manifest with the shared Zod contract. Connection requirements select assignments stored by `(app_id, owner_type, owner_id, slug)` in platform Postgres. Secret declarations directly reference `(Owner, name)` in the existing Doppler vault and need no assignment record. Missing `secrets` means no secret requirements; the old individual/shared mode values are rejected. Secret value loading and hosted agent execution remain a later step.

## Viewer profile capability

`Viewer.getCurrentUser()` returns the web-owned safe profile `{ id, name, image }` or null. Local startup adds a VIEWER service binding targeting the Viewer export in the same development-only auxiliary Worker as Tools. It calls web's /api/me with the CLI access token. Hosted dispatcher uses native loopback exports to create props.viewer with the existing viewer session; it passes only the RPC stub into user code. Web owns verification and user-table lookup, and each HTTP boundary validates the returned profile with Zod. Dispatcher has no identity policy or profile database. CTX_AUTH_ISSUER defaults to the existing production web issuer in dispatcher and comes from CLI configuration locally.

The SDK's createApp installs that handle into viewerContext. React Router's native default context returns null for anonymous requests, which retain empty hosted props. A web 401 likewise returns null; other HTTP failures propagate. The capability exposes no credential, AppID argument, or additional login. The local and hosted interfaces are implemented and compile. The installed local loader is verified against web through the native auxiliary Worker. The template re-exports the SDK root loader, which reads the profile through viewerContext; Layout consumes root route data and renders the avatar/name through stock shadcn Avatar inside the ShadowRoot. The header has separate full-height sections for its prompt and identity, divided by 1px slate-200 borders. Anonymous viewers see “Not signed in”. Local header rendering is verified; hosted execution is not yet verified or deployed.

## CLI authentication

The CLI login implementation uses OAuth device authorization through web's existing Better Auth OAuth provider. The user approves a code at web's `/device` page; `openid-client` handles device requests, polling, and refresh. Tokens target `urn:ctx:platform` with `ctx:access`. The CLI stores tokens in `~/.contextlayer/auth.json` and `ctx whoami` calls web's `/api/me` directly, where web's existing authentication boundary verifies the access token's signature, issuer, audience, expiry, subject, and scope using Better Auth's native resource client. App creation and personal connection operations require authentication. Hostname resolution and app connection/tool operations enforce app viewing authorization; Git source access and dashboard listing also require authentication and the owner/member management rule. The device extension requires web schema migration and a registered public OAuth client before use. Local and production end-to-end verification passed: the user approved the device code, the CLI saved its tokens, and `ctx whoami` authenticated successfully against `/api/me`. Production uses issuer `https://www.usecontextlayer.com/api/auth` and platform `https://slate.usecontextlayer.com`. CLI authentication is included in npm releases starting with 0.12.0.

After successful login, the CLI registers its Git credential helper in the OS user's global Git configuration, scoped to `<CTX_PLATFORM_URL>/git`. Configuration stores the actual Node and CLI executable paths, not tokens. Git owns URL matching and HTTP authentication; `ctx git-credential` supplies native Bearer credentials by calling the existing `getAccessToken()` implementation, including refresh. The existing auth file remains the only credential store. Registration belongs to login so clone works before a checkout exists; init only sets the repository's immutable remote.

App listing and Git source access use the same `authorizeAppManagement` operation as private viewing. Public visibility only bypasses that rule for viewing. The API app catalog and dashboard inherit required authentication; the API handler and React Router loader call the same `listApps` operation with the verified identity and configured auth issuer. It retrieves organization memberships once per listing, then filters apps through the shared pure management rule before reading Artifacts commits. Dashboard loaders receive identity and configuration through native React Router context. Browser sign-in wiring and the visibility dropdown remain a later slice.

## Composio Platform connections

Owner-level connection management uses authenticated `GET` and `POST /api/connections/{type}/{owner_id}`, with `user` or `org` in the HTTP path. The CLI uses the same `resolveOwner` and `ownerPath` as secrets; command help owns personal/organization selection. The shared `listConnections` and `authorizeConnection` operations receive the canonical Owner and verified caller, enforce `authorizeOwner` before provider work, and use that Owner's ID for native Composio account listing or session creation. Listing follows Composio pagination and returns only ID, toolkit, alias, display name, and status, validated with Zod. Authorization calls `session.authorize(toolkit)` and returns the hosted link; the member completing OAuth manages the account for the selected Owner. Composio owns credentials, refresh, and the private account's OAuth lifecycle. There is no separate Composio user mapping: account setup, listing, and manifest-selected execution use the same Owner ID. Organization members can manage the organization's accounts through the existing membership rule. The previous user-only `/api/connections` endpoint is replaced. The project key is a platform Worker secret supplied by Doppler `platform/prod`, never a CLI credential. This supports Composio Platform only; existing For You connections are not imported. App assignment and Platform tool execution are implemented below.

## App-scoped connection listing

`ctx connections <target> list` accepts an AppID, public hostname, or `local`. One authenticated OpenAPI operation, `POST /api/apps/{target}/connections/list`, inherits app viewing authorization and delegates requirement resolution to `listAppConnections` with the canonical authorized app. With an empty JSON body it fetches the registered app’s deployed `/slate.json`. With a `manifest` body it validates and uses those requirements for this request only. Local CLI mode must run from the app root. It reads `public/slate.json` relative to the current directory, extracts the AppID from origin’s `/git/<app-id>` URL, and submits both using the saved user login. It does not search parent directories or add an AppID to the manifest. The Git remote supplies an identifier; inherited app viewing middleware authorizes its canonical app before listing, assignment writes, or tool execution. It requires no local dev server and does not persist the supplied manifest. AppID and hostname targets use the deployed manifest. The response contains the app and each requirement’s slug, toolkit, mode, and connection_id; assignments are read from `app_connection_assignment` for the viewer and app Owner, then joined according to each requirement’s mode; unassigned requirements return null. Owner-level account listing and authorization remain separate from app requirement listing.

The CLI owns local file/Git I/O and HTTP presentation. The API boundary validates the target into either `{ id }` or `{ public_hostname }` and validates any supplied manifest with Zod. Inherited middleware passes the normalized target into `resolveAppForViewing`, which performs one app lookup and calls the shared viewing rule. The entire `/apps/:target` operation group inherits required authentication and viewing authorization. The handler passes the resulting `AppAccess`—the canonical app paired with its verified `AuthIdentity`—into the domain operation, which owns the deployed-manifest fetch and returns structured requirements. It forwards that identity's existing credential when fetching the deployed manifest, so private manifests remain authorized. Local requirements are request-scoped input, never a replacement for deployed requirements.

## Owner-scoped connection assignment storage

`app_connection_assignment` stores choices using `(app_id, owner_type, owner_id, slug)` as its composite primary key. `app_id` is a UUID foreign key to `app.id` with `ON DELETE CASCADE`; the other columns and `connection_id` are non-null text. `owner_type` is `user` or `organization`, matching the canonical `Owner`. `slug` is the manifest connection key and `connection_id` is Composio’s connected-account ID. Toolkit and mode remain in the manifest. Migration 006 renames the former `user_id` column to `owner_id`, preserves existing assignments as user Owners, and changes the primary key; Kanel generates the resulting types. Apply it before deploying this code. Downgrading refuses organization assignments because the previous schema cannot represent them.

The existing assignment operation loads the declared requirement, resolves its mode through `getCredentialOwner`, and uses native Postgres upsert. Viewer assignment requires app viewing permission; owner assignment requires the existing app-management rule (owning user or owning-organization membership). Local CLI assignment reads the checkout manifest and passes it with the AppID from Git origin. Substituting a local manifest for assignment or execution requires app management, so ordinary viewers cannot author a declaration that selects the app Owner’s account. Provider-account ownership and toolkit-compatibility validation retain their existing scope; requirement existence is now necessary to choose its Owner.

Migration 002 is applied to production Neon. The deployed assignment/listing API was verified by assigning the demo app’s work-email requirement and reading the same stored connection through local, AppID, and public-hostname targets. CLI changes are available in the local build; no npm release has been cut.

### Platform tool execution

`POST /api/apps/{target}/tools/call` accepts `{slug, tool, arguments}` with an optional local `manifest`. It inherits authentication, app viewing, and subscription access. The platform loads the requirement through the same manifest operation used by connection listing and assignment. `resolveAppConnection` selects its canonical Owner and looks up that Owner’s assignment; `callTool` uses the selected Owner’s ID for the native Composio session and explicitly selects the connected account and toolkit. It preserves Composio’s `{data, error, logId}` response. Missing requirements or assignments return 404, and forbidden configuration or manifest substitution returns 403. Ordinary hosted viewers can execute an authored owner-mode requirement through the app viewing boundary without acquiring permission to configure that Owner’s connections or manage its vault. Viewer-mode execution remains scoped to that viewer’s accounts. The Composio project key remains on the platform.

Local loader integration uses the development-only Vite startup helper and Tools Worker described above. Its access token is a startup snapshot; no continuously refreshing local authentication service is involved.

### Dashboard account controls

The dashboard account menu uses Better Auth’s browser client and Better Auth UI’s session/multi-session hooks against web’s configured auth issuer. Web owns session listing, switching, and sign-out; these native auth operations do not acquire parallel platform endpoints. A component-owned QueryClient keeps server renders isolated. Better Auth UI refreshes session queries after switching. After Better Auth confirms an account switch, React Router navigates to Personal with history replacement and loads the new user’s authorized app list. Add account returns through web’s existing sign-in page. UI primitives use shadcn base-nova and Font Awesome Slab.

The dashboard uses `/dashboard/personal/apps` and `/dashboard/org/<organization-slug>/apps`; `/dashboard` redirects to Personal. The switcher presents Personal and organization names as plain text with consistent row spacing, without avatars or settings actions. Its choices come directly from web through Better Auth UI’s organization-list hook. The server resolves an organization slug against web’s authenticated `/api/platform/organizations` response using the caller’s existing credential, then uses the stable organization ID to query apps. The shared `ownerSchema` and derived `Owner` in `shared/lib/app-usage.ts` are the canonical user-or-organization ownership shape, re-exported by platform’s `app/owner.ts` used by app creation and listing. The authenticated creation operation accepts an optional `organization_slug`; its domain function resolves membership through web before choosing that organization’s stable ID or the verified user’s ID and writing the app. The dashboard’s `OwnerDetails` derives from it and includes schema-derived organization name/slug metadata; Personal is the verified user’s owner variant, never a null organization. No active-organization session mutation occurs, so tabs may select different workspaces. The app-list API accepts optional `owner_user_id` or `owner_organization_id` query parameters for non-browser consumers; omitting both lists all manageable apps. Zod rejects supplying both, and the handler converts the validated query to `Owner` or the listing’s all variant. Both the API and loader call the same `listApps` function with a typed filter and independent management authorization.

## App-owner billing access

Web’s native Better Auth/Polar integration owns individual and team customer creation, checkout and billing management. Platform receives `customer.state_changed` directly at `POST /api/polar/webhooks`; Polar’s SDK verifies the signature using the required `POLAR_WEBHOOK_SECRET`. `saveCustomerState` upserts the complete native state and event timestamp in `polar_customer_state`, keyed by Polar customer UUID with a unique nullable `external_id`. That external ID matches `app.owner_user_id` or `app.owner_organization_id`. Polar’s merchant `organization_id` is unrelated to our organization ownership. Kanel generates the JSON column with the native SDK Customer State type.

The existing viewing policy still owns public/private and membership authorization. After it succeeds, one `requireAppSubscription` middleware calls `checkAppSubscription` on runtime hostname resolution and actual tool execution. It reads the owner’s saved state and allows a nonempty `active_subscriptions` array; missing or empty state yields 402. Free counts. Dispatcher forwards the actual incoming pathname so exactly `/slate.json` can retain ordinary authorization without requiring billing. It forwards 402 through its existing failure path. Hosted and local Tools both call the gated platform endpoint; local page rendering itself does not go through hosted dispatch. App creation/listing, dashboard, Git and connection configuration do not require a subscription. Initialize existing owners from Polar’s native Customer State API before enforcement; no request-time API fallback or membership mirror is introduced. Usage metering follows execution: dispatcher records recognised dynamic GETs (1 clip) and POST/PUT/PATCH/DELETE requests (3 clips), while the platform tool API records returned executions (1 clip). The shared `app-usage` module converts the canonical `{ id, owner }` and event name into native Polar ingestion, with `metadata.clips` and `metadata.user_code_worker_id`. Resolution supplies its owner through the shared Zod contract; platform converts its loaded app through `getAppOwner`. Both boundaries use native `waitUntil` and return without awaiting Polar. Best-effort classification for these methods recognises HTML, JSON (including application `+json`), React Router `text/x-script`, plain text, CSV, XML, NDJSON, event streams and redirects. JavaScript, CSS, image, font and WebAssembly responses and exact `/slate.json` produce no usage events. Response headers are app-controlled, so this is the user-approved normal-traffic heuristic, not an unbypassable distinction between static and dynamic responses. No SDK-side reporting or route instrumentation is required; rates and canonical owner attribution stay in trusted Workers. Polar’s existing Clips meter aggregates all three event types and owns allowances and prices.
