# Architecture

The repository contains eleven packages; `@usecontextlayer/cli` and `@usecontextlayer/sdk` are public and the others are private:

- `cli` — Published as `@usecontextlayer/cli`; Commander-based `ctx` executable, bundled with tsdown; its version comes from its package manifest, and `init` delegates checkout scaffolding to the official `create-cloudflare@latest` React Router scaffold.
- `sdk` — Public `@usecontextlayer/sdk` integration: shared React Router document Layout, reusable HTML page shells for standalone MCP servers, Tools and Databases interfaces and React Router contexts, slate request handling, local auxiliary Worker, and authored MCP tool/View builds through Vite. Subpath exports keep React UI, Vite/Node imports, and Worker runtime imports separate.
- `db-infra` — Postgres/Kysely connections and migration infrastructure.
- `dev-env` — Private development and integration setup shared with web. It owns database initialization, native service startup and development provider discovery; callers supply application-owned migrations and compose returned connection facts. Runtime applications do not depend on it. Root `pnpm dev`, `pnpm dev:ctx`, `pnpm dev:env` and Vitest are its consumers. Web owns local identity/client initialization and returns the initialized public CLI client ID to startup. The existing `@usecontextlayer/cli/auth` operations own saved credentials, issuer/client matching, refresh and authenticated identity/membership reads; both production CLI callers and setup pass explicit issuer/client and credential-directory settings into them. That export contains only `getAccessToken`, `getCurrentUser`, `listOrganizations`, `LoginRequiredError` and the `AuthEnv` type; interactive login remains a CLI command. Integration fixtures select these capabilities through Vitest dependencies and native fixture lifetimes. Test bodies own their product actions and scenario resources.
- `shared` — Shared resource contracts, Worker capabilities, and usage metering.
- `twilio` — Twilio Functions for founder call routing and answer screening.
- `platform` — Cloudflare Workers application: an Artifacts Git proxy under `/git`, OpenAPI endpoints under `/api`, and the React Router dashboard under `/dashboard`.

- `build` — Cloudflare Worker using `@cloudflare/ci` and Workflows to build commits pushed to Artifacts in isolated Sandbox runners.

- `dispatcher` — Cloudflare Worker that resolves public hostnames through the platform API and invokes the WfP Worker named by SlateID.

- `auth` — Worker that owns viewer sign-in on the user-code domain.

- `mcp-microsoft-planner-premium` — Standalone Planner Premium MCP Worker using Dataverse queries for reads and the Schedule API for writes. Read queries begin at Planner entity sets and can expand related data under the caller's Dataverse permissions; Microsoft owns query expressions, pagination, native entity fields, action parameters and response fields. Initial retrieval and continuation have separate MCP tools sharing one authenticated client. Deployment configuration selects the shared multi-tenant Entra application; each connection selects its Dataverse org, bound to the token's audience. Microsoft owns consent and token issuance; Composio stores and refreshes credentials; the Worker stores no clients, codes or tokens. The HTTP edge checks bearer claims and expiry and confines credential forwarding to supported Dataverse HTTPS origins derived from the audience; continuation URLs must remain within that environment and an allowed Planner root. These checks do not verify Microsoft's signature; Dataverse validates the forwarded credential. Its Microsoft-issued Dataverse tokens are outside the Better Auth resource model in [OAuth resources and scopes](#oauth-resources-and-scopes); no ContextLayer slate is involved.

Development authentication uses the authority being exercised. Shared setup signs into running web through Better Auth's native client and cookie helper; the consuming fixture owns that session and signs out during cleanup. The development package owns the shared baseline credential parser. Web's isolated tests may use Better Auth `testUtils()` with the application's auth configuration when authentication is only setup. Connected user and organization creation uses the normal application operations so Polar lifecycle hooks run. CLI OAuth credentials remain owned by the CLI; viewer handoff and slate-scoped OAuth grants retain their actual protocols.

## Multiple consumers

Almost every user-facing platform capability is exposed through OpenAPI so the web dashboard, CLI, and a future MCP consumer share the same product operations. Zod owns their input and output contracts. A shared domain function owns each operation’s business logic, authorization, and database calls; API handlers adapt it to HTTP and React Router loaders/actions invoke it directly in-process. UI components own presentation and interaction. This is a standing design rule, not a claim that every future CLI command or MCP surface exists today. Better Auth owns its native authentication protocols; product APIs consume the resulting verified identity.

## Security boundary: trusted services and authored slates — principles

These principles define the security boundary the system must uphold; they are requirements, not assertions that every protection is implemented today.

Treat web, platform, auth, and dispatcher as trusted ContextLayer services, and authored browser code and user Workers as untrusted. The same boundary must apply in hosted slates and local development. Serving ContextLayer UI inside an authored app must not grant that app trusted authority.

Web and platform management APIs must require native web sessions or explicitly authorized CLI credentials and must reject viewer-cookie authentication. Viewer-cookie acceptance must be explicit and limited to platform slate resolution and web's private-organization membership fact endpoint. General profile and organization reads must require native web or CLI credentials. Viewer credentials must not contain reusable management credentials or permit replay as a native web session; rejecting a cookie name alone does not establish that separation.

Hosted authored slates should receive only explicitly delegated runtime capabilities bound to the canonical slate and viewer. Local authored slates should receive only runtime capabilities bound to their selected local resources, with personal-account authority derived from the verified developer. A tool-execution capability must authorize only its permitted runtime operation, without granting permission to connect or assign accounts, access general organization operations, or forward arbitrary authenticated API requests. Trusted services must hold credentials and enforce authorization; user code should receive only the capability and its permitted result. Platform should own slate authorization decisions, and dispatcher should consume those decisions and transport requests without duplicating policy.

Untrusted browser code and user Workers must never receive reusable ContextLayer management credentials. Fetching authored content, including `/slate.json`, must not carry web session cookies or CLI access tokens, including across redirects. Private content must still require viewing authorization without disclosing the caller's management credential. Trusted auth must own viewer-session changes; authored responses must not create, replace, or clear ContextLayer authentication cookies.

Connection assignment and other privileged chrome operations must run on a trusted browser origin. Shadow DOM isolates styles, not JavaScript authority. An authenticated same-origin relay available to chrome is equally available to authored page scripts and must not expose management operations. Cross-origin frame messages must validate the sending origin and frame and carry only the intended presentation interaction, such as resizing; they must not expose credentials or become an authenticated API bridge. Chrome system requests should run independently of the authored app's React Router loaders and user Worker and enter neither slate-request nor tool-execution clips metering. Billing policy should remain owned by the existing metering paths.

Local development must preserve the same boundary. A saved CLI credential must remain in trusted local tooling and its auxiliary Worker and must not be exposed to authored browser or Worker code. Browser origins serving local apps must not gain credentialed web/platform API access through blanket localhost trust. HttpOnly, cookie domains, and CORS should support the boundary without replacing the separation of authority.

## Authority model — principles

Authority means the operations and resources a verified caller or delegated runtime capability is permitted to use. The system must establish that authority at a trusted preparation boundary and carry its scoped result into execution. Interfaces and domain signatures must exclude inputs that would let a caller substitute a different credential Owner, declaration source, or assignment. Reshape existing platform interfaces when necessary to remove those choices; do not preserve an ambiguous local-or-hosted execution operation and compensate with provenance flags or permission branches.

Personal-account discovery and execution must derive their resource Owner from the verified caller's user identity. Neither HTTP requests nor execution-facing domain callers may supply an Owner, organization, or declaration that changes this derivation. A requested account ID selects an account within that personal scope; it must never select the identity or confer account authority. Slate access, subscription, and usage context must remain separate from credential ownership.

Hosted preparation must own coherent pushed declaration selection, consumer selection, resource Owner derivation, and hosted assignment resolution under the canonical authorized slate and run actor. A caller may request an operation through the delegated runtime interface, but must not replace its declaration, selected Owner, or resolved assignment. Pure collection and consumer selection remain shared functions; trusted preparation owns the I/O and authorization rather than making each downstream consumer reread declarations or decide authority independently.

Common provider execution should receive an already scoped native Composio session plus the tool and arguments. Session creation belongs to the trusted personal or hosted preparation path, which fixes identity, declared toolkit, and account pinning before execution. Provider execution has no responsibility for choosing slate, viewer, developer, or resource Owner. Account ownership enforcement remains at the provider boundary. A low-level session helper must not become a public execution operation accepting an arbitrary Owner.

Native authentication route composition must keep personal-account operations under native web or authorized CLI authentication and exclude viewer cookies. Hosted runtime delegation retains its limited slate/viewer authority; it must not authenticate personal-account management operations. Explicit Owner-management operations are separate and enforce their own Owner authorization. This structure must exclude local declarations from hosted authority, local assignments from hosted assignment resolution, caller-selected credential Owners from personal execution, and runtime viewer credentials from management authentication.

## Platform and web: ownership and dataflow

Web owns Better Auth users, sessions, organizations, and organization memberships. Platform owns slate membership as the separate slate-to-user relationship. Platform owns slates and their authorization. Platform stores the owning user or organization ID, without copying web's identity or membership records. A browser session cookie is a signed opaque session identifier; platform does not extract identity from it or verify it with another session secret.

Platform must preserve the verified credential's authority in `AuthIdentity`, the closed union of `OwnerIdentity` and `ViewerIdentity`. Native web sessions and OAuth tokens verified for the platform resource with `platform:access` produce owner identities; viewer sessions and OAuth tokens verified for a canonical slate MCP resource with `mcp:access` produce viewer identities. OAuth identities retain their opaque credential, verified claims, and verified resource. Management domain operations must require owner identity; viewing operations may accept either. Owner identity establishes the credential's management authority, not ownership of an arbitrary slate or resource: the existing ownership and membership predicates still decide access. A shared user ID must never promote viewer authority into owner authority.

For trusted dashboard requests, platform forwards the user's native Cookie header to web's `/api/auth/get-session` endpoint and uses the verified user returned by Better Auth. CLI requests retain their scoped bearer access tokens. The request's verified identity and credential flow through the Hono boundary into shared domain functions and dashboard React Router loaders. Web's `/api/me` owns the current-user profile contract: `{ id, name, image }`, with nullable image and no response caching. It accepts authorized CLI bearer tokens and native web cookies. `ctx whoami` calls web directly using the origin of `CTX_AUTH_ISSUER`; platform does not expose or proxy that endpoint. Trusted chrome should read the profile inside its own frame; authored SDK/runtime code should expose no profile-read capability.

Required authentication has one Hono middleware implementation. Protected API and Git routes respond with 401 when identity is absent. Dashboard routes enable the sign-in response: an unauthenticated GET that prefers HTML through Hono's native `accepts` helper redirects to web's `/auth/sign-in`, passing the requested dashboard URL as Better Auth UI's `redirectTo`. The existing UI supplies it as Better Auth's social `callbackURL`; web owns authentication and trusted-origin validation. Requests that do not prefer HTML retain 401. `Accept` selects the response behavior; request `Content-Type` describes the body. Platform reuses the web cookie after sign-in. Production uses web’s native Better Auth cross-subdomain cookie on `usecontextlayer.com` and trusts the platform sign-in return origin.

CSRF protection follows identity verification and uses the verified credential kind. Cookie and viewer-session authenticated form mutations must pass Hono's native Origin or Sec-Fetch-Site checks. Verified bearer requests do not require browser origin metadata. Requests without verified identity reach the existing authentication boundary and its sign-in response or 401 challenge.

For management requests, when platform needs user-scoped web facts such as organization memberships, it forwards the same user's authorized native web cookie or CLI access token. Web authenticates the caller and returns authoritative facts through its authenticated endpoint; platform applies its own slate rules to those facts. These requests do not use a machine-to-machine credential. Better Auth owns credential verification and session revocation; platform owns the resulting slate-access decision.

Private organization viewing must select the membership read by verified identity authority. Owner identities use web's platform organization records; viewer identities use `/api/viewer/organizations/:organizationId/membership` for only `{isMember}` about the canonical slate's owning organization. For an MCP viewer, platform forwards the slate-bound bearer in `Authorization` and its verified resource in the endpoint's `resource` query parameter so web can verify the same audience and scope. Viewer sessions retain their existing cookie path. Web remains the membership authority; platform applies its viewing predicate to that fact. This narrow read must not grant general organization access or management authority.

## Resource configuration and execution — principles

These are architectural requirements for local development and hosted execution. Implementation decisions, progress, and verification belong in the ExecPlan; recording a requirement here does not assert that its implementation is complete.

<a id="domain-model"></a>

A declaration is the file (`slate.json`) in which a consumer names the resources it requires. A slate has an app (its interactive part), agents, mcps, workflows (planned), and resources; resources are connections, databases, and secrets. Apps, agents, and mcps are the consumers of resources. `Resources` is the slate-wide collection of requirements with consumer metadata. `SlateResourceConfiguration` adds canonical Owners, saved connection references, database references and viewer-mode secret presence to those requirements; a configuration can still have missing inputs. A connection is declared by slug, toolkit, and mode; a connected account is the provider-side credential at Composio. An assignment satisfies a connection with a connected account, hosted or local; the actions are connect an account and assign it to a connection. `Owner` is the canonical organization-or-personal identity that owns a slate or resource, with `organization` and `personal` as its type values; `owner` and `viewer` are declaration modes for selecting a resource Owner in hosted execution. A run actor is the app or a person a job acts for, independently of resource ownership. A slate member is the stored slate-to-person fact that the person has been provisioned after complete setup; an organization member has a separate web-owned organization membership. The local copy of a slate is its checkout. A slate's name is its hostname label, with no separate display-name column. Keep these concepts distinct in configuration and execution.

One shared declaration model must feed all consumers. public/slate.json and agents/{name}/slate.json use exactly the same declaration schema and form one slate-wide namespace per resource kind. A repeated key denotes the same resource: connection declarations must agree on mode and toolkit, and database/secret declarations must agree on mode. Central collection and validation must retain which app or agent requires each resource. Inventory and initial membership must use the whole collection; request preparation must use only its app or named-agent requirements. One pure resolution rule must report missing inputs from the configuration it receives. Whole-slate completeness must govern initial personal provisioning, while request completeness must govern execution.

Local inputs must be applied at the local construction boundary before consumer selection. Resources must already reflect the current checkout's validated declarations; local connection assignments, environment-supplied secrets, and developer-local database references and committed migration artifacts must be assembled there as well, before runtime consumers receive them. Resources remains the collected requirements value; resolved assignments, database references, and secret values are execution inputs, not authored requirements. Consumers must not reread local files or environment variables, apply local overrides, or look up hosted assignments after selection. Shared schemas, collection, selection, and provider primitives should serve both environments; environment-specific I/O and authority belong at their respective boundaries.

Local connections must always use the signed-in developer's personal accounts, regardless of slate ownership or the declaration's viewer/owner mode. Platform must derive that personal Owner from verified authentication and independently authorize the narrowly requested toolkit/account before provider work. Neither a local declaration nor an account ID grants access to another user or organization's accounts. Save development assignments from connection slug to connected account ID in the checkout's ignored `.contextlayer/connections.json`; do not read or write hosted assignments to resolve or save local assignments. Composio retains provider credentials.

Local secret values must come exclusively from developer-local environment variables. Local databases must use the same SQLite-backed Durable Object class and native Drizzle migrator as hosted execution, with persisted state under the slate’s ignored .contextlayer/databases directory. Local tooling constructs database references and migration bundles from the current checkout before consumer selection. Native local runtime startup applies that history before app or agent queries. Local resolution must never use platform vault values, hosted databases, or hosted configuration as a fallback. Pushing authored declarations and migrations does not deploy development state or environment values. Chrome must be disabled in local development through native Vite development detection; local account configuration uses the CLI identity.

Hosted resource resolution must derive the canonical Owner from the pushed declaration and authorized actor: viewer selects the acting user's personal Owner, and owner selects the slate's owning user or organization. Platform owns hosted connection assignments; hosted secret references select the existing Owner/name vault model; database ownership follows the declaration. Owner authorization must precede account management or vault management. Public visibility grants viewing only, while the owning user or an owning-organization member has slate management permission independently of visibility. Hosted runtime delegation may permit an authorized viewer to execute a slate's owner-mode requirement without granting general Owner account or vault management. Local personal-account execution must preserve a separate authorization path from that hosted delegation.

## Platform storage and request flow

Hosted declaration consumers must share one coherent latest-`main` repository snapshot, read through native Artifacts by canonical SlateID and validated with the shared declaration schema. The declaration reader receives no caller credentials; platform authorization precedes its use. Repository declaration reads must bypass authored Workers, public dispatch, and clips metering, keeping credentials inside trusted services. Slate configuration, tool and database execution, agent preparation, and provisioning must consume this common declaration boundary. A repository without a commit on `main` is the typed `no-commit` setup condition, carried through hosted resource reads as data. Resource listing, connection listing and connection assignment expose the shared `{ reason: "no-commit" }` payload with HTTP 409; the CLI and chrome explain that nothing has been pushed yet. This state is distinct from a committed slate with no resource requirements. API and scheduled agent runs are hosted executions even when their caller is a developer; neither may read that developer's local declarations, assignments, or environment.

Developer resource configuration must use only the current checkout's declarations. Local tooling reads public/slate.json and agents/{name}/slate.json, validates them with the same declaration schema, and collects Resources locally, without supplementing requirements from pushed or deployed state. Platform must never accept caller-supplied local declarations or Resources as declaration authority for resource listing, assignment, or execution, including from slate Owners. Local tooling composes local requirements with independently authorized account metadata; platform must answer only narrowly scoped connected-account discovery and execution requests for that local workflow. Hosted CLI targets, chrome, and dashboard use the coherent pushed snapshot and platform-owned hosted configuration.

The dashboard uses shadcn/ui with the `base-nova` preset and standard Tailwind layout utilities.

Platform separates page routes from asset URLs: React Router's basename is `/dashboard/`, while Vite uses its default `/` asset base. Cloudflare's native selective `assets.run_worker_first` sends `/api/*`, `/git/*`, and `/dashboard/*` through the Worker, including dashboard data requests. Scripts, CSS, and fonts use native asset serving outside those routes; production bundles live under `/assets/`. This configuration belongs only to platform. User-slate requests retain the existing dispatcher authorization flow.

Slate visibility is platform configuration stored in the non-null text column `slate.visibility`, separate from ownership and the authored declaration. `slateVisibilitySchema` validates `public` or `private` in code, and `DEFAULT_SLATE_VISIBILITY = "private"` supplies the creation default. There is no PostgreSQL visibility check or persistent default. Database slate rows are parsed into the slate schema before returning slate-bearing domain results. `PATCH /api/slates/{target}` accepts `{visibility: "public" | "private"}` for a SlateID or public hostname. Its shared `updateSlateVisibility` function enforces slate management permission for the owning user or owning-organization members, writes only visibility, and returns the saved slate. Public viewing grants no management permission.

Hono middleware creates a request-scoped Postgres.js/Kysely connection from validated Worker bindings and passes through the native Artifacts binding. Route groups select identity verification: non-MCP slate resolution accepts viewer cookies as well as native web/CLI credentials; MCP slate resolution requires its slate-bound bearer credential; protected management APIs, Git, and dashboard use only native web/CLI credentials. The middleware stores the optional `AuthIdentity`; protected groups require it before running. API handlers and React Router loaders share these through their framework contexts; `waitUntil` closes the database after the handler finishes. The Cloudflare Vite plugin runs development in workerd and builds the Worker plus client assets. The platform's `slate` table contains `id` (UUID primary key, generated by Postgres), `public_hostname` (text with a unique index), and nullable text `owner_user_id` and `owner_organization_id` columns. PostgreSQL's `slate_exactly_one_owner` constraint requires exactly one Owner. Slate identity is immutable; the public hostname is independent. Package-owned Kysely migrations and Kanel-generated models follow the `db-infra` patterns, using a separate logical database on the shared local Postgres instance.

Local platform development and integration Workers must use remote Cloudflare resources isolated from production. Native Wrangler environments and framework configuration select bindings before requests run; runtime callers must not select namespaces or override this boundary.

`POST /api/slates` requires authorized CLI bearer or native web-cookie authentication and passes the verified identity, auth issuer, and validated creation input into `createSlate()`. The shared domain function resolves an optional `organization_slug` against the caller's authoritative organization records before any writes; an absent membership returns 404. Omission selects the verified user. With the resulting typed `Owner`, it generates a friendly adjective/color/animal hostname, inserts a private slate, and creates an Artifacts repository named by its UUID. Better Auth in web owns user identities and organization memberships; platform stores their IDs, with no cross-database foreign keys or copied memberships. The agreed viewing rule allows anybody for public slates, the owning user for private personal slates, or members of the owning organization for private organization slates; platform resolution, connection configuration and delegated execution enforce this rule, with Git source access and management restricted to the owning-user or owning-organization-member rule regardless of visibility. Organization membership checks use that slate's owning organization regardless of the session's selected organization. `ctx init` requires the saved login before scaffolding, sends the optional organization slug and its access token to creation, and sets `/git/<slate-id>` as the checkout's remote. `GET /api/slates` and the dashboard loader call the shared `listSlates()` operation, which returns only slates manageable by the verified caller and their latest main-branch Artifacts commit. Commit hashes remain Cloudflare-owned data. Zod defines API contracts, with OpenAPI at `/api/openapi.json`.

`GET /api/slates/resolve?hostname=<public-hostname>&pathname=<incoming-path>` inherits optional identity verification and viewing authorization through Hono middleware. `resolveSlateForViewing()` looks up the unique `slate.public_hostname` and delegates to `authorizeSlateViewing()` using the validated canonical slate and already-retrieved membership facts. The viewing and management predicates are pure; the domain operation owns membership I/O. Public viewing allows anybody; private viewing requires the owning user or membership in the owning organization. Web owns the authoritative `{id, slug, name}` organization records used for membership checks and organization-slug resolution. Platform obtains those facts through trusted service calls; a viewer credential does not grant direct access to web's organization API. Successful resolution returns the immutable SlateID and canonical Owner; required sign-in returns 401, denied viewing returns 403, and an unassigned hostname returns 404. Platform owns the mapping and authorization decision; dispatcher consumes the result for browser requests and `/mcp`; public OAuth resource metadata is served separately without viewing authorization.

Public hostname assignment rejects subdomains in the hardcoded reserved list in `packages/platform/app/slates.schema.ts`. `local` is reserved because it selects the current checkout in the CLI. `auth` is reserved for the auth-forwarding worker at `auth.contextlayer.xyz`. Neither can be a slate subdomain.

Git clients use the immutable `/git/<slate-id>` endpoint. The Git route group inherits identity verification and required authentication. `getGitAccess` resolves the slate and calls `authorizeSlateManagement` before obtaining any repository-scoped Artifacts credentials. Only the owning user or members of the owning organization may clone, pull, or push, including public slates. The Git service determines read versus write credentials: upload-pack reads and receive-pack writes, including their GET discovery requests. Hono's proxy helper forwards protocol traffic; Artifacts credentials stay server-side. Pushes do not create slate records.

## Slate forking, membership, and resource ownership

Git-powered forking must be a core capability of the slate model. Users must be able to take an existing slate as a starting point and independently adapt its code and behavior while preserving its source lineage. The platform must support forking, slate membership, and resource ownership as orthogonal concepts that compose. Shared slates and independently customized slates must both fit the same domain model.

Forking combined with AI must enable customized slates to continue receiving upstream improvements. Git must preserve the upstream relationship and shared history so changes can be identified and merged; AI should help resolve conflicts and adapt upstream changes to the fork's customized code while preserving the intent of its customizations. This is why forking is central to the slate model: users should be able to make a slate their own and continue benefiting from fixes, features, and improvements to the slate they started from. Independent customization and continued upstream evolution must be supported together.

| Concept | Responsibility |
| --- | --- |
| Forking | Independent control over a slate's code and behavior, with Git lineage and AI-assisted integration of upstream improvements. |
| Slate membership | The relationship between a slate and the people who use it. |
| Resource ownership | Ownership of credentials, connected accounts, and documents, with access governed by resource authorization and connection assignments. |

Forking must use Git to create an independently customizable slate while preserving source ancestry. A fork must have its own slate identity and repository, with its own ownership and membership context. Its Owner may be the same as the source slate's Owner or a different personal or organization Owner. A fork must support one or many slate members, just as any other slate does. Git lineage must describe the relationship between codebases; it must not determine slate membership or resource access.

Slate membership must allow multiple people to use the same slate without requiring separate code forks. Member-specific resources should support personal state within a shared slate. Independent changes to slate code should be expressed through forking rather than through membership. Forking must not replace membership, and membership must not prevent forking.

Credentials and connected accounts must belong to their personal or organization Owner independently of any slate, code lineage or slate membership. Slates may share authorized connected accounts without sharing control of their code. Hosted databases must be identified by (SlateID, canonical Owner, declared slug): two slates with the same Owner and slug receive separate databases, while agreeing app and agent declarations within one slate select the same database. Viewer mode selects the acting user’s Owner and owner mode selects the slate’s Owner. A code fork must not copy credentials, transfer stored data or grant access to the source slate’s resources.

Declaring a hosted database must be sufficient configuration. Platform must derive its identity centrally and use one platform-owned SQLite-backed Durable Object class with an isolated named instance per database, without database assignments or a picker. Deployment must provision owner-mode databases for the app actor even with no members. Initial membership must provision the person's viewer-mode databases under the [membership rule](#slate-membership-and-unattended-execution). Both lifecycles must share provisioning and consume one coherent declaration and migration snapshot. Committed database migrations must complete before schedules are installed or a personal request executes; repeated provisioning must preserve stored data through the native migrator's applied-history ledger. Inventory must remain metadata-only, and queries must consume prepared database references. Artifacts must own source; Durable Objects must own persistent slate data.

Forks and shared slates must use the same resource-selection and execution semantics. An agent's unattended scope must continue to derive from its own actor-dependent requirements, independently of whether its slate is a fork or how many members use it. Forking, membership, and resource sharing should let people choose independent code customization, shared slate use, and shared resources without making any one choice determine the others.

## Owner-owned shared secrets

Shared secrets must belong to the canonical personal or organization `Owner`, independently of slate ownership. `PUT` and `DELETE /api/secrets/{type}/{owner_id}/{name}` must accept `personal` or `org` at the HTTP boundary and return only `{ owner, name }`. Secret and connected-account management must share Owner authorization before provider I/O: a personal Owner must match the verified caller, and an organization Owner must require membership supplied by web through the caller's existing credential. Managing an Owner's secrets must remain independent of any slate lookup, slate membership or subscription.

Doppler must own hosted vault storage; [DEVELOPING.md](DEVELOPING.md#shared-secret-management-verification) owns development and production vault configuration. Authored-slate local development must instead use developer-local environment values. Platform must construct `OWNER_<PERSONAL|ORGANIZATION>_<uppercase UTF-8 hex Owner ID>_<name>` keys and select the vault; clients must never select provider keys or configs or receive the vault token. Vault configuration must be required for viewer-secret presence reads, trusted value loading and mutations. Owner-only configuration must not list vault names; unrelated platform operations must remain independent of vault configuration. The config-scoped token covers the vault, so platform authorization must enforce Owner isolation. Stored values must enter only trusted execution, never an HTTP read operation or logs; provider failures must expose only the operation and status.

Slate-aware secret supply must select its canonical Owner from the coherent pushed declaration and reuse Owner-scoped authorization and storage. A successful save must remain successful when another setup input is missing, and must attempt membership through the [shared membership rule](#slate-membership-and-unattended-execution). Owner-scoped set/drop must remain independent of slate enrollment. Chrome must consume shared presence metadata without loading stored values or exposing secret values or configuration to authored code.

CLI secret management must use the same verified Owner and authorization as other trusted consumers. Secret entry must be masked when interactive, and values and provider credentials must stay out of CLI output. The CLI must never receive the vault token; command help owns input and Owner-selection syntax.

## Authored agents

A slate can contain named agents at `agents/<name>/instructions.md`. The slate's existing Git push writes their standing instructions to its Artifacts repository. `GET /api/slates/{target}/agents/{name}` returns `{ commit, instructions }` from the latest commit on `main`, pinning the file read to that commit. `getAgent` in `packages/platform/app/agents.server.ts` applies the same owner/owning-organization-member source permission as Git, including for public slates, then calls the shared native Artifacts reader. The endpoint follows the existing authenticated slate boundary and Zod/OpenAPI contract. Reading the definition is independent of the slate's build or deployment; the repository remains its source.

Hosted execution must separate the authorized trigger, prepared run and native execution. The trigger must supply a canonical slate, explicit app/user actor and user prompt. Preparation must resolve only the selected agent's resources to canonical Owners and references before background execution; viewer-mode requirements must first satisfy the [membership rule](#slate-membership-and-unattended-execution). The prepared run must carry agent instructions and source revision, resource references and actor, with caller credentials and secret values excluded from persisted configuration. An app actor has no person against whom viewer resources can resolve. Source and rich execution inspection must require slate management, while manually requested jobs, catalog discovery, and ordinary operation/result access must follow private-slate viewing authorization. Owner-only runs must remain independent of personal setup and membership; app actors and public viewers must not prepare viewer-mode resources.

A stable native Cloudflare Agent is addressed by slate, agent, and actor and owns a `RoutedAgents` catalog. Each catalog entry addresses an independent top-level job Agent, with its own prepared run and fresh Pi conversation. `PiHarness` installs on that job's native Lifecycle and opens Pi Durable over its SQLite storage. Pi owns submissions, model execution, pending state, transcripts, results and recovery; the SDK owns durable wakeups. Prepared configuration belongs to the job, so later jobs cannot change the resources selected by an earlier one. Model credentials are loaded from the selected Owner's secret store into trusted in-memory Pi AI provider configuration, without entering persisted configuration or prompts. Authored instructions render through a native Pi prompt section, and the task is a separate user input.

Hosted model selection must reuse declared-secret Owner resolution, independently of API-key ownership. Pi must own the selected model in conversation state: new jobs read current configuration, while existing conversations retain their selection. A default applies only when the model is undeclared; a declared missing or unavailable model must fail without substitution. Model identity may appear in native execution records; API-key values must remain private.

Job admission uses the stable Agent’s native `blockConcurrencyWhile` around catalog creation, job lookup and the initial job submission. This holds catalog discovery until the job has persisted its native Pi receipt, including while Composio sessions and tool definitions are prepared. Requests in the same slate/agent/actor scope are serialized during admission; other scopes and already-running job execution remain independent. Cloudflare’s 30-second callback limit bounds initialization, not the duration of the submitted job.

Each job owns a fresh Linux computer through its native Durable Object container attachment. Pi's native `CodingTools` extension supplies `read`, `write`, `edit` and `bash`, available directly and through Code Mode, using the same `RemoteExecutionEnv`; the Pi environment daemon runs inside the container, while the harness, SQLite records, resource authority and provider credentials stay in the Worker. The job supplies environments at each native Pi use, sharing one connection and filesystem within that job. API and scheduled jobs use this same ownership path, so different jobs cannot reuse a computer. Native Pi owns filesystem operations, shell execution, output handling and cancellation; the application supplies the container stream transport. When Pi becomes idle, the job closes the daemon connection independently of result reads. Cloudflare retains the container for ten minutes after the owning Durable Object becomes inactive; stopping it discards files and processes, while Pi's SQLite records remain durable. Job deletion disposes Pi and destroys its attached container through native Lifecycle. The computer is ephemeral execution storage, not a persisted slate workspace.

Pi's native CodeMode extension runs JavaScript in an inline QuickJS sandbox inside the job Durable Object. Its `tools` calls use the same registered native tools as direct model calls, including `bash` through the job's `RemoteExecutionEnv`. Pi owns tool discovery through `searchTools`, `describeTool` and `describeNamespace`, nested execution, replay and conversation storage; the application must not maintain a second tool catalog. The sandbox exposes registered capabilities rather than ambient Worker bindings, network access or filesystem access. It requires no separate Worker or binding. Each execution disposes its VM, and the job Lifecycle closes Pi before closing its sandbox.

Declared agent connections must expose individual Composio actions through Pi's native tool registry. Each connection slug names a CodeMode namespace; its flat tool names are `<connectionSlug>__<COMPOSIO_ACTION_SLUG>`, and its actions retain Composio's input schemas unchanged. Connection selection is bound by the tool registration rather than added to action arguments. At job admission, shared `createConnectionSession` creates one `direct_tools` session per prepared connection, pinned to its canonical Owner, toolkit and assigned account, with Composio connection management and sandbox disabled. The job persists native session IDs beside its prepared run and receipt and resumes those sessions after reconstruction. Pi discovers deferred actions through native CodeMode search and description helpers; the actions are callable by CodeMode only. Composio owns both the session response envelope and action data schemas. Pi declarations must compose the native session envelope with the catalog’s resolved data schema for successful calls, retaining native error responses and opaque data where Composio declares no data schema. Composio execution stays in the trusted Worker and preserves the full native session response, including `{data, error, logId}`; the Linux computer receives no Composio credentials. Loader/action Tools retain their existing authorization, billing and scoped session path. Job billing requires a separately agreed implementation.

Job creation must return HTTP 202 with `{job, receipt}` and a `Location` pointing to the job resource. The job is a native `RoutedAgentEntry` with immutable metadata containing the prepared actor and trusted trigger: `{type: "api"}` or `{type: "schedule", scheduleId, schedule}`. Scheduled provenance carries both the native runtime ID and authored schedule name, preserving source identity across reprovisioning. The receipt retains native Pi `{operationId, session, accepted}`. Pi generates its operation ID independently of the routed job ID; the job persists that receipt and uses its operation and session identifiers for operation inspection, waiting, and abortion. Callers supply only the prompt, never a conversation ID, physical object name, actor or provenance. Each root session may have the local string `"1"`; job identity and session together identify the conversation.

Catalog and execution are separate resources. `GET /api/slates/{target}/agents/{name}/jobs/{id}` returns the native catalog entry; `/operation` returns native pending `{operationId, session, status: queued | running}` or settled `{operationId, session, status: done | unanswered, reason?, text?}` records, and `/result` awaits native settlement. These responses exclude the transcript. Catalog listing returns `{jobs: [...]}` for the app actor and verified caller's user actor, ordered by creation time descending and ID descending for ties. `?schedule=<authored-name>` selects catalog provenance without loading execution. Listing and catalog detail must not wake jobs or copy their execution state into metadata; native `createdAt` and `updatedAt` describe catalog changes in milliseconds. Authorized scope selection and the native `RoutedAgents` mapping locate each job through RPC, with no public physical address or second address table. The stable Agent returns the native job stub to trusted domain operations, which invoke execution methods directly and dispose the handle when finished. The parent owns catalog admission, schedules and deletion; it must not mirror the job's execution API. Job capabilities remain server-side, with authorization preceding resolution.

Rich inspection must use the same source-management authority as authored instructions because messages and native task payloads may reveal source, tool arguments, and results. Under each job, `GET /sessions` exposes native Pi session information, `/sessions/{session}/messages` exposes active `EntryRecord` transcripts, `/usage` exposes native model/tool usage summed across conversations, and `/inspection` exposes native scheduling, unfinished tasks, and queued or placed submissions. Inspection is a live-work view, not a completed-task history. Preserve native identity fields, model message content, context edits, task checkpoints, diagnostics, and extension-defined payloads without translating them into a second application execution model. Boundary schemas may validate native envelopes while treating nested native payloads as opaque; they must retain those fields. Missing jobs or sessions return HTTP 404. These reads neither create conversations nor submit further input, and ordinary operation/results remain transcript-free.

Job lifecycle mutations require the same slate-management authority as authored source inspection. `DELETE /jobs/{id}/operation` delegates to native Pi abort and returns its boolean as HTTP 200, retaining the job and its execution records; a native `false` is not a missing-job response. `DELETE /jobs/{id}` delegates catalog and independent-object deletion to `RoutedAgents` and returns HTTP 204 on success. Missing catalog entries return HTTP 404. Deletion follows the native lifecycle without a separate pending-state restriction.

Schedule inspection requires source-management authority because native schedule payloads contain authored prompts. `GET /api/slates/{target}/agents/{name}/schedules` returns the native `Schedule<ScheduledAgentRun>[]` for the app and verified caller's user scopes; `/schedules/{scheduleId}` returns one native record. Only authored callbacks belong in these responses. Native fields, including `time` in Unix seconds, retain their meanings. Git owns schedule authoring; these inspection routes do not introduce another schedule configuration store.

Schedule provisioning extends the existing Artifacts push → native CIWorkflow build → slate deployment flow through a trusted build-to-platform service binding. After deployment succeeds, the callback passes only slate identity. Deployment and membership creation share one provisioning operation: after deployment, provisioning refreshes the app and existing members, while membership creation provisions the verified person. It consumes one coherent declaration snapshot, provisions owner-mode databases for the app actor and viewer-mode databases for supplied members, and passes that same snapshot to schedule provisioning. Provisioning derives each agent's unattended scope from its own Resources and reads schedule files from the shared reader's immutable agent trees; the event's build commit does not select declarations. Schedule payloads carry slate and agent identity, explicit run actor, schedule name, and user prompt. Each firing prepares execution for that actor from the latest coherent snapshot, as API jobs do. Authored schedules live at `agents/<name>/schedules/<prompt>.md`: YAML frontmatter declares canonical five-field UTC cron, and the Markdown body is the scheduled user prompt. The Agents SDK owns parsing and persistent cron recurrence; Cloudflare Durable Object alarms wake the named instance. The callback uses the same execution and result primitives as API jobs. Provisioning replaces authored schedules on the selected actor instances and cancels authored schedules on instances outside the derived scope, preserving framework-owned lifecycle work. When preparation reports `agent-definition-missing`, the instance cancels its own authored schedules at the next firing; missing connection assignments and transient failures still fail without cancellation. Existing job listing discovers app jobs and the authenticated caller's user jobs; ordinary job operation/result access retains private-slate viewing authorization independently of membership.

Local execution belongs to the CLI's `packages/cli/agents.ts`. From the checkout root, `ctx agent local run <name> <prompt>` reads that checkout's `agents/<name>/instructions.md` and invokes Claude Agent SDK with the checkout root as its working directory. The command owns native Vite startup for the slate’s local resource Worker, and Wrangler’s external service-binding proxy supplies the same prepared local database state to the agent’s SDK MCP database_query tool. The native `claude_code` system preset supplies runtime instructions; its appended text contains platform instructions followed by the authored file. The task is a separate SDK `prompt`. Explicit `settingSources: []` disables automatic user/project settings and CLAUDE.md loading, while native managed policies still apply. The command prints the successful final result and surfaces SDK failures. It uses native Claude authentication and does not use hosted database state. The SDK is loaded only for agent execution and remains an external runtime dependency so its matching Claude executable can resolve normally.

### Slate membership and unattended execution

Slate membership must supply the people whose personal resources have been provisioned; [the domain model](#domain-model) owns its vocabulary. Membership and unattended execution must remain separate concepts: membership supplies people, while each agent's own requirements determine its unattended execution scope. A slate may have members with no unattended agents, only app-scoped agents, or a mixture. Agent requirement changes must not change membership.

Membership creation must require a committed declaration snapshot whose full app-and-agent configuration resolves without unassigned connections or missing viewer-mode secrets. Saving a declared connection assignment, supplying a declared secret through the slate-aware operation, and first use requiring viewer-mode resources must all attempt membership through that same domain owner and pure configuration resolver. An intermediate assignment or secret save must remain successful when another input is missing. Owner-only requests must resolve their own inputs without creating membership or depending on unrelated personal setup. Creation must not automatically establish membership for the creator. Existing membership must survive later missing configuration; each request must report missing inputs from its own requirements. Membership must enable unattended participation without a separate opt-in and must grant neither viewing nor source-management authority.

Platform must store membership in `slate_member`, keyed by `(slate_id, user_id)` with a cascading slate foreign key and web-owned user ID. One membership operation must own completeness checking, insertion and initial provisioning. The membership record must not become committed until initial provisioning completes. Only a newly established relationship may install initial personal databases and schedules; repeated use or configuration saves must not reinstall them. Deployment must independently provision the app actor and existing members. Membership creation must not submit a job, and public slates must never acquire membership. No explicit join HTTP route or CLI command may bypass completed setup.

An agent requiring any `viewer` resource must be member-scoped for unattended execution. An agent requiring zero `viewer` resources must be app-scoped. This derivation must consider all actor-dependent requirements, including connections, secrets, and databases. Unattended scope must be derived from requirements rather than independently configured or stored as a separate execution-target setting.

| Concept | Meaning |
| --- | --- |
| Unattended scope | Derived from the agent's requirements: `app` or `member`. |
| Run actor | The concrete app or slate member that one run acts for. |
| Resource mode | `owner` selects the slate's owning user or organization; `viewer` selects the acting member's personal Owner. |

App-scoped unattended execution must run once for the app, with the app itself as actor and no acting person or invented system user. Member-scoped unattended execution must run for slate members, with each run acting for a particular member. Stored slate membership must supply the actors for member-scoped execution and must carry no agent scope setting. Membership determines who participates; the agent's requirements determine its unattended scope.

Hosted resource ownership must remain orthogonal to unattended execution scope. Hosted resource resolution must select the slate's owning user or organization for `owner` mode and the acting member's personal Owner for `viewer` mode. A member-scoped agent may read a member's Gmail, use the organization's model credential, and write to that member's slate-specific priorities database. An app-scoped run has no member against whom a `viewer` resource could resolve; deriving scope from requirements excludes that incompatible combination.

The derivation must use the agent's own requirements, independently of the app's requirements. The app may use `viewer` resources while its unattended agent requires only `owner` resources and runs once for the app. Unattended scope must not determine interactive app identity or redefine manually requested job behavior.

```text
Agent requirements → unattended scope
  app    → one run acting for the app
  member → slate membership supplies members → runs acting for particular members

Run actor + resource declaration → selected resource
```

### Authored MCP tools and Views

An authored MCP tool lives in `mcp/<name>/index.ts` with its own `slate.json`. MCP Views live separately in `mcp-ui/<name>/index.html`, with React entries using MCP Apps' host bridge. A tool's `_meta.ui.resourceUri` identifies its View, so several tools can reference the same resource. After platform’s slate resolution succeeds, `/mcp` is served by the dispatcher’s native MCP SDK handler. Discovery and resource reads use generated assets without forwarding caller credentials. Each tool call becomes a fresh JSON request into the authored Worker with a trusted `mcpTool` selector in native props; the Worker validates its arguments and invokes the authored handler. The dispatcher validates the native tool result and schedules one `tool_call` usage event through the shared metering operation. MCP discovery and resource reads bypass ordinary HTTP response classification. Authorization, canonical slate/Owner selection, subscription gating, and metering remain trusted-service concerns.

The View receives inputs and results and requests tool calls through the host's MCP Apps bridge. It does not receive ContextLayer credentials or fetch the slate's cookie-gated web routes. Serving its self-contained HTML as an authenticated MCP resource keeps rendering separate from slate-origin navigation.

### Cross-site chrome authentication — principles

The chrome must run in an iframe on a trusted origin: `platform.usecontextlayer.com`, `frame.usecontextlayer.com`, or `usecontextlayer.com`, isolated from the authored parent. Private slate entry should leave the chrome authenticated as the same viewer automatically, without an additional popup sign-in step. The chrome iframe's session flow must work across the site boundary to `contextlayer.xyz` while preserving isolation from the authored parent.

Better Auth should own identity verification and session revocation. The chrome's iframe should authenticate directly with the native web session, and web logout must invalidate its authentication. Native session cookies must use Secure, HttpOnly, and SameSite=None in every environment. Credentials must remain in trusted documents and services; the authored parent must receive neither credentials nor profile/connection data. Frame forms must submit to the trusted platform origin while permitting the native provider authorization redirects. Cookie-authenticated form mutations must reject cross-site submissions through the framework's native CSRF protection. Better Auth's origin checks must remain enabled, and authored origins must not gain credentialed CORS access to web or platform.

### Viewer sign-in boundary — principles

Web's Better Auth should own the user's identity and web session, and auth should own viewer sign-in on the user-code domain. Viewer sign-in must identify the same user without copying a reusable web session credential into the authored-slate domain. Viewer authority must be limited to viewing and explicitly delegated slate runtime operations and must not authenticate web/platform management requests.

Dispatcher should ask platform for that decision and supply only slate/viewer-bound capabilities to authored code. Private viewing and declaration retrieval must preserve the security boundary above: authentication must stay in trusted services, and authored requests, responses, and redirects must not expose management credentials or control viewer-session changes.

## Key contract: slate resource requirements

The author owns `<CHECKOUT>/public/slate.json`, served at `/slate.json` by the framework's native static-asset handling. It declares the interactive app's resource requirements; `agents/{name}/slate.json` declares each agent's requirements using exactly the same shared schema. Vite serves the slate's local file during development and includes it in the production assets, so each deployment carries its own requirements. Do not add a custom resource route, a copied root declaration, or a separate requirements store.

The declaration contains a `connections` object keyed by the slug used in `tools.call(slug, toolSlug, args)`. Each connection declares its Composio `toolkit` and `mode` (`viewer` or `owner`). The `databases` object is keyed by slug and `secrets` by name; both declare the same modes. `connections` is required, even when empty; omitted `databases` and `secrets` default to empty maps. A database slug must name one directory segment for its authored migration location, excluding slashes, backslashes, `.` and `..`; the shared Declaration/Resources contract must own this validation for both local and hosted configuration. In hosted execution, `viewer` selects the acting user’s personal Owner and `owner` selects the slate’s owning user or organization. Local development retains those authored modes for hosted execution but uses the developer-local sources defined above. New slates start with empty `connections` and `secrets` objects. `@usecontextlayer/shared/declaration` owns the Zod declaration contract and mode vocabulary; CLI, SDK, and platform use it. For example:

```json
{
  "connections": {
    "work-email": {
      "toolkit": "gmail",
      "mode": "viewer"
    }
  }
}
```

Resource keys form one slate-wide namespace per resource kind across consumer declarations. Shared `collectSlateResources` accepts `{ app: Declaration, agents: Record<string, Declaration> }` and returns the explicit `Resources` type: the same maps as `Declaration`, with `connections` and `databases` keyed by slug and `secrets` keyed by name, plus consumer metadata on each requirement. Repeated connection requirements must agree on mode and toolkit; repeated database and secret requirements must agree on mode. Conflicts raise validation errors, with no file precedence or inheritance. The pure `resourcesForConsumer(resources, consumer)` function returns a filtered `Resources` value for `{ type: "app" }` or `{ type: "agent", name }`, retaining requirement and consumer metadata without reading files or applying overrides. Configuration uses the full collection and execution uses this selector; authored declarations remain unmodified. Database requirements declare ownership selection; concrete instance configuration and SQL access belong to resource resolution.

Platform's `readSlateDeclarations` owns the repository declaration boundary. It uses the native Artifacts binding and a disposable repository handle, resolves `main` once, discovers agent directories through that commit's Git trees, and reads `public/slate.json` plus each `agents/{name}/slate.json` using the resolved commit hash. Each file passes through the same shared declaration schema before collection. The result contains the commit, discovered agent tree references, original consumer declarations and collected resources; the hash establishes a coherent read rather than a deployment pointer. Provisioning alone reads each collected database slug’s native migration bundle at that commit and shares it across member instances. The reader accepts no caller credentials, resolves no connection assignments, database references, or secret values, and creates no instances or jobs. Hosted declaration selection must always use this reader rather than caller-supplied Resources. Downstream operations receive plain Resources: configuration uses the complete collection and execution selects its consumer through `resourcesForConsumer`. The immutable commit stays in the repository reader's result for instruction and provisioning coherence; configuration consumers need no source or commit flag.

Local tooling reads every app and agent declaration in the current checkout and collects Resources locally. Callers inspecting a running slate can fetch its static `/slate.json` under viewing authorization, but that deployed asset must not become a second authoritative hosted declaration source. Hosted operations select requirements from the coherent repository snapshot. ## OAuth resources and scopes

An OAuth **resource** identifies the API a token is intended for. A **scope** names a permission within that API. The resource answers “where may this token be used?”; the scope answers “what access was granted?” Better Auth owns these concepts: a resource's `identifier` is requested through the OAuth `resource` parameter and becomes the token's `aud` claim; its `allowedScopes` lists the permissions it permits.

| API | Canonical resource identifier / token audience | Access scope |
| --- | --- | --- |
| Platform | `https://platform.usecontextlayer.com` in every environment | `platform:access` |
| A slate's MCP server | Its canonical `https://<slate-hostname>/mcp` URL | `mcp:access` |

Use one canonical URI spelling consistently in registration, authorization requests, discovery and verification. Platform has one logical resource identifier across development, tests and production, independent of its network address. Local environments use their own web issuer and signing keys; signature and issuer verification keep their tokens separate from production. Scope names stay the same across environments and slates; the audience identifies the intended API. `offline_access` keeps its standard meaning for refresh-token issuance. These two access scopes express the existing permissions; finer-grained permissions require a product requirement.

The issuer identifies web's authorization server; the resource identifies the protected API; the client ID identifies the requesting application. Keep those facts distinct. Web's platform profile and membership reads participate in the same logical platform resource even though web serves those endpoints. Resource identity does not change to the address of whichever process performs verification. Service URLs, bound ports and Worker bindings are connection facts. `CTX_PLATFORM_URL` selects where to send platform requests; it never defines the OAuth resource. Keep the platform resource constant in the protocol configuration. Derive each MCP resource from the stored slate hostname according to MCP’s canonical-server-URI rules. Request Host and forwarded headers do not define token authority.

Development startup must publish the initialized connection facts it owns: the four service URLs and public CLI client ID in the checkout’s ignored `.env.json`. Connected commands and test fixtures must consume that same record through shared typed composition, deriving the issuer and checkout-local credential directory without repeating provider discovery. Shell exports and subprocess environments are output boundaries over those same settings. The record must contain public connection facts, while saved OAuth credentials remain in the selected login directory. Startup reuses the complete saved port set when all ports are free and assigns an entirely new set when any is occupied.

Composition must retain rich connection values until serialization at each package’s `env.ts` boundary. Full service addresses use `_URL`; `_HOST` is reserved for a hostname and optional port without a scheme. Preserve upstream names such as `BETTER_AUTH_URL`. Public webhook ingress may differ from the local service address. There is no global environment registry, fixed hostname scheme, or environment-variable setting for the platform OAuth resource.

Verify signature, issuer, expiry, subject, audience and required scope before applying existing ownership, membership and billing policy. A slate token cannot gain platform authority from a shared user ID or the generic word “access.” A common `mcp:access` scope works across slates because their audiences differ. Preserve verified authority in the identity passed to authorization. This OAuth use of “resource” names a protected API; it is distinct from an MCP content resource or a declared connection, database, or secret.

These conventions follow [OAuth resource indicators](https://www.rfc-editor.org/rfc/rfc8707.html#section-2), [OAuth scope semantics](https://www.rfc-editor.org/rfc/rfc6749.html#section-3.3), [Better Auth's resource model](https://better-auth.com/docs/plugins/oauth-provider#resources), and [MCP's canonical server URI](https://modelcontextprotocol.io/specification/latest/basic/authorization#canonical-server-uri). Registration and migration procedure belongs in [DEVELOPING.md](DEVELOPING.md#oauth-registration-and-migration).

## Owner-scoped connection assignment storage

`slate_connection_assignment` stores assignments using `(slate_id, owner_type, owner_id, slug)` as its composite primary key. `slate_id` is a UUID foreign key to `slate.id` with `ON DELETE CASCADE`; the other columns and `connection_id` are non-null text. `owner_type` is `personal` or `organization`, matching the canonical `Owner`. `slug` is the declared connection slug and `connection_id` is Composio’s connected-account ID. Toolkit and mode remain in the declaration. Package-owned migrations define the slate schema directly and enforce the canonical Owner kinds; Kanel generates the resulting types.

After persistence, API and chrome must share the same membership attempt and partial-save behavior defined by the [membership rule](#slate-membership-and-unattended-execution). Public viewing alone must grant no Owner-management authority. Development assignment must save only ignored local assignments and must never change hosted assignments, even when the developer is also a hosted viewer or slate Owner. Connecting an account at the provider must remain independent of assigning its connection ID.

The hosted assignment key identifies slate, Owner, and resource; local development must remain isolated through its separate local assignment storage rather than introducing an environment dimension into hosted assignments.

### Platform tool execution

The platform’s `Execution.callTool` method accepts the canonical SlateID, viewer session token, and hosted `{slug, tool, arguments}` call through the dispatcher’s service binding, without caller-supplied resource declarations. Its separate `queryDatabase` method accepts the same slate/viewer identity and a declared slug, SQL and parameters. These operations have no public HTTP execution routes. Cloudflare’s binding supplies authority to invoke them; Better Auth verifies viewer identity from the session token. Both methods enforce slate viewing and billing access before domain execution. The shared `HostedExecution` binding contract carries typed `allowed`, `result`, and `reason` outcomes. Execution must resolve only the request's inputs and require personal provisioning under the [membership rule](#slate-membership-and-unattended-execution) exactly when viewer-mode resources are requested. An undeclared slug returns `not-declared`. App actors and public viewers requiring viewer resources receive `forbidden`, independently of stored membership. Resource inventory and credential configuration retain their existing authorization and remain available before membership is established. The hosted Tools and Databases capabilities throw ordinary `Error` objects for `forbidden` and `not-declared`. A missing connection assignment returns `connection-required` with its slug, and an absent viewer-mode secret returns `secret-required` with its name; both use native HTTP 409 Responses described below; billing refusal preserves the shared billing message. App loaders/actions govern what a viewer may do through these capabilities because calls must pass through app code. Platform reads the coherent pushed Resources, selects the app’s requirements, resolves the canonical Owner and hosted assignment, and invokes native Composio execution through shared `createConnectionSession`. The toolkit must always come from the selected validated declaration, never inferred from the saved account ID. The helper creates the Owner-scoped session used by delegated execution, personal-account HTTP execution and hosted-agent tools and preserves Composio’s `{data, error, logId}` response. Ordinary hosted viewers can execute a hosted owner-mode requirement through the slate viewing boundary without acquiring permission to manage that Owner’s connected accounts or its vault. Viewer-mode execution remains scoped to that slate member’s accounts. The Composio project key remains on platform. Hosted runtime authority is explicitly delegated to the canonical slate and viewer; a viewer credential grants no general API access. Local execution instead resolves its declaration and assignment locally and uses independently authorized personal-account execution.

Local loader integration uses the development-only Vite startup helper and auxiliary Worker. Trusted CLI construction must assemble checkout configuration before selecting the app’s requirements with `resourcesForConsumer`. Only selected connection inputs, canonical slate context, and the CLI credential belong in local Tools props; unrelated secret values, database inputs, and agent-only connections must not enter this capability. LocalTools and hosted Tools must be separate typed Worker entrypoints: local calls resolve account ID/toolkit from their trusted startup inputs and use personal concrete-account execution, while hosted calls use viewer-session delegation to the hosted slug operation. They must share result/error semantics without accepting an optional declaration or interpreting a caller-supplied environment flag. Its access token is a startup snapshot; no continuously refreshing local authentication service is involved. Native Vite development detection must disable chrome locally, and local startup metadata must never become browser configuration.

A declared connection without an account assignment must be reported as `connection-required` with its slug, distinct from an undeclared resource (`not-declared`). A missing viewer-mode secret must be reported as `secret-required` with its name. Shared Zod schemas must own these safe payloads. Hosted Tools and Databases must preserve them as native HTTP 409 Responses over Cloudflare RPC, and SDK adapters must throw them in the authored app so its route error boundary can handle setup guidance. Authored error handling must preserve these Responses through any intervening data-access layer. The documented Drizzle helper currently wraps query failures in its own error, so its hosted database queries produce a generic route error instead of setup guidance; direct database queries preserve the native Responses. Local Tools must use the same connection-refusal contract for missing startup assignments. Missing setup must stop before provider execution or tool usage recording; unrelated failures must remain exceptions. Successful tool calls must retain `{ data, logId }`. Account catalogs and credentials must stay in their trusted owners.

## Slate-Owner billing access

Web’s native Better Auth/Polar integration owns individual and team customer creation, checkout, and billing management. Platform handles signed `customer.created` and `customer.state_changed` events at `POST /api/polar/webhooks`, verified by Polar’s SDK using `POLAR_WEBHOOK_SECRET`. A newly created customer with an external ID receives a native subscription to `POLAR_FREE_PRODUCT_ID`. Polar owns subscription lifecycle, credit fulfillment, and renewal; its state-change event supplies the resulting entitlement. `polar_customer_state` is a bounded-staleness copy of Polar’s complete native Customer State, keyed by Polar customer UUID with a unique nullable `external_id`. The webhook and billing gate share `saveCustomerState`; the database stamps `refreshed_at` on insert and conflict update, independently of webhook event timestamps or customer modification dates. That external ID matches `slate.owner_user_id` or `slate.owner_organization_id`. Polar’s merchant `organization_id` is unrelated to our organization ownership. Kanel generates the JSON column with the native SDK Customer State type.

Identity and viewing authorization precede the single shared `checkSlateBilling` decision. Hostname resolution, delegated tool/database execution, and local personal-account execution reuse it with the canonical slate Owner. The gate pulls Customer State by the Owner’s external ID on a missing row or when `refreshed_at` is older than one hour, saves it, and evaluates the saved state. Polar not-found leaves no new row and refuses with `subscription-required`; customer creation remains web’s responsibility, and other Polar failures surface. Any saved active subscription outside the configured Free product admits. Free requires a positive saved balance on the configured `POLAR_CLIPS_METER_ID`. Meter balance movement does not trigger a state-change webhook, so an exhausted Free Owner may remain admitted for up to the hour. Product and meter IDs identify environment-specific Polar resources; credits and allowance amounts are not copied into platform policy. No active subscription and exhausted Free balance return nonempty HTTP 402 messages. Exhaustion includes the subscription renewal date and an existing web billing destination: personal billing for a personal Owner, or the organization chooser for an organization Owner. Web owns organization membership and slug navigation. Its existing adapter routes already subscribed customers to Polar’s native portal, which owns paid plan changes and payment details.

The billing boundary retains its existing scope before runtime dispatch, including hosted assets and MCP discovery/resources. Dispatcher forwards the actual incoming pathname; exactly `/slate.json` retains viewing authorization while skipping billing. Local Tools uses the personal concrete-account operation with separate credential authority and preserves the platform billing message. Local page rendering itself does not go through hosted dispatch. Slate creation/listing, dashboard, Git, connection configuration, and billing management remain available. The configured Free product must have a zero fixed price and no metered price, so exhaustion cannot create overage charges, with its recurring credit benefit granting the allowance. Polar owns the only balance ledger. Paid plans retain their existing overage policy. Usage reporting is asynchronous after execution, so a positive-balance admission check does not reserve clips or establish an exact operation ceiling.

Usage metering follows execution: dispatcher records recognised dynamic GETs (1 clip) and POST/PUT/PATCH/DELETE requests (3 clips), while delegated execution and the personal-account tool API record returned tool executions (1 clip). The shared `slate-usage` module converts the canonical `{ id, owner }` and event name into native Polar ingestion, with `metadata.clips` and `metadata.user_code_worker_id`. Resolution supplies its Owner through the shared Zod contract; platform converts its loaded slate through `getSlateOwner`. Both boundaries use native `waitUntil` and return without awaiting Polar. Best-effort classification for these methods recognises HTML, JSON (including application `+json`), React Router `text/x-script`, plain text, CSV, XML, NDJSON, event streams and redirects. JavaScript, CSS, image, font and WebAssembly responses and exact `/slate.json` produce no usage events. Response headers are controlled by the authored Worker, so this is the user-approved normal-traffic heuristic, not an unbypassable distinction between static and dynamic responses. No SDK-side reporting or route instrumentation is required; rates and canonical Owner attribution stay in trusted Workers. Polar’s existing Clips meter aggregates all three event types and owns allowances and prices.
