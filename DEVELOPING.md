# Developing

This workspace contains nine packages: the public `@usecontextlayer/cli` and `@usecontextlayer/sdk` plus seven private packages, including the platform application and viewer auth Worker. Use the root package scripts and Turbo for libraries and applications. Main pushes run checks; version-tag pushes publish npm packages.

## Setup

Run from the repository root:

```sh
mise trust
mise install
pnpm install --frozen-lockfile
```

The root `.node-version` pins Node for Cloudflare builds, local development, and GitHub Actions. `mise.toml` reads that file and provides Node and pnpm; the pnpm version must match `package.json`. Corepack stays unused. `pnpm-workspace.yaml` enforces the Node version floor and disables automatic dependency repair during task execution, so install dependencies explicitly before running tasks.

## Workspace commands

```sh
pnpm run check
pnpm run format.verify
pnpm run tsc
pnpm test
pnpm run build
```

`check` runs workspace-reference and Tailwind checks, fixes formatting, and typechecks. `format.verify` checks without editing files. The Tailwind checker discovers stylesheet entry points across `packages/`; it reports explicitly when there are no Tailwind stylesheets to scan.

For package-scoped work, use Turbo selectors:

```sh
pnpm exec turbo run build tsc --filter=@usecontextlayer/shared...
pnpm exec turbo run test --filter=@usecontextlayer/shared...
pnpm exec turbo run dev:watch --filter=@usecontextlayer/db-infra...
```

A library carries `dev:watch` for rebuilding its output. The general task convention remains: a server's `dev` starts it, `dev:watch` adds watching, and a package defines only the forms it actually uses. Turbo owns dependency builds through `^build`.

## Building platform capabilities

Design almost every capability offered by the web dashboard as an OpenAPI operation usable by the CLI and a future MCP consumer. Define its Zod input/output contract and shared domain function, including authorization and database calls; connect the API handler and React Router loader/action to that same function. Loaders/actions call it in-process. Verify the product operation through its existing API or CLI path and verify the browser interaction where needed. Browser presentation belongs in the UI; authentication protocol handling belongs to Better Auth.

## CLI development

The new `ctx login` / `ctx whoami` flow requires web with its OAuth device extension migrated and a public CLI client registered for the `urn:ctx:platform` resource. `CTX_AUTH_ISSUER` defaults to `https://www.usecontextlayer.com/api/auth` in CLI and platform; `CTX_AUTH_CLIENT_ID` defaults to the registered production public client ID in the CLI. Configure both CLI and platform with the same issuer for local testing, and point `CTX_PLATFORM_URL` at that platform. Only localhost/127.0.0.1 issuers permit HTTP in the CLI. Credentials are written to `~/.contextlayer/auth.json` with owner-only permissions on creation. Local and production end-to-end login and authenticated `whoami` passed. Production web is migrated, the public client is registered, and platform verifies its tokens. The CLI targets production by default; set `CTX_PLATFORM_URL=http://localhost:3010` to use the local platform. CLI authentication is included in npm releases starting with 0.12.0.
Build the local `ctx` executable, then invoke the built executable from the repository root:

```sh
pnpm exec turbo run build --filter=@usecontextlayer/cli
pnpm ctx --version
pnpm ctx init my-react-router-app
```

Run the built CLI's `ctx login` once to register its credential helper for this OS user, including when you already have a saved login from an earlier version. Registration points Git at the executable used for login; run login again if that installation moves. Git needs native `authtype` credential support (the development machine's Git 2.55.0 advertises it). Login and init must target the same platform URL so Git's registered URL scope matches the remote.

Create test projects outside this checkout. The pnpm executable must also work from the generated project's directory; a machine-wide mise default supplies it outside repo-local tool configuration, without `mise exec` or a CLI workaround.

## Platform viewer authentication

Platform's general APIs, Git, and dashboard accept CLI access tokens in Authorization: Bearer or native Better Auth web cookies. Only non-MCP GET /api/apps/resolve requests, POST /api/apps/:target/tools/call and POST /api/apps/:target/databases/query additionally accept ctx-viewer-auth. Resolution with pathname=/mcp requires an app-bound bearer token with ctx:mcp; viewer and native web cookies do not authenticate MCP. Web's /api/me and /api/platform/organizations reject the viewer cookie. Runtime viewer authentication still checks the copied session through web's /api/auth/get-session using the bearer plugin; no token format, sign-in, or logout mechanism changed. Explicit bearer credentials take precedence. Private-organization viewing sends the viewer cookie to web’s dedicated GET /api/viewer/organizations/:organizationId/membership endpoint. Web validates the existing session and returns {isMember}; platform applies its own viewing policy. Native web and CLI membership reads retain /api/platform/organizations.

For native browser session development, run web at `http://localhost:3000`, set `CTX_AUTH_ISSUER=http://localhost:3000/api/auth` in Doppler `platform/dev`, and open platform at `http://localhost:3030/dashboard/personal/apps` after starting its Vite server on port 3030. Use localhost for both browser URLs: cookies are shared across ports, but localhost and 127.0.0.1 are different cookie hosts. Sign into web normally, then open platform. These cookies are verified against local web, so CLI credentials must come from that same issuer for an identity comparison. Restoring the production issuer resumes production CLI/viewer checks. Production web shares its native cookie across `usecontextlayer.com` using Better Auth’s `crossSubDomainCookies` configuration.

Signed-out browser navigation to the dashboard redirects to web's existing sign-in page with the original dashboard URL in `redirectTo`. The existing social sign-in UI forwards it to Better Auth's `callbackURL`; local web already trusts localhost ports. Dashboard fetch/data requests retain 401 through native `Accept` negotiation, and API/Git routes always retain 401. To check the redirect with curl, send `Accept: text/html`; curl's default wildcard header receives 401. Web explicitly trusts `https://slate.usecontextlayer.com` as a production sign-in callback origin; no additional secret or schema migration is required.

For local identity verification, run ctx whoami against the matching web issuer; native web cookies and CLI tokens should authenticate /api/me, while a viewer cookie should return 401 on both web profile and organization endpoints. Platform should accept that viewer cookie for private personal app resolution and delegated tool/database authentication, and reject it on general APIs. The auth.node.integration.test.ts check exercises these platform boundaries over HTTP through the production-build Wrangler harness, with real Better Auth sessions and an isolated local Postgres database. Build platform first, then run pnpm exec turbo run test:integration:node --filter=@usecontextlayer/platform -- auth.node.integration.test.ts. Docker must be available for the native Worker configuration. This suite creates both identities through Better Auth and performs no external provider calls.

Browser form fixtures must send the same-origin Origin or Sec-Fetch-Site metadata that browsers supply. JSON fixtures must carry application/json. Platform applies Hono's native CSRF checks after verification for cookie/session form requests; verified bearer calls, including bodyless CLI join requests, need no browser origin headers. Anonymous protected calls retain the authentication boundary's 401 response.

The MCP checks run the real built platform and dispatcher through the committed Wrangler `test` environments and prebuilt production bundles, with an isolated local database and Better Auth signing service. Build platform and dispatcher first with `pnpm exec turbo run build --filter=@usecontextlayer/platform --filter=@usecontextlayer/dispatcher`. The authentication-only case verifies metadata, cookie-only challenges, app-bound identity through private viewing to the subscription gate, cross-app/management rejection, and ordinary browser viewing. Run `pnpm exec turbo run test:integration:node --filter=@usecontextlayer/platform -- mcp.node.integration.test.ts --testNamePattern 'bind MCP'`; this case performs no authored tool invocation or provider usage write. Wrangler authentication is required for the native remote bindings. Web’s separate native-provider integration test verifies Claude CIMD discovery, signed consent, PKCE issuance and refreshed app tokens.

The complete MCP file additionally builds an authored echo app through the production SDK and React Router, deploys its UUID-named Worker to `contextlayer-test`, and drives discovery, View reads and tool invocation through a native MCP Client. It needs sandbox `POLAR_ACCESS_TOKEN`, `POLAR_ENVIRONMENT=sandbox`, and an active `CTX_TEST_POLAR_USER_SUBSCRIPTION_ID`. The native subscription/customer APIs supply the app Owner and billing fixture; no provider customer or subscription is created. **Obtain explicit permission before each run:** one successful echo call writes one immutable `tool_call` usage event of one clip to that subscription’s customer, tagged with the test’s new AppID. Discovery, resource reads and rejected invalid arguments must produce no additional usage. After that permission, run `doppler run -p platform -c dev -- pnpm exec turbo run test:integration:node --filter=@usecontextlayer/platform --force -- mcp.node.integration.test.ts`. The suite removes its own deployed Worker and drops its own database and temporary build directory. These checks are local-only integration coverage.

## App ownership

Run `ctx login` before `ctx init`. Initialization reads the saved login before scaffolding and authenticates `POST /api/apps`. The platform resolves an optional `organization_slug` from the JSON body against web’s organization records for the verified caller; a match creates an app with that organization ID and `owner_user_id` null. A slug outside those memberships returns 404 before any database or Artifacts write. Omitting it records the verified user as `owner_user_id`, with `owner_organization_id` null. See `ctx init --help` for organization selection. Migration 003 adds both nullable text columns and PostgreSQL's `app_exactly_one_owner` check: exactly one column must be non-null. Domain creation owns selection of the typed user-or-organization owner. Git source access and app listing enforce the owner/member management rule. Viewing authorization applies to hostname resolution and app connection/tool APIs. Users and organizations remain in web's Better Auth database.

Migration 003 requires every existing app to have an owner. Resolve existing rows before running it; there is no automatic backfill or deletion in the migration. Production migrations run separately from the main-push deployment pipeline.

Migration 004 adds non-null text `app.visibility` and backfills existing apps to `private`. App creation explicitly supplies the private default from the code constant `DEFAULT_APP_VISIBILITY`; the database has no visibility check or persistent default. Zod validates the public/private values when app rows are returned. Apply migration 004 before running this version against an existing database. Main pushes deploy the matching Worker code through the existing Cloudflare Workers Builds pipeline. Platform hostname resolution enforces public/private viewing and dispatcher consumes its decision for every app path. Every route in the `/apps/:target` operation group inherits required authentication and the same viewing authorization before its handler; connection listing, assignment, and tool execution take the resulting app-and-caller `AppAccess` input; Git source access and management listing enforce ownership independent of visibility. `PATCH /api/apps/{target}` accepts JSON visibility (`public` or `private`) and returns the saved app; the shared `updateAppVisibility` function requires its owner or an owning-organization member before writing. Public viewers cannot change visibility. This uses the existing column and requires no additional migration.

## Authored database development

ctx init installs the native Drizzle ORM/Kit versions and supplies a SQL-first db:migration script, template instructions and databases/updates example. Keep each database’s config, query schema and native migration output under databases/<name>. Declare its slug/mode in app or agent Slate. Run pnpm db:migration --config databases/<name>/drizzle.config.ts --name <change>, write the blank SQL explicitly, and update schema.ts for query types. Commit SQL and generated metadata together. Never run schema-diff generation or drizzle-kit push. Multiple statements use the native --> statement-breakpoint separator.

React Router loaders/actions can construct the native Drizzle query client with database(context.get(databasesContext), "updates", schema) from @usecontextlayer/sdk. The equivalent SQL capability is context.get(databasesContext).query("updates", sql, params). Local native startup applies current-checkout migrations; publication applies pending committed migrations for existing members; later joining applies full history. Querying and agent job preparation do not apply migrations. App data no longer uses Artifacts folders, Git pushes or document paths.
