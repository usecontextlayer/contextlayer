# PRODUCT-DEVELOPMENT-v1: why → what → how → fresh eyes → slices

Alignment before writing code is often significantly cheaper than alignment after writing code. This process buys that alignment in three brainstorm tracks — they are the heart of it.

1. **Invoke.** This process runs only when the user invokes it by name; the agent never self-invokes it. Outside an invocation this document imposes nothing — the agent does not propose invoking it; the user routes all work.

2. **Brainstorm in three tracks, in order.** Each track is a different question, run with `superpowers:brainstorming`'s conversational craft under the overrides in steps 3–4:
   - **WHY** — the user's motivation and success bar: what outcome they want, why it is worth building, and what would make it a failure even if it worked. Understood well enough to predict which framings the user will accept and which they will reject.
   - **WHAT** — the design decisions: scope, features, behavior, user experience. What gets built, and what deliberately doesn't.
   - **HOW** — the implementation shape: architecture, components, data flow, error handling, testing. Where each piece lives and how the data moves, agreed before any of it exists.

3. **The question protocol.** Questions are MCQ-shaped, written in prose — enumerated options are less mentally taxing on the user than open-ended questions — and asked ONE per turn, never via the AskUserQuestion tool. Every question carries the agent's recommendation (its taste) AND its prediction of the user's pick (its model of the user); divergence between the two is CRITICAL signal — it signifies that additional thinking must be done before the next question is asked. The agent adjusts that model after every answer. The user's final word in a message is the pick — intra-message oscillation is calibration data, never an invitation to re-ask. While a track is open the conversation stays inside it; a user note about another track banks that decision for its track without opening the track. The agent may propose opening the next track, but the user MUST ALWAYS ratify — no track opens without the user's explicit say.

4. **The gate, identical for every track.** A track locks only when the agent can predict the user's yes's and no's with an extremely high degree of empirical confidence — and "predict" means precise: the exact pick, not the direction. Anything that needs a user decision is its own question — bundling decisions into one message is NOT allowed (strict now; the user may loosen later). The gate's evidence is the track's accumulated prediction record; closing the track is itself a single question carrying nothing else.

5. **Write at lock.** The moment a track locks, its outcome is written into the spec document as its own section (one spec per run; `internal/in-progress/` for engine/multi-project work, `web/docs/in-progress/` for web work). A locked section records the user's picks and explicit no's, with distilled rationale, written for a reader who never saw the conversation — and with enough detail that such a reader not only understands it but cannot misunderstand it: every settled nuance is spelled out, because a nuance left implicit gets skipped or misread, and the reader's guess silently replaces the user's decision. One prohibition governs all spec writing: an agent proposal is NEVER written as a user decision — if the user hasn't picked, the spec says so.

6. **Fresh eyes.** After all three tracks lock, run the `fresh-eyes` skill once on the completed spec and resolve its findings with the user before any code exists. A resolution that adds or changes a decision is a change to locked content and fires step 9's cascade; a verbatim restoration of something the user actually said is record repair — applied and reported, no re-void.

7. **Implement iteratively.** One small vertical slice at a time in a faux worktree (always ask the user before creating one), check-ins between slices; NEVER write an implementation plan.

8. **Pause on judgment.** The moment a judgment, taste, or scope call appears, hand it to the user and wait; mechanical, obvious-scope calls are made and reported.

9. **Re-entry.** The gate is a three-party transitivity claim: the predict-gate measures agent ≈ user, and the locked model implicitly claims user ≈ reality — together they let agent ≈ reality stand. Implementation is when reality finally votes. A gap or contradiction is reality rejecting a lock — the chain is broken no matter how strong the agent↔user record was. So a discovery at ANY point — in a later track or during implementation — reopens the track it belongs to (tracks are hierarchical: WHY ⊃ WHAT ⊃ HOW), and the cascade always fires, with no size tiers and no agent judgment of materiality: the reopened track re-earns its gate, every downstream gate is void and re-earned — because even a small, innocuous WHAT change can dramatically transform HOW — and the fresh-eyes clearance voids with them, re-run or waive being the user's call. A reopened track is worked through the same question protocol (steps 3–4), and its answer is written into the spec's relevant section BEFORE any code proceeds. The rebuild is naturally proportional: a clean gap-fill can re-lock in a single question. Silent adaptation is never an option.

Steps 7–8 are the implementation methodology and remain open to refinement; the planning and re-entry rules (steps 1–6 and 9) are set.
