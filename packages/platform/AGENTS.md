# Platform

These instructions define the intended architecture and principles the platform should uphold. Requirements describe what must be true, not proof that every protection or feature is implemented. Keep implementation progress and temporary experiments in the planning documents.

## OpenAPI, Zod, and Shared Domain Functions

**Use OpenAPI for application APIs, Zod for validation, and one shared domain function for each operation's business logic and database calls. API handlers and server-side loaders/actions must call that same function.** Apply this shape even to a simple database query.

- **Schemas must own the contract.** Define API input and output schemas with Zod. Reuse them for validation, inferred TypeScript types, and generated OpenAPI documentation. Reuse the same input schema wherever callers accept the same untrusted input.
- **API handlers should own HTTP.** Parse and validate request inputs, call the domain function, and translate its result into an HTTP response. Keep business decisions and database queries in the shared function.
- **Loaders and actions should call the domain function directly.** React Router server loaders/actions should invoke it in-process, validate their untrusted inputs, and adapt its result to the framework's response conventions. Do not call our own API over HTTP or implement a second database path.
- **Domain functions must own the operation.** Accept typed, normalized arguments, enforce business rules, perform database reads/writes, and return typed results. Do not accept framework request/context objects or return HTTP responses.
- **Use ordinary functions grouped by domain.** One operation should have one implementation, regardless of its entry points. Do not add service classes, a generic repository layer, or a dependency-injection framework to express this boundary.

For example, `GET /api/apps` and the app-listing loader should both call `listApps(...)`. That function should own the query; the endpoint and loader should each adapt its result for their caller. OpenAPI and the shared operation should be part of the first implementation.

## App identity and storage

Platform should own the immutable `app.id` UUID and unique `app.public_hostname`, without a separate display name. The UUID should name the Artifacts repository and the `/git/<app-id>` address. Create apps during `ctx init`, not on first push. PostgreSQL must enforce exactly one of `owner_user_id` or `owner_organization_id` through `app_exactly_one_owner`. Those IDs must refer to web's Better Auth identities without duplicating their records in platform.

Normalize validated creation input and the verified caller into the canonical `Owner` union in `app/owner.ts` before writing. Creation, listing, connections, and secrets should share that ownership shape. Dashboard `OwnerDetails` should derive its variants from `Owner`, adding schema-derived organization name/slug metadata only for presentation. `POST /api/apps` must require authentication. An omitted `organization_slug` should select the verified user; a supplied slug must resolve against the caller's authoritative organization list before database or Artifacts writes. Return 404 for an unavailable organization. Callers must not choose another user as owner.

Use existing `db-infra` helpers, package-owned Kysely migrations, and Kanel-generated models. Never hand-edit generated models. Keep `verbatimModuleSyntax: false` for compatibility with Kanel's default Database type export. The server should own its database connection; migrations and Kanel generation should run through the package's Node database management commands.

Store `app.visibility` as non-null text, validate `public`/`private` through `appVisibilitySchema`, and use `DEFAULT_APP_VISIBILITY = "private"` for creation. Parse app rows through `appSchema` before returning app-bearing results. Public viewing should allow anybody; private personal viewing must require the owning user, and private organization viewing must require membership in the app's owning organization. The session's selected workspace must not determine membership. All viewing consumers should share `authorizeAppViewing`; source access and management must use the owner/member rule regardless of visibility.

## App membership

Platform must own `app_member` as the existing user's relationship to an app, keyed by `(app_id, user_id)`, without copying web's identities or organization memberships. Explicit joining must enable member-scoped unattended participation; viewing must not create membership. Creation must automatically join the individual creator through the same `joinApp` operation inside the existing app-creation transaction, including for organization-owned apps. Other organization members must join explicitly.

Expose `POST /api/apps/{target}/join` with Zod/OpenAPI and the existing authenticated viewing boundary. Exclude public apps at the join route; private viewing permission grants joining permission. Derive the member's user ID from verified `AppAccess`, never caller input. Shared `joinApp` must own insertion using the composite key's native conflict handling and return `{ app_id, user_id }`. Membership must not grant viewing or source-management access or start a job. Job authorization remains viewing-based; preparation requires membership only when the selected agent needs viewer-mode resources. Keep the CLI on the authenticated API path and defer chrome controls until separately requested. Apply migration `007_app_member` before using this code against an existing database.

Keep React Router's `/dashboard/` basename separate from Vite's default `/` asset base. Local platform development and integration tests must select the native test environment with isolated remote resources. Keep namespace selection in Wrangler configuration. Deploy this Worker through the shared repository-root `scripts/cloudflare.sh` build/deploy phases, matching dispatcher, auth, and build. Native `secrets.required` in the effective Wrangler configuration owns required runtime secret names; Doppler owns their values. Let Wrangler resolve Vite's generated deployment configuration. Keep the bootstrap Doppler token and registry credential in the build environment, and do not add package-specific deployment scripts or another secret allowlist.

## Platform and web ownership

Web should own users, Better Auth sessions, organizations, memberships, and identity verification. Platform should own apps and app authorization. Treat cookies and tokens as opaque credentials; never derive identity from unverified fields or introduce a second session secret, session store, or membership mirror.

For native browser requests, forward the caller's Cookie header to web's `/api/auth/get-session` for verification. Retain CLI bearer authentication through web's JWKS. Keep the verified identity and its credential together at the request boundary so loaders and domain functions use the same caller.

Web's `/api/me` should own the safe profile contract (`id`, `name`, nullable `image`) for authorized CLI tokens and native web sessions and must reject viewer cookies. Trusted consumers should call web directly; do not add a public platform profile proxy or delegate profile reads to authored code. For user-scoped web facts, forward that caller's authorized credential to the appropriate web endpoint. Web must authenticate the caller and return authoritative facts; platform should apply its app rules. Do not introduce machine-to-machine authentication for these reads.

## API authentication and authorization

Default platform API, Git, and dashboard authentication must accept only native web sessions and authorized CLI tokens. Use the existing `identifyUser` middleware and narrow optional identity with `requireAuth` at protected boundaries. Explicit bearer credentials should take precedence. Keep one identity context; do not maintain a separate user context variable.

Viewer-cookie acceptance must be explicit and limited to non-MCP `GET /api/apps/resolve` requests. Hosted tool calls and database queries must enter only through the separate Execution WorkerEntrypoint over dispatcher’s native EXECUTION service binding. The binding establishes invocation authority; Better Auth establishes viewer identity from the session token passed as data. Validate AppID and the call at this boundary, then reuse viewing, billing and domain operations. Keep these methods separate from Publication because their callers and trust differ. App loaders/actions can enforce viewer-specific behavior only when authored app code is the sole path to these resources. App resolution validates its query once through the native OpenAPI validator, then calls `getAppViewerIdentity` with that typed input: exactly `pathname=/mcp` uses Better Auth’s native resource-client verification with the canonical app MCP URL audience and `mcp:access` scope, without any cookie fallback. Forward its OAuth challenge before applying the existing viewing and billing operations to the same validated hostname/pathname. Public `GET /api/apps/mcp/metadata` resolves the stored app hostname and uses that same native helper to describe its MCP resource and central issuer; it grants no runtime access. Mount resolution before default API identity verification, and mount the API before native identity middleware for Git/dashboard. Connection reads/writes, app management, agent-source reads, secrets, Git, and dashboard must reject viewer-cookie authentication. Better Auth should verify viewer identity, but viewer credentials must not contain reusable web management credentials or be replayable as native web sessions. Keep session ownership in web and all credentials out of authored code.

Reuse one authentication middleware for `requireAuth` and `requireDashboardAuth`. Enable redirects only for dashboard GETs preferring HTML: use Hono's `accepts` helper and web's `/auth/sign-in?redirectTo=<requested-dashboard-url>`. Non-HTML dashboard requests and API/Git requests should return 401. Negotiate through `Accept`, not request `Content-Type`; unspecified or wildcard preferences should retain 401. Better Auth's existing UI and native protocols should own social callbacks and trusted-origin validation, without a custom callback protocol or session mechanism.

Native web/CLI organization reads should use `/api/platform/organizations` for `{id, slug, name}` records. Viewer-authenticated private organization viewing must instead use web's explicitly allowed `/api/viewer/organizations/:organizationId/membership` for only `{isMember}` about the canonical app's owner. Keep this HTTP boundary in `checkViewerOrganizationMembership`, selected explicitly by `resolveAppForViewing` for viewer sessions. Web must verify the session and remain the membership authority.

`resolveAppForViewing` should normalize an AppID or public-hostname target, look up the canonical app, retrieve membership facts, and call the pure `authorizeAppViewing(app, identity, isOwnerOrganizationMember)`. Keep network I/O and framework context out of the pure predicate. The resolution endpoint should return 200 with `{id, owner}`, 401 for required sign-in, 403 for denied viewing, and 404 for an absent app. Dispatcher must consume this decision for every hosted-app path without duplicating authorization policy.

`authorizeAppManagement` should own the pure owner/member rule for Git source access, app listing, visibility updates, and other management operations. Public visibility must grant viewing only. Retrieve authoritative membership facts before applying the rule; `listApps` should fetch them once for its listing. `PATCH /api/apps/{target}` should validate through `updateAppVisibilityRequestSchema`, resolve canonical `AppAccess`, and call the shared `updateAppVisibility` operation. That operation must require management before writing and return the saved app.

Git must require authentication and management before reading Artifacts or minting credentials. Share `getGitAccess` and `listApps` across their consumers. Upload-pack should receive read credentials and receive-pack write credentials, including GET discovery; HTTP method alone must not determine publication permission. Keep Artifacts credentials server-side. Organization membership should carry no additional role restriction.

## Connections and shared secrets

Connections and secrets must use the canonical `Owner`. Shared `authorizeOwner` in `owner.server.ts` must establish that a personal Owner matches the verified caller or that web confirms organization membership before provider I/O. `ownerParamsSchema` should validate HTTP `user`/`org` parameters and convert them to the canonical Owner at the boundary.

Use `secrets.schema.ts` and `secrets.server.ts` for shared-secret management. Platform alone should construct provider keys and select the vault through `CTX_CUSTOMER_CREDENTIALS_DOPPLER_PROJECT`, `CTX_CUSTOMER_CREDENTIALS_DOPPLER_CONFIG`, and the config-scoped `CTX_CUSTOMER_CREDENTIALS_DOPPLER_TOKEN`. Local development should select `customer-credentials-local/prod`; deployed platform should select `customer-credentials/prod`. Require vault configuration for authorized secret operations without coupling unrelated routes to it. Return only Owner/name. Never log values, request bodies, credentials, or provider responses. Manifest secret declarations should reference the selected Owner's named vault secret directly; do not add a secret-assignment table.

`GET` and `POST /api/connections/{type}/{owner_id}` should list or authorize the selected Owner's Composio Platform accounts. `listConnections` and `authorizeConnection` must receive validated configuration, verified identity, and canonical Owner and enforce management before provider calls. Filter account lists and create provider sessions using that same Owner ID. Shared account discovery must use Composio's native `statuses: ["ACTIVE"]` query on every page for both Owner-scoped and personal-account listing. The shared `connectionSchema` must represent an active account, with literal `ACTIVE` status; consumers receive eligible accounts without interpreting provider lifecycle states. An organization member may complete OAuth, but the resulting connection must belong to the organization. Keep provider credentials and account refresh in Composio; app assignments should reference those accounts. CLI `owner.ts` should share personal/organization resolution across connection and secret commands.

`listAppConnections` and `assignAppConnection` should receive canonical `AppAccess` from the shared viewing boundary and validated pushed Resources. Hosted `callTool` receives canonical AppAccess and owns that pushed read internally. `getCredentialOwner` should resolve viewer mode to the acting user and owner mode to the app's owning user or organization. Persist assignments by `(app_id, owner_type, owner_id, slug)` and read both Owners together when listing. Owner assignment must require app management; viewer assignment should follow app viewing. Authored owner-mode execution should require viewing; viewer-mode execution must require app membership for interactive and job use. Credential configuration retains its existing authorization and remains available before joining. Resolve the ephemeral app/viewer/member relationship from the existing `app_member` table at trusted execution preparation; return `membership-required` before resource execution for a non-member, distinct from `not-declared`. Hosted Execution methods must return typed results through the shared `HostedExecution` contract; the shared capabilities throw ordinary `Error` objects with exact messages `membership-required` and `not-declared`, preserving the public Tools and Databases interfaces and local execution contracts. Hosted operations must never accept caller-supplied Slates or Resources, including from app owners. Hosted execution preparation owns the centralized pushed declaration read, consumer selection, canonical resource Owner, and assignment resolution; its execution-facing signature must not accept replacement requirements. Configuration operations read the same centralized snapshot before passing validated Resources to shared collection/configuration logic.

Keep declared-requirement, canonical Owner, and assignment selection in shared `resolveAppConnection`. Share `createConnectionSession` for Composio sessions pinned to that Owner's assigned account and toolkit. Personal-account and hosted execution preparation must establish authority separately before using native scoped session execution. `listPersonalConnections` and `callConnectionTool` must derive the personal user Owner from verified native identity, with no caller-selected Owner or organization. Personal HTTP operations use native web/CLI authentication and reject viewer cookies; their domain identity type must exclude viewer credentials. A concrete account ID selects within that personal authority. Its app context preserves viewing, subscription, and usage policy independently of credential ownership. The hosted slug-based Tools operation retains published app/viewer delegation. Reuse native service-binding ownership and the authored Tools interface while keeping these authority paths explicit; no optional Resources transport or provenance permission flag. Hosted agents reuse the same account selection during authorized job preparation and connect the resulting Composio session through Think's native MCP support. Think owns MCP transport and tool execution; Composio owns service-account credentials, refresh, and external API calls. Use Think's native lifecycle hooks for future agent billing; no agent billing policy is implemented yet.

Keep undeclared connections and declared-but-unassigned connections distinct in `resolveAppConnection`. An unassigned declared connection returns `connection-required` with its slug; the hosted Tools adapter exposes the shared Zod setup payload with status 409. An undeclared resource returns `not-declared`. Missing assignments must stop before provider execution and tool usage recording. Tools transports the setup Response over native RPC, and the SDK throws it on the app side so React Router can render setup guidance without exposing account catalogs or credentials. Do not turn arbitrary failures into account-setup conditions.

Authorization belongs to the operation boundary before the read; the reader receives no caller credentials, resolves no resource values, and invokes no authored Worker. Construct `Resources` before passing declarations downstream. Local tooling must read and validate all current-folder app/agent Slates and collect Resources locally. Development connection bindings remain in ignored app-local configuration, secret values come from exact-name environment variables, and databases are native local SQLite instances with state under .contextlayer/databases. Local construction includes database references and native migration artifacts before consumer selection; runtime startup applies the full collected history before queries.

Linux /workspace holds scratch files; no Git checkout or repository credentials are used for app data. Keep model/vault credentials in Worker code. Compose runtime, platform, and published instructions as system context, with the task as a user message. Load the declared Owner’s model key from Doppler’s literal `value.raw` inside trusted execution and pass it directly to the model provider. Keep the key and vault token out of persisted run configuration, prompts, and workspace files. Use Think’s native `configure` and `submitMessages` for background execution, with one stable named Durable Object per app/agent/actor and a separate UUID for each submission. Return the serializable `AgentJob` contract at the Durable Object RPC boundary: submission UUID, native `instance_name`, `source: api | schedule` from native submission metadata, native Think status, nullable saved assistant text, and optional native error. ## App-owner billing access

Use Polar's native SDK to verify raw requests at `POST /api/polar/webhooks` with `POLAR_WEBHOOK_SECRET`. Enroll newly created customers with an external ID in the configured native Free product on `customer.created`; acknowledge after native subscription creation succeeds. On `customer.state_changed`, acknowledge only after `saveCustomerState` persists the full native Customer State. Better Auth owns individual and team customer creation; Polar owns subscription and credit fulfillment, balances, renewal, and the customer portal. Use package migrations and Kanel for the schema. Treat `external_id` as the Better Auth user/organization ID and Polar's `organization_id` as our merchant, never the app's owning team.

Keep billing access separate from identity and viewing authorization. Runtime resolution and the `Execution` entrypoint must call shared `checkAppBilling` after viewing authorization; personal-account execution must call the same decision while retaining its own credential authority. Read the app owner's saved native `active_subscriptions`; missing/empty state returns 402. Any active subscription outside the configured Free product retains the existing database-only admission policy. Identify Free by `POLAR_FREE_PRODUCT_ID`, then query native Customer State for the live `POLAR_CLIPS_METER_ID` balance; admit positive balance and deny exhaustion with 402. These required, environment-specific IDs identify Polar resources rather than copying allowances or balances. Keep one billing decision at the existing runtime boundaries, including hosted assets and MCP discovery/resources. Resolution should receive the actual incoming `pathname`; exactly `/slate.json` skips billing while retaining viewing authorization. Connection configuration, app creation/listing, Git, dashboard, and billing management remain available. Return a nonempty billing message with the renewal date for exhaustion and an existing web billing destination appropriate to the app owner; local Tools must preserve that message. Use personal billing for a user owner and the organization chooser for an organization owner; web owns membership/slug resolution and native portal navigation. Free must have no metered price, so exhaustion cannot create overage charges. Usage reporting remains asynchronous after execution, so admission does not provide atomic clip reservations. Do not introduce a second balance ledger or legacy no-plan enrollment/backfill.
