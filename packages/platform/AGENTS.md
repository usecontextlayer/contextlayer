# Platform

These construction rules use the vocabulary defined in ARCHITECTURE.md's [domain model](../../ARCHITECTURE.md#domain-model). Requirements describe what must be true, not proof that every protection or feature is implemented. Keep concepts, dataflow, and trust boundaries in ARCHITECTURE.md, operating workflows in [DEVELOPING.md](../../DEVELOPING.md), and implementation history in ExecPlans.

## OpenAPI, Zod, and Shared Domain Functions

**Use OpenAPI for application APIs, Zod for validation, and one shared domain function for each operation's business logic and database calls. API handlers and server-side loaders/actions must call that same function.** Apply this shape even to a simple database query.

- **Schemas must own the contract.** Define API input and output schemas with Zod. Reuse them for validation, inferred TypeScript types, and generated OpenAPI documentation. Reuse the same input schema wherever callers accept the same untrusted input.
- **API handlers should own HTTP.** Parse and validate request inputs, call the domain function, and translate its result into an HTTP response. Keep business decisions and database queries in the shared function.
- **Loaders and actions should call the domain function directly.** React Router server loaders/actions should invoke it in-process, validate their untrusted inputs, and adapt its result to the framework's response conventions. Do not call our own API over HTTP or implement a second database path.
- **Domain functions must own the operation.** Accept typed, normalized arguments, enforce business rules, perform database reads/writes, and return typed results. Do not accept framework request/context objects or return HTTP responses.
- **Use ordinary functions grouped by domain.** One operation should have one implementation, regardless of its entry points. Do not add service classes, a generic repository layer, or a dependency-injection framework to express this boundary.

For example, `GET /api/slates` and the slate-listing loader should both call `listSlates(...)`. That function should own the query; the endpoint and loader should each adapt its result for their caller. OpenAPI and the shared operation should be part of the first implementation.

## Slate identity and storage

Platform should own the immutable `slate.id` UUID and unique `slate.public_hostname`. The slate’s name is the hostname label before `CTX_SLATES_DOMAIN`; there is no separate name column. The UUID should name the Artifacts repository and the `/git/<slate-id>` address. Create slates during `ctx init`, not on first push. PostgreSQL must enforce exactly one of `owner_user_id` or `owner_organization_id` through `slate_exactly_one_owner`. Those IDs must refer to web's Better Auth identities without duplicating their records in platform.

Normalize validated creation input and the verified caller into the canonical `Owner` union in `app/owner.ts` before writing. Creation, listing, connections, and secrets should share that ownership shape. Dashboard `OwnerDetails` should derive its variants from `Owner`, adding schema-derived organization name/slug metadata only for presentation. `POST /api/slates` must require authentication. An omitted `organization_slug` should select the verified user; a supplied slug must resolve against the caller's authoritative organization list before database or Artifacts writes. Return 404 for an unavailable organization. Callers must not choose another user as Owner.

Use existing `db-infra` helpers, package-owned Kysely migrations, and Kanel-generated models. Never hand-edit generated models. Keep `verbatimModuleSyntax: false` for compatibility with Kanel's default Database type export. The server should own its database connection; migrations and Kanel generation should run through the package's Node database management commands.

Store `slate.visibility` as non-null text, validate `public`/`private` through `slateVisibilitySchema`, and use `DEFAULT_SLATE_VISIBILITY = "private"` for creation. Parse slate rows through `slateSchema` before returning slate-bearing results. Public viewing should allow anybody; private personal viewing must require the owning user, and private organization viewing must require membership in the slate's owning organization. The session's selected organization must not determine membership. All viewing consumers should share `authorizeSlateViewing`; source access and management must use the owner/member rule regardless of visibility.

## Slate membership

Platform must own `slate_member` as the existing user's relationship to a slate, keyed by `(slate_id, user_id)`, without copying web's identities or organization memberships. Explicit joining must enable member-scoped unattended participation; viewing must not create membership. Creation must automatically join the individual creator through the same `joinSlate` operation inside the existing slate-creation transaction, including for organization-owned slates. Other organization members must join explicitly.

Expose `POST /api/slates/{target}/join` with Zod/OpenAPI and the existing authenticated viewing boundary. Exclude public slates at the join route; private viewing permission grants joining permission. Derive the member's user ID from verified `SlateAccess`, never caller input. Shared `joinSlate` must own insertion using the composite key's native conflict handling and return `{ slate_id, user_id }`. Membership must not grant viewing or source-management access or start a job. Job authorization remains viewing-based; preparation requires membership only when the selected agent needs viewer-mode resources. Keep the CLI on the authenticated API path and defer chrome controls until separately requested.

## Workers runtime

Validate Worker bindings in `env.ts`. Follow [DEVELOPING.md](../../DEVELOPING.md#platform-development) for Worker startup and environment loading; use Wrangler's native `secrets.required` to load declared environment variables instead of maintaining `.dev.vars`. Hono middleware should own each request's Postgres.js/Kysely connection, share it with API handlers and React Router loaders, and close it through `waitUntil`. Do not run migrations or Kanel generation inside the Worker.

Keep React Router's `/dashboard/` basename separate from Vite's default `/` asset base. Use selective `assets.run_worker_first` for `/api/*`, `/git/*`, and `/dashboard/*` so page/data requests and APIs reach their authorization boundaries while assets use native Cloudflare/Vite serving. Do not put assets under `/dashboard/` or run the Worker first for every path. Keep dispatcher authorization for hosted slates separate.

Use the native ARTIFACTS binding for slate source, acquiring disposable repository handles with using. SQLite-backed Durable Objects own persistent slate databases through the private DATABASES namespace. Configure separate source namespaces and native Worker environments for production and test. Do not add runtime Artifacts REST clients, database REST storage clients, or API-token secrets.

Local platform development and integration tests must select the native test environment with isolated remote resources. Keep namespace selection in Wrangler configuration. Vite must use the source entrypoint, while built local startup must load the compiled bundle with the selected source configuration; preview must not inherit production bindings from a previous build.

Deploy this Worker through the shared repository-root `scripts/cloudflare.sh` build/deploy phases, matching dispatcher, auth, and build. Native `secrets.required` in the effective Wrangler configuration owns required runtime secret names; Doppler owns their values. Let Wrangler resolve Vite's generated deployment configuration. Keep the bootstrap Doppler token and registry credential in the build environment, and do not add package-specific deployment scripts or another secret allowlist.

## Platform and web ownership

Follow ARCHITECTURE.md's [platform and web boundary](../../ARCHITECTURE.md#platform-and-web-ownership-and-dataflow). Treat cookies and tokens as opaque credentials; never derive identity from unverified fields or introduce a second session secret, session store, or membership mirror.

For native browser requests, forward the caller's Cookie header to web's `/api/auth/get-session` for verification. Retain CLI bearer authentication through web's JWKS. Keep the verified identity and its credential together at the request boundary so loaders and domain functions use the same caller.

Web's `/api/me` should own the safe profile contract (`id`, `name`, nullable `image`) for authorized CLI tokens and native web sessions and must reject viewer cookies. Trusted consumers should call web directly; do not add a public platform profile proxy or delegate profile reads to authored code. For user-scoped web facts, forward that caller's authorized credential to the appropriate web endpoint. Web must authenticate the caller and return authoritative facts; platform should apply its slate rules. Do not introduce machine-to-machine authentication for these reads.

## API authentication and authorization

Default platform API, Git, and dashboard authentication must accept only native web sessions and authorized CLI tokens. Use the existing `identifyUser` middleware and narrow optional identity with `requireAuth` at protected boundaries. Explicit bearer credentials should take precedence. Keep one identity context; do not maintain a separate user context variable.

Viewer-cookie acceptance must be explicit and limited to non-MCP `GET /api/slates/resolve` requests. Hosted tool calls and database queries must enter only through the separate Execution WorkerEntrypoint over dispatcher’s native EXECUTION service binding. The binding establishes invocation authority; Better Auth establishes viewer identity from the session token passed as data. Validate SlateID and the call at this boundary, then reuse viewing, billing and domain operations. Keep these methods separate from Provisioning because their callers and trust differ. App loaders/actions can enforce viewer-specific behavior only when authored app code is the sole path to these resources. Slate resolution validates its query once through the native OpenAPI validator, then calls `getSlateViewerIdentity` with that typed input: exactly `pathname=/mcp` uses Better Auth’s native resource-client verification with the canonical slate MCP URL audience and `mcp:access` scope, without any cookie fallback. Forward its OAuth challenge before applying the existing viewing and billing operations to the same validated hostname/pathname. Public `GET /api/slates/mcp/metadata` resolves the stored slate hostname and uses that same native helper to describe its MCP resource and central issuer; it grants no runtime access. Mount resolution before default API identity verification, and mount the API before native identity middleware for Git/dashboard. Connection reads/writes, slate management, agent-source reads, secrets, Git, and dashboard must reject viewer-cookie authentication. Keep viewer credential handling at the [viewer sign-in boundary](../../ARCHITECTURE.md#viewer-sign-in-boundary--principles), with session ownership in web and all credentials out of authored code.

Reuse one authentication middleware for `requireAuth` and `requireDashboardAuth`. Enable redirects only for dashboard GETs preferring HTML: use Hono's `accepts` helper and web's `/auth/sign-in?redirectTo=<requested-dashboard-url>`. Non-HTML dashboard requests and API/Git requests should return 401. Negotiate through `Accept`, not request `Content-Type`; unspecified or wildcard preferences should retain 401. Better Auth's existing UI and native protocols should own social callbacks and trusted-origin validation, without a custom callback protocol or session mechanism.

Native web session and CLI organization reads should use `/api/platform/organizations` for `{id, slug, name}` records. Viewer-authenticated private organization viewing must instead use web's explicitly allowed `/api/viewer/organizations/:organizationId/membership` for only `{isMember}` about the canonical slate's Owner. Keep this HTTP boundary in `checkViewerOrganizationMembership`, selected explicitly by `resolveSlateForViewing` for viewer identities. Forward an MCP viewer's slate-bound bearer in Authorization and its verified resource in the endpoint's `resource` query parameter; viewer sessions retain their cookie path. Web must verify the credential and remain the membership authority.

`resolveSlateForViewing` should normalize a SlateID or public-hostname target, look up the canonical slate, retrieve membership facts, and call the pure `authorizeSlateViewing(slate, identity, isOwnerOrganizationMember)`. Keep network I/O and framework context out of the pure predicate. The resolution endpoint should return 200 with `{id, owner}`, 401 for required sign-in, 403 for denied viewing, and 404 for an absent slate. Dispatcher must consume this decision for browser requests and `/mcp` without duplicating authorization policy; public OAuth resource metadata remains a separate unauthenticated route.

`authorizeSlateManagement` should own the pure owner/member rule for Git source access, slate listing, visibility updates, and other management operations. Public visibility must grant viewing only. Retrieve authoritative membership facts before applying the rule; `listSlates` should fetch them once for its listing. `PATCH /api/slates/{target}` should validate through `updateSlateVisibilityRequestSchema`, resolve canonical `SlateAccess`, and call the shared `updateSlateVisibility` operation. That operation must require management before writing and return the saved slate.

Git must require authentication and management before reading Artifacts or minting credentials. Share `getGitAccess` and `listSlates` across their consumers. Upload-pack should receive read credentials and receive-pack write credentials, including GET discovery; HTTP method alone must not determine deployment permission. Keep Artifacts credentials server-side. Organization membership should carry no additional role restriction.

## Connections and shared secrets

Connections and secrets must use the canonical `Owner`. Shared `authorizeOwner` in `owner.server.ts` must establish that a personal Owner matches the verified caller or that web confirms organization membership before provider I/O. `ownerParamsSchema` should validate HTTP `personal`/`org` parameters and convert them to the canonical Owner at the boundary.

Use `secrets.schema.ts` and `secrets.server.ts` for shared-secret management. Platform alone should construct provider keys and select the vault through `CTX_OWNER_CREDENTIALS_DOPPLER_PROJECT`, `CTX_OWNER_CREDENTIALS_DOPPLER_CONFIG`, and the config-scoped `CTX_OWNER_CREDENTIALS_DOPPLER_TOKEN`. Follow [DEVELOPING.md](../../DEVELOPING.md#shared-secret-management-verification) for vault configuration. Require vault configuration for authorized secret operations without coupling unrelated routes to it. Return only Owner/name. Never log values, request bodies, credentials, or provider responses. Declared secrets should reference the selected Owner's named vault secret directly; do not add a secret-assignment table.

`GET` and `POST /api/connections/{type}/{owner_id}` should list or connect the selected Owner's Composio Platform accounts. `listConnections` and `connectAccount` must receive validated configuration, verified identity, and canonical Owner and enforce management before provider calls. Filter connected account lists and create provider sessions using that same Owner ID. Shared connected account discovery must use Composio's native `statuses: ["ACTIVE"]` query on every page for both Owner-scoped and personal-account listing. The shared `connectionSchema` must represent an active connected account, with literal `ACTIVE` status; consumers receive eligible connected accounts without interpreting provider lifecycle states. An organization member may complete OAuth, but the resulting connected account must belong to the organization. Keep provider credentials and account refresh in Composio; slate assignments should reference those connected accounts. CLI `owner.ts` should share personal/organization resolution across connection and secret commands.

`listSlateConnections` and `assignSlateConnection` should receive canonical `SlateAccess` from the shared viewing boundary and validated pushed Resources. Hosted `callTool` receives canonical SlateAccess and owns that pushed read internally. `getCredentialOwner` should resolve viewer mode to the acting user and owner mode to the slate's owning user or organization. Persist assignments by `(slate_id, owner_type, owner_id, slug)` and read both Owners together when listing. Owner assignment must require slate management; viewer assignment should follow slate viewing. Authored owner-mode execution should require viewing; viewer-mode execution must require slate membership for interactive and job use. Credential configuration retains its existing authorization and remains available before joining. Resolve the ephemeral `SlateActor` relationship from the existing `slate_member` table at trusted execution preparation; return `membership-required` before resource execution for a non-member, distinct from `not-declared`. Hosted Execution methods must return typed results through the shared `HostedExecution` contract; the shared capabilities throw ordinary `Error` objects with exact messages `membership-required` and `not-declared`, preserving the public Tools and Databases interfaces and local execution contracts. Hosted operations must never accept caller-supplied declarations or Resources, including from slate Owners. Hosted execution preparation owns the centralized pushed declaration read, consumer selection, canonical resource Owner, and assignment resolution; its execution-facing signature must not accept replacement requirements. Configuration operations read the same centralized snapshot before passing validated Resources to shared collection/configuration logic.

Keep declared-requirement, canonical Owner, and assignment resolution in shared `resolveSlateConnection`. Share `createConnectionSession` for Composio sessions pinned to that Owner's assigned connected account and toolkit. Personal-account and hosted execution preparation must establish authority separately before using native scoped session execution. `listPersonalConnections` and `callConnectionTool` must derive the personal Owner from verified native identity, with no caller-selected Owner or organization. Personal HTTP operations use native web/CLI authentication and reject viewer cookies; their domain identity type must exclude viewer credentials. A concrete account ID selects within that personal authority. Its slate context preserves viewing, subscription, and usage policy independently of credential ownership. The hosted slug-based Tools operation retains hosted slate/viewer delegation. Reuse native service-binding ownership and the authored Tools interface while keeping these authority paths explicit; no optional Resources transport or provenance permission flag. Hosted agents reuse the same assignment resolution during authorized job preparation and connect the resulting Composio session through Think's native MCP support. Think owns MCP transport and tool execution; Composio owns connected account credentials, refresh, and external API calls. Use Think's native lifecycle hooks for future agent billing; no agent billing policy is implemented yet.

Keep undeclared connections and declared-but-unassigned connections distinct in `resolveSlateConnection`. An unassigned declared connection returns `connection-required` with its slug; the hosted Tools adapter exposes the shared Zod `connection-required` payload with status 409. An undeclared resource returns `not-declared`. Missing assignments must stop before provider execution and tool usage recording. Tools transports the `connection-required` Response over native RPC, and the SDK throws it on the app side so React Router can render guidance for the unassigned connection without exposing connected account catalogs or credentials. Do not turn arbitrary failures into unassigned connections.

## Declaration sources and contracts

Use the schema, `collectSlateResources`, and `resourcesForConsumer` from `@usecontextlayer/shared/declaration` to enforce the [resource contract](../../ARCHITECTURE.md#key-contract-slate-resource-requirements); do not duplicate collection or validation. Derive neutral resource configuration responses in `@usecontextlayer/shared/slate-resources` from Resources, preserving consumers and adding selected canonical Owners plus saved connection IDs. Derive the connection-specific response in `@usecontextlayer/shared/slate-connections` from that same contract; extend neutral responses with `slateSchema` for platform OpenAPI and reuse them in trusted clients. Keep database column branding for connection assignment inputs in `app/slate-connections.schema.ts`. `getSlateResourceConfiguration` should coordinate assignment reads and call pure `prepareSlateResourceConfiguration` to assemble requirements, canonical Owners, and saved connection IDs. `listSlateResources` consumes the full collection and `listSlateConnections` projects its connection entries; expose this through `POST /api/slates/{target}/resources/list` and call the same domain operation directly from trusted loaders. Secret configuration should reuse existing Owner/name set/drop operations, with no slate-specific vault or assignment record. Hosted database configuration must retain requirements/consumers and canonical Owners and derive `instance_name` centrally from `(SlateID, Owner, slug)`. Derivation is pure metadata, not evidence of provisioning. Share `prepareSlateDatabaseConfiguration` between broader configuration assembly and membership provisioning; do not resolve database Owners again in runtime consumers. Resource inventory must not load secret values, provision databases or claim database readiness. The chrome loader should consume selected Owners from connection listing rather than resolve them again. Authored SDK/runtime code must expose neither profile nor connection-read capabilities.

Hosted declaration consumers must use shared `readSlateDeclarations` with the native Artifacts binding and canonical SlateID. Resolve latest `main` once and read the declarations for the slate's app and agents from that immutable commit; return an `allowed: true` snapshot with the commit, discovered agent tree references, validated declarations and collected Resources, or `{ allowed: false, reason: "no-commit" }` when `main` has no commit. Preserve that outcome through `getSlateResources`; the resource API group maps it once to HTTP 409 using shared `noCommitSchema`, documents it on listing and assignment operations, and chrome renders it as loader data. Provisioning must consume those discovered trees rather than rediscover agents. The commit establishes read coherence, not an event-selected revision or persisted deployment pointer. Authorization belongs to the operation boundary before the read; the reader receives no caller credentials, resolves no resource values, and invokes no authored Worker. Construct `Resources` before passing declarations downstream. Follow the [resource contract](../../ARCHITECTURE.md#slate-tool-calls-and-local-development--agreed-contract) for local tooling; platform must not accept its declarations or Resources. Personal connected account discovery must require a toolkit and return only verified-user connected account metadata. Concrete-account execution must accept only account ID, toolkit, tool/arguments, and slate access/billing context, without reading hosted declarations or assignments. Configuration uses the complete collection; interactive execution and agent preparation/provisioning must use pure shared `resourcesForConsumer(resources, consumer)` with the slate's app or named agent. Keep the selector free of I/O and local overrides. Chrome and hosted CLI targets must read pushed declarations.

## Agent source and preparation

Use `agents/<name>/instructions.md` in the slate's Artifacts repository for agent definitions. `getAgent` must require source-management permission through `SlateAccess` before reading, including for public slates. Pin the read to the selected `main` commit and return the instructions with that hash. Expose inspection through `GET /api/slates/{target}/agents/{name}` with Zod/OpenAPI. Viewing permission alone must not grant source inspection.

Keep `getAgentRun` as shared internal preparation from a canonical slate, explicit `AgentActor`, agent name, and user prompt. The API boundary authenticates and authorizes viewing before supplying its user actor; the scheduling boundary passes the run actor without caller credentials. Select that named agent's Resources through shared `resourcesForConsumer` from the coherent latest repository snapshot and pin instruction reads to its commit, without applying source-inspection management permission to execution. Preparation must not accept an event-selected revision; API and scheduled execution share this latest-snapshot path. Resolve the actor’s `SlateActor` relationship through the existing membership table and selected requirements before configuration assembly, returning `membership-required` for a non-member requiring viewer-mode resources. Resolve the selected requirements through `getSlateResourceConfiguration` for the authorized resource actor, reusing the same Owner/assignment assembly as resource inventory and app execution. Pure `prepareAgentRun` consumes that configuration and constructs a complete run only after required connections are assigned; it does not resolve Owners or return a run for later mutation. Viewer-scoped resources require a member actor; owner-scoped resources remain available through viewing. `agentRunSchema` contains the slate/actor, authored instructions and source revision, separate prompt, canonical secret Owner references, selected connection Owner/account/toolkit references, and selected database Owner/instance references projected from the existing configuration, without caller credentials, repository tokens or secret values. Database execution consumes those prepared references without deriving Owners or physical instance names again or running migrations. Toolkit must always come from the validated declaration. Keep assignment persistence in `slate-connections.server.ts` and configuration assembly in `slate-resources.server.ts`; execution consumers must not independently resolve assignments or Owners. Do not reconstruct HTTP authentication inside a job.

Use Cloudflare Think for hosted agent execution and a real Linux sandbox attached to that same Durable Object through native `ctx.container`. Select Linux `bash` and native MCP tools through `beforeTurn.activeTools`, and disable just-bash. Register one native MCP server for each selected connection before submitting the job, pass Composio's returned MCP headers inside the trusted Worker, and use native connection readiness/restoration. Expose `database_query` against only the agent’s prepared database references, using parameterized SQL through the private namespace. Writes persist immediately. Keep Linux `/workspace` for scratch files; no Git checkout or repository credentials are used for slate data. Keep model/vault credentials in Worker code. Compose runtime, platform, and deployed instructions as system context, with the task as a user message. Load the declared Owner’s model key from Doppler’s literal `value.raw` inside trusted execution and pass it directly to the model provider. Keep the key and vault token out of persisted run configuration, prompts, and sandbox files. Use Think’s native `configure` and `submitMessages` for background execution, with one stable named Durable Object per slate/agent/actor and a separate UUID for each submission. Use `getAgentByName` for all instance addressing, including inspection, so the SDK owns lifecycle startup. Inspect native submission status and retrieve the persisted assistant message directly through `session.getMessage(messageId)`; Think must own the queue, status ledger, and message storage without a parallel Workflow or job table. Expose job start, slate-scoped job listing, and inspection through `POST /api/slates/{target}/agents/{name}/jobs`, `GET /api/slates/{target}/agents/{name}/jobs`, and `GET /api/slates/{target}/agents/{name}/jobs/{id}?instance_name=<url-encoded-instance-name>` with Zod/OpenAPI. These routes must reuse the existing `requireAuth` and central `requireSlateViewing` boundary. Any authorized viewer of a private slate may request and inspect its jobs; preparation refuses viewer-mode requirements for a non-member with `membership-required`, mapped to the existing HTTP 403, while `agent-definition-missing` maps to 404 and `connection-required` with its slug maps to the shared 409 `connection-required` payload; do not add an initiating-caller permission rule. Temporarily reject public slates through one independently removable condition on the jobs route group, without changing central viewing authorization. Scope each job to its stored slate ID and agent name. Define shared fields for the [job contracts](../../ARCHITECTURE.md#authored-agents) once in `agentJobSummarySchema` and extend it with `message` for `agentJobSchema`. Map Think’s timestamps explicitly to snake_case at the runtime boundary and read `source` from native submission metadata. Listing must read submissions directly without loading messages. Use loose objects requiring only `type` for message parts, preserving the SDK’s fields. Validate each job once on receipt from Durable Object RPC in the shared domain operation: Cloudflare’s RPC types cannot describe the native opaque message/metadata payloads. Do not also parse the job in the runtime. Keep preparation and secret loading internal; job billing still requires a separately agreed implementation.

Schedules live at `agents/<name>/schedules/<prompt>.md`; parse YAML frontmatter through the installed Agents SDK's `parseSkillFrontmatter`, require a five-field `cron` in UTC, and deliver the Markdown body as a user prompt. The build must call the trusted `Provisioning` WorkerEntrypoint through its native service binding only after deployment succeeds, passing slate identity so provisioning reads the latest coherent repository snapshot rather than the event commit. Joining and deployment must call ordinary `provisionSlate`: joining supplies the verified joined user actor, while deployment supplies the app actor and existing member actors. That operation owns the one latest `readSlateDeclarations` snapshot and passes it explicitly to `provisionAgentSchedules`; schedule provisioning must not read latest again. Provision the full collected database union only for supplied member actors, deriving shared owner instances and distinct viewer instances. Use database declarations directly; do not add database assignments. Provisioning alone reads each collected database slug’s native migration journal and SQL once at the snapshot’s commit, sharing the bundle across deduplicated member instances. Use Drizzle durable-sqlite migrate to apply pending history through the private native SQLite-backed namespace. Complete database provisioning before schedule provisioning. Inventory, queries and run preparation neither read migration artifacts nor migrate databases. Read schedule files through the snapshot's discovered agent trees so provisioning uses one coherent input and one discovery owner. Represent a repository's no-commit state explicitly; joining must succeed before source exists, without inventing declarations. Derive each agent's unattended scope through `resourcesForConsumer`: any viewer connection, secret or database selects member scope; zero viewer requirements selects app scope. Schedule payloads carry slate/agent identity, explicit actor, schedule name, and prompt, without a commit selector or caller credential. Address each actor's stable instance through shared native naming and `getAgentByName`. Provision authored schedules only within the derived scope and cancel authored schedules on supplied actors outside it. Native `schedule(cron, callback, payload)` and Cloudflare Durable Object alarms own timing and recurrence. Replace only authored `runScheduled` callbacks through native schedule listing/cancellation; preserve Think's queued-turn scheduling. Each firing uses its actor with shared preparation and native submission/result storage. When preparation reports `agent-definition-missing` or `membership-required`, the instance cancels its own authored schedules at the next firing; missing connection assignments and transient failures still fail without cancellation. Job listing must include jobs acting for the slate's app and the verified caller's user jobs, without changing viewing authorization or making membership a requirement for owner-only API jobs or inspection.

Use Polar's native SDK to verify raw requests at `POST /api/polar/webhooks` with `POLAR_WEBHOOK_SECRET`. Apply the [billing admission policy](../../ARCHITECTURE.md#slate-owner-billing-access) there instead of duplicating it at consumers. Pass the actual incoming pathname to resolution for its declaration exemption. Validate Polar settings in `env.ts`, use the native SDK for Customer State, and preserve the shared refusal message through local and hosted Tools. Use the existing web billing destinations; web owns membership/slug resolution and portal navigation. Keep usage reporting asynchronous through the shared metering operation. Do not introduce a second balance ledger or no-plan enrollment/backfill.

## Slate usage

Keep the canonical Owner schema, resolution contract, and Polar event weights in `@usecontextlayer/shared/slate-usage`. Platform's `app/owner.ts` should re-export `Owner`, keep `OwnerDetails` for dashboard presentation, and use `getSlateOwner` to convert canonical slates. Return that Owner to dispatcher after authorization.

After `callTool` returns an execution result, its delegated entrypoint or personal-account HTTP handler should schedule `recordSlateUsage` for one `tool_call` clip through native `executionCtx.waitUntil`. Missing assignments and authorization denials must not generate usage. Returned Composio execution errors should still count as executed calls. ## Chrome

Follow the [chrome boundary](../../ARCHITECTURE.md#slate-chrome). Mount the chrome iframe through the SDK's `Layout` and serve it through platform's React Router route at `/dashboard/chrome/slates/:target`, keeping its UI, styles, and fonts in platform. Authenticate chrome through the existing native web session middleware; do not add another session store or expose credentials to authored code. Let web own cookie configuration, identity verification, and revocation.

Validate chrome inputs at the request boundary and call the shared authorized domain operations. Read the profile from web. Reuse collected Resources and selected credential Owners from connection listing, with Owner authorization before provider I/O. Keep connected account catalogs inside chrome and available only to viewers who can manage that Owner. Let native loaders/actions own mutations and revalidation without a parallel client-side assignment store. Keep chrome data out of authored loaders, Workers, and clips metering.

Limit messages between chrome and the authored parent to presentation information such as height. Validate origin, source window, and payload at the receiver; never send authentication, profile, or connection data to the parent or expose an authenticated API relay. Protect session-changing actions at the trusted request boundary and use native authentication protocols.

Treat React Router's `/dashboard/__manifest` as public route metadata like assets, without granting access to protected loaders or APIs. Apply CSP `frame-ancestors` to permit HTTPS slate subdomains of `CTX_SLATES_DOMAIN`; permit local HTTP embedding only when platform runs on localhost. Forbid object embeds and base-URL changes. Keep form submissions on the platform origin while permitting the existing Composio authorization destinations. Use Hono's native CSRF middleware for cookie-authenticated form mutations. CSP controls embedding and cannot override browser cookie policy. Do not grant authored origins credentialed CORS access.

## Slate database access and migrations

Use the shared native `SlateDatabase` class for SQLite storage and `ctx.storage.sql` for queries. Delegate transactions, SQL splitting, and applied migration history to Drizzle's `durable-sqlite` migrator. Read `databases/<slug>/migrations` journal and SQL artifacts only during provisioning, pinned to the declaration snapshot's commit. Provision from the authored SQL history; never infer DDL from TypeScript query schemas. Follow [DEVELOPING.md](../../DEVELOPING.md#authored-database-development) for authoring migrations.

Route hosted SQL access through `querySlateDatabase`. The `Execution.queryDatabase` service-binding method must verify the viewer session, apply slate viewing and billing checks, validate declared slug/SQL/parameters, and call that operation. No public HTTP query route may grant direct access with a cookie or token. Select only resources declared by the slate's app and resolve canonical physical references internally. Trusted dispatcher `Databases` props bind the authorized slate/viewer; SDK loaders/actions receive only that request-scoped query capability. Agent SQL tools select only their own prepared resources. Keep physical namespace access and database provisioning private.
