# Platform

These construction rules use the vocabulary defined in ARCHITECTURE.md's [domain model](../../ARCHITECTURE.md#domain-model). Requirements describe what must be true, not proof that every protection or feature is implemented. Keep repo-wide concepts, dataflow, and trust boundaries in ARCHITECTURE.md, repo-wide operating workflows in [DEVELOPING.md](../../DEVELOPING.md), and implementation history in ExecPlans. Package-specific concepts, construction rules and workflows belong here, following [DOCS.md](../../DOCS.md).

## OpenAPI, Zod, and Shared Domain Functions

**Use OpenAPI for application APIs, Zod for validation, and one shared domain function for each operation's business logic and database calls. API handlers and server-side loaders/actions must call that same function.** Apply this shape even to a simple database query.

- **Schemas must own the contract.** Define API input and output schemas with Zod. Reuse them for validation, inferred TypeScript types, and generated OpenAPI documentation. Reuse the same input schema wherever callers accept the same untrusted input.
- **API handlers should own HTTP.** Parse and validate request inputs, call the domain function, and translate its result into an HTTP response. Keep business decisions and database queries in the shared function.
- **Loaders and actions should call the domain function directly.** React Router server loaders/actions should invoke it in-process, validate their untrusted inputs, and adapt its result to the framework's response conventions. Do not call our own API over HTTP or implement a second database path.
- **Domain functions must own the operation.** Accept typed, normalized arguments, enforce business rules, perform database reads/writes, and return typed results. Do not accept framework request/context objects or return HTTP responses.
- **Use ordinary functions grouped by domain.** One operation should have one implementation, regardless of its entry points. Do not add service classes, a generic repository layer, or a dependency-injection framework to express this boundary.

For example, `GET /api/slates` and the slate-listing loader should both call `listSlates(...)`. That function should own the query; the endpoint and loader should each adapt its result for their caller. OpenAPI and the shared operation should be part of the first implementation.

## Slate identity and storage

Platform should own the immutable `slate.id` UUID and unique `slate.public_hostname`. The slate’s name is the hostname label before `CTX_SLATES_DOMAIN`; there is no separate name column. The UUID should name the Artifacts repository and the `/git/<slate-id>` address. Create slates during `ctx init`, not on first push. PostgreSQL must enforce exactly one of `owner_user_id` or `owner_organization_id` through `slate_exactly_one_owner`. Those IDs must refer to web's Better Auth identities without duplicating their records in platform.

Normalize validated creation input and the verified caller into the canonical `Owner` union in `app/owner.ts` before writing. Creation, listing, connections, and secrets should share that ownership shape. Dashboard `OwnerDetails` should derive its variants from `Owner`, adding schema-derived organization name/slug metadata only for presentation. `POST /api/slates` must require authentication. An omitted `organization_slug` should select the verified user; a supplied slug must resolve against the caller's authoritative organization list before database or Artifacts writes. Return 404 for an unavailable organization. Callers must not choose another user as Owner.

Use existing `db-infra` helpers, package-owned Kysely migrations, and Kanel-generated models. Never hand-edit generated models. Keep `verbatimModuleSyntax: false` for compatibility with Kanel's default Database type export. The server should own its database connection; migrations and Kanel generation should run through the package's Node database management commands.

Store `slate.visibility` as non-null text, validate `public`/`private` through `slateVisibilitySchema`, and use `DEFAULT_SLATE_VISIBILITY = "private"` for creation. Parse slate rows through `slateSchema` before returning slate-bearing results. Public viewing should allow anybody; private personal viewing must require the owning user, and private organization viewing must require membership in the slate's owning organization. The session's selected organization must not determine membership. All viewing consumers should share `authorizeSlateViewing`; source access and management must use the owner/member rule regardless of visibility.

## Slate membership

Platform must own `slate_member` as the existing user's relationship to a slate, keyed by `(slate_id, user_id)`, without copying web's identities or organization memberships. `addSlateMember` in `slate-members.server.ts` must be the only membership insertion owner. It must return for existing members before reading assignments or vault names; for a new private-slate member, it must resolve the full collected Resources before inserting and provisioning the person. The creator follows this same rule; creation must not create membership. Use the same pure configuration resolver for requests and membership completeness, reporting unassigned connections and missing viewer-mode secrets before provisioning. Inventory remains metadata-only. Existing membership must survive missing setup, and repeated use must not reinstall schedules.

Completed setup is the only membership entry point; do not expose an explicit join HTTP route or CLI command. Derive the member's user ID from the verified run actor, never caller input. Internal `addSlateMember` must own insertion using the composite key's native conflict handling and provision only when the insert returns a new row. Keep insertion and initial provisioning in one native database transaction, using the supplied coherent declaration snapshot. Membership must not grant viewing or source-management access or start a job. Job authorization remains viewing-based. `prepareSlateResourceExecution` must resolve only the request's selected resources. When they include viewer-mode requirements, require a private user actor and call `addSlateMember` before resolving those selected inputs. Owner-only requests require viewing and their own inputs, without creating membership or depending on unrelated personal setup. Public users and app actors must receive `forbidden` for viewer-mode requirements, independently of stored membership.

## Workers runtime

Use Cloudflare Workers through `react-router-hono-server/cloudflare` and the Cloudflare Vite plugin. Use workerd for local development and Wrangler for local production verification. Validate Worker bindings in `env.ts`. Pass domain functions only the native bindings they use and provider settings through parsed `PlatformConfig`, rather than passing the whole Worker environment. Framework contexts may carry individual bindings for loaders/actions. Follow [DEVELOPING.md](../../DEVELOPING.md#connected-development) for Worker startup and environment loading; use Wrangler's native `secrets.required` to load declared environment variables instead of maintaining `.dev.vars`. Hono middleware should own each request's Postgres.js/Kysely connection, share it with API handlers and React Router loaders, and close it through `waitUntil`. Do not run migrations or Kanel generation inside the Worker.

Keep React Router's `/dashboard/` basename separate from Vite's default `/` asset base. Use selective `assets.run_worker_first` for `/api/*`, `/git/*`, and `/dashboard/*` so page/data requests and APIs reach their authorization boundaries while assets use native Cloudflare/Vite serving. Do not put assets under `/dashboard/` or run the Worker first for every path. Keep dispatcher authorization for hosted slates separate.

Use the native ARTIFACTS binding for slate source, acquiring disposable repository handles with using. SQLite-backed Durable Objects own persistent slate databases through the private DATABASES namespace. Configure separate source namespaces and native Worker environments for production and test. Do not add runtime Artifacts REST clients, database REST storage clients, or API-token secrets.

Local platform development and integration tests must select the native test environment with isolated remote resources. Keep namespace selection in Wrangler configuration. Vite must use the source entrypoint, while built local startup must load the compiled bundle with the selected source configuration; preview must not inherit production bindings from a previous build.

Deploy this Worker through the shared repository-root `scripts/cloudflare.sh` build/deploy phases, matching dispatcher, auth, and build. Native `secrets.required` in the effective Wrangler configuration owns required runtime secret names; Doppler owns their values. Let Wrangler resolve Vite's generated deployment configuration. Keep the bootstrap Doppler token and registry credential in the build environment, and do not add package-specific deployment scripts or another secret allowlist.

## Platform and web ownership

Follow ARCHITECTURE.md's [platform and web boundary](../../ARCHITECTURE.md#platform-and-web-ownership-and-dataflow). Treat cookies and tokens as opaque credentials; never derive identity from unverified fields or introduce a second session secret, session store, or membership mirror.

For native browser requests, forward the caller's Cookie header to web's `/api/auth/get-session` for verification. Retain CLI bearer authentication through web's JWKS. Keep the verified identity and its credential together at the request boundary so loaders and domain functions use the same caller.

Web's `/api/me` should own the safe profile contract (`id`, `name`, nullable `image`) for authorized CLI tokens and native web sessions and must reject viewer cookies. Trusted consumers should call web directly; do not add a public platform profile proxy or delegate profile reads to authored code. For user-scoped web facts, forward that caller's authorized credential to the appropriate web endpoint. Web must authenticate the caller and return authoritative facts; platform should apply its slate rules. Do not introduce machine-to-machine authentication for these reads.

## API authentication and authorization

Default platform API, Git, and dashboard authentication must accept only native web sessions and authorized CLI tokens. Use the existing `identifyUser` middleware and narrow optional identity with `requireAuth` at protected boundaries. Explicit bearer credentials should take precedence. Keep one identity context; do not maintain a separate user context variable.

Viewer-cookie acceptance must be explicit and limited to non-MCP `GET /api/slates/resolve` requests. Hosted tool calls and database queries must enter only through the separate Execution WorkerEntrypoint over dispatcher’s native EXECUTION service binding. The binding establishes invocation authority; Better Auth establishes viewer identity from the session token passed as data. Validate SlateID and the call at this boundary, then reuse viewing, billing and domain operations. Keep these methods separate from Provisioning because their callers and trust differ. App loaders/actions can enforce viewer-specific behavior only when authored app code is the sole path to these resources. Slate resolution validates its query once through the native OpenAPI validator, then calls `getSlateViewerIdentity` with that typed input: exactly `pathname=/mcp` uses Better Auth’s native resource-client verification with the canonical slate MCP URL audience and `mcp:access` scope, without any cookie fallback. Forward its OAuth challenge before applying the existing viewing and billing operations to the same validated hostname/pathname. Public `GET /api/slates/mcp/metadata` resolves the stored slate hostname and uses that same native helper to describe its MCP resource and central issuer; it grants no runtime access. Mount resolution before default API identity verification, and mount the API before native identity middleware for Git/dashboard. Connection reads/writes, slate management, agent-source reads, secrets, Git, and dashboard must reject viewer-cookie authentication. Keep viewer credential handling at the [viewer sign-in boundary](../../ARCHITECTURE.md#viewer-sign-in-boundary--principles), with session ownership in web and all credentials out of authored code.

Reuse one authentication middleware for `requireAuth` and `requireDashboardAuth`. Enable redirects only for dashboard GETs preferring HTML: use Hono's `accepts` helper and web's `/auth/sign-in?redirectTo=<requested-dashboard-url>`. Non-HTML dashboard requests and API/Git requests should return 401. Negotiate through `Accept`, not request `Content-Type`; unspecified or wildcard preferences should retain 401. Better Auth's existing UI and native protocols should own social callbacks and trusted-origin validation, without a custom callback protocol or session mechanism.

Native web session and CLI organization reads should use `/api/platform/organizations` for `{id, slug, name}` records. Viewer-authenticated private organization viewing must instead use web's explicitly allowed `/api/viewer/organizations/:organizationId/membership` for only `{isMember}` about the canonical slate's Owner. Keep this HTTP boundary in `checkViewerOrganizationMembership`, selected explicitly by `resolveSlateForViewing` for viewer identities. Forward an MCP viewer's slate-bound bearer in Authorization and its verified resource in the endpoint's `resource` query parameter; viewer sessions retain their cookie path. Web must verify the credential and remain the membership authority.

`resolveSlateForViewing` should normalize a SlateID or public-hostname target, look up the canonical slate, retrieve membership facts, and call the pure `authorizeSlateViewing(slate, identity, isOwnerOrganizationMember)`. Keep network I/O and framework context out of the pure predicate. The resolution endpoint should return 200 with `{id, owner}`, 401 for required sign-in, 403 for denied viewing, and 404 for an absent slate. Dispatcher must consume this decision for browser requests and `/mcp` without duplicating authorization policy; public OAuth resource metadata remains a separate unauthenticated route.

`authorizeSlateManagement` should own the pure owner/member rule for Git source access, slate listing, visibility updates, and other management operations. Public visibility must grant viewing only. Retrieve authoritative membership facts before applying the rule; `listSlates` should fetch them once for its listing. `PATCH /api/slates/{target}` should validate through `updateSlateVisibilityRequestSchema`, resolve canonical `SlateAccess`, and call the shared `updateSlateVisibility` operation. That operation must require management before writing and return the saved slate.

Git must require authentication and management before reading Artifacts or minting credentials. Share `getGitAccess` and `listSlates` across their consumers. Upload-pack should receive read credentials and receive-pack write credentials, including GET discovery; HTTP method alone must not determine deployment permission. Keep Artifacts credentials server-side. Organization membership should carry no additional role restriction.

## Connections and shared secrets

Connections and secrets must use the canonical `Owner`. Shared `authorizeOwner` in `owner.server.ts` must establish that a personal Owner matches the verified caller or that web confirms organization membership before provider I/O. `ownerParamsSchema` should validate HTTP `personal`/`org` parameters and convert them to the canonical Owner at the boundary.

Use `secrets.schema.ts` and `secrets.server.ts` for shared-secret management. Platform alone should construct provider keys and select the vault through `CTX_OWNER_CREDENTIALS_DOPPLER_PROJECT`, `CTX_OWNER_CREDENTIALS_DOPPLER_CONFIG`, and the config-scoped `CTX_OWNER_CREDENTIALS_DOPPLER_TOKEN`. Follow [shared secret management verification](#shared-secret-management-verification) for vault configuration. Require vault configuration for authorized secret operations without coupling unrelated routes to it. Return only Owner/name. Never log values, request bodies, credentials, or provider responses. Declared secrets should reference the selected Owner's named vault secret directly; do not add a secret-assignment table. Keep secret-key construction and recognition in `secrets.server.ts`, sharing the prefix builder and canonical Owner schema rather than maintaining consumer-specific Owner-type lists.

`setSlateSecret` must receive canonical `OwnerSlateAccess` and the coherent pushed snapshot, select the declared secret's canonical Owner, and delegate to `setSharedSecret` for authorization and persistence. After a successful save, call `addSlateMember` directly, as connection assignment does; an incomplete setup must not fail an otherwise valid save. Chrome and `PUT /api/slates/{target}/secrets/{name}` must call that shared operation. Chrome should list viewer-mode secret requirements, consumers and the shared configuration's `supplied` presence field, and submit values through a password form without returning stored values. Owner-scoped set/drop remains independent of any slate.

`GET` and `POST /api/connections/{type}/{owner_id}` should list or connect the selected Owner's Composio Platform accounts. `listConnections` and `connectAccount` must receive validated configuration, verified identity, and canonical Owner and enforce management before provider calls. Filter connected account lists and create provider sessions using that same Owner ID. Shared connected account discovery must use Composio's native `statuses: ["ACTIVE"]` query on every page for both Owner-scoped and personal-account listing. The shared `connectionSchema` must represent an active connected account, with literal `ACTIVE` status; consumers receive eligible connected accounts without interpreting provider lifecycle states. An organization member may complete OAuth, but the resulting connected account must belong to the organization. Keep provider credentials and account refresh in Composio; slate assignments should reference those connected accounts. CLI `owner.ts` should share personal/organization resolution across connection and secret commands.

`listSlateConnections` should receive canonical `SlateAccess` and validated pushed Resources. `assignSlateConnection` must receive the coherent pushed snapshot, parsed configuration and explicit runtime bindings from the trusted boundary. After its existing authorized save, call `addSlateMember` directly; missing setup is not an assignment failure, while complete setup provisions the person. Keep this trigger inside the shared domain operation so chrome and API consumers behave identically. Pass the already-read snapshot through to provisioning. Hosted `callTool` receives canonical SlateAccess and owns that pushed read internally. `getCredentialOwner` should resolve viewer mode to the acting user and owner mode to the slate's owning user or organization. Persist assignments by `(slate_id, owner_type, owner_id, slug)` and read both Owners together when listing. Owner assignment must require slate management; viewer assignment should follow slate viewing. Authored owner-mode execution should require viewing; private viewer-mode execution establishes membership from complete setup before first use. Credential configuration retains its existing authorization and remains available before membership. Keep the existing app/user run actor and read the membership fact from `slate_member` for private users requesting viewer-mode resources; non-members must complete whole-slate setup through `addSlateMember` before those resources can execute. Return `forbidden` for app actors and public users requesting viewer-mode resources, distinct from `not-declared`. Hosted Execution methods must return typed results through the shared `HostedExecution` contract; the shared capabilities throw ordinary `Error` objects with exact messages `forbidden` and `not-declared`, preserving the public Tools and Databases interfaces and local execution contracts. Hosted operations must never accept caller-supplied declarations or Resources, including from slate Owners. Hosted execution preparation owns the centralized pushed declaration read, consumer selection, canonical resource Owner, and assignment resolution; its execution-facing signature must not accept replacement requirements. Configuration operations read the same centralized snapshot before passing validated Resources to shared collection/configuration logic.

Keep declared-requirement, canonical Owner, and assignment resolution in shared `resolveSlateConnection`. Share `createConnectionSession` for Composio sessions pinned to that Owner's assigned connected account and toolkit. Personal-account and hosted execution preparation must establish authority separately before using native scoped session execution. `listPersonalConnections` and `callConnectionTool` must derive the personal Owner from verified native identity, with no caller-selected Owner or organization. Personal HTTP operations use native web/CLI authentication and reject viewer cookies; their domain identity type must exclude viewer credentials. A concrete account ID selects within that personal authority. Its slate context must require management through `getSlate` before subscription checks and usage billing, independently of personal credential ownership. The hosted slug-based Tools operation retains hosted slate/viewer delegation. Reuse native service-binding ownership and the authored Tools interface while keeping these authority paths explicit; no optional Resources transport or provenance permission flag. Hosted agents reuse the same assignment resolution during authorized job preparation and persist selected connection references with the job. Pi owns agent execution; Composio owns connected account credentials, refresh, and external API calls. The registered native Bash tool executes through the job's attached Linux computer.

Keep undeclared connections and declared-but-unassigned connections distinct in `resolveSlateConnection`. An unassigned declared connection returns `connection-required` with its slug; the hosted Tools adapter exposes the shared Zod `connection-required` payload with status 409. An undeclared resource returns `not-declared`. Missing assignments must stop before provider execution and tool usage recording. Tools transports the `connection-required` Response over native RPC, and the SDK throws it on the app side so React Router can render guidance for the unassigned connection without exposing connected account catalogs or credentials. Do not turn arbitrary failures into unassigned connections.

## Declaration sources and contracts

Use the schema, `collectSlateResources`, and `resourcesForConsumer` from `@usecontextlayer/shared/declaration` to enforce the [resource contract](../../ARCHITECTURE.md#key-contract-slate-resource-requirements); do not duplicate collection or validation. Derive neutral resource configuration responses in `@usecontextlayer/shared/slate-resources` from Resources, preserving consumers and adding selected canonical Owners, saved connection IDs and viewer-mode secret `supplied: boolean` presence metadata. Derive the connection-specific response in `@usecontextlayer/shared/slate-connections` from that same contract; extend neutral responses with `slateSchema` for platform OpenAPI and reuse them in trusted clients. Keep database column branding for connection assignment inputs in `app/slate-connections.schema.ts`. `getSlateResourceConfiguration` in `slate-resource-configuration.server.ts` should coordinate assignment reads and names-only vault reads only when viewer-mode secrets are in scope, then call pure `prepareSlateResourceConfiguration` to assemble requirements, canonical Owners, saved connection IDs and secret presence. The pure `resolveSlateResourceConfiguration` must read only this configuration; resolver, OpenAPI inventory and chrome must consume the same `supplied` field rather than recomputing presence. `listSlateResources` consumes the full collection and `listSlateConnections` passes a connection-only projection through the same assembly, without unrelated secret reads; expose this through `POST /api/slates/{target}/resources/list` and call the same domain operation directly from trusted loaders. Secret configuration should reuse existing Owner/name set/drop operations, with no slate-specific vault or assignment record. Hosted database configuration must retain requirements/consumers and canonical Owners and derive `instance_name` centrally from `(SlateID, Owner, slug)`. Derivation is pure metadata, not evidence of provisioning. Share `prepareSlateDatabaseConfiguration` between broader configuration assembly and membership provisioning; do not resolve database Owners again in runtime consumers. Resource inventory must not load secret values, provision databases or claim database readiness. The chrome loader should consume complete shared resource configuration, including selected Owners and secret presence, rather than assemble or resolve them again. Authored SDK/runtime code must expose neither profile nor connection-read capabilities.

Hosted declaration consumers must use shared `readSlateDeclarations` with the native Artifacts binding, canonical SlateID and an explicit immutable commit. Builds supply the triggering event commit; latest-state Platform operations use `readLatestSlateDeclarations` to select `main` once at their initiating boundary. Return an `allowed: true` snapshot with the commit, discovered agent tree references, validated declarations and collected Resources; the latest-state reader returns `{ allowed: false, reason: "no-commit" }` when `main` has no commit. Preserve that outcome through `getSlateResources`; the resource API group maps it once to HTTP 409 using shared `noCommitSchema`, documents it on listing and assignment operations, and chrome renders it as loader data. Provisioning must consume those discovered trees rather than rediscover agents. Carry the selected snapshot through every phase of the operation; it establishes source coherence without introducing a persisted deployment pointer. Authorization belongs to the operation boundary before the read; the reader receives no caller credentials, resolves no resource values, and invokes no authored Worker. Construct `Resources` before passing declarations downstream. Follow the [resource contract](../../ARCHITECTURE.md#slate-tool-calls-and-local-development--agreed-contract) for local tooling; platform must not accept its declarations or Resources. Personal connected account discovery must require a toolkit and return only verified-user connected account metadata. Concrete-account execution must accept only account ID, toolkit, tool/arguments, and slate access/billing context, without reading hosted declarations or assignments. Configuration uses the complete collection; interactive execution and agent preparation/provisioning must use pure shared `resourcesForConsumer(resources, consumer)` with the slate's app or named agent. Keep the selector free of I/O and local overrides. Chrome and hosted CLI targets must read pushed declarations.

## Agent source and preparation

Use `agents/<name>/instructions.md` in the slate's Artifacts repository for agent definitions. `getAgent` must require source-management permission through `SlateAccess` before reading, including for public slates. Pin the read to the selected `main` commit and return the instructions with that hash. Expose inspection through `GET /api/slates/{target}/agents/{name}` with Zod/OpenAPI. Viewing permission alone must not grant source inspection.

Keep `getAgentRun` as shared internal preparation from a canonical slate, explicit `AgentActor`, agent name, and user prompt. The API boundary authenticates and authorizes viewing before supplying its user actor; the scheduling boundary passes the run actor without caller credentials. Select that named agent's Resources through shared `resourcesForConsumer` from the coherent latest repository snapshot and pin instruction reads to its commit, without applying source-inspection management permission to execution. Preparation must not accept an event-selected revision; API and scheduled execution share this latest-snapshot path. Use shared `prepareSlateResourceExecution` for request preparation. If the selected agent requires viewer resources, it must require a private user actor and call `addSlateMember`, whose whole-slate completeness rule owns membership provisioning. Preparation itself must always resolve only the selected agent's resources; owner-only agents must not create membership or require unrelated personal setup. Return `connection-required` or `secret-required` for missing setup. Keep the app/public viewer-mode refusal independent of automatic private membership. Resolve the selected requirements through `getSlateResourceConfiguration` for the authorized resource actor, reusing the same Owner/assignment assembly as resource inventory and app execution. Pure `prepareAgentRun` consumes the resolved configuration with non-null connection IDs and constructs the run; it does not resolve Owners or return a run for later mutation. Viewer-scoped resources require a member actor; owner-scoped resources remain available through viewing. `agentRunSchema` contains the slate/actor, authored instructions and source revision, separate prompt, canonical secret Owner references, selected connection Owner/account/toolkit references and selected database instance/Owner references, without caller credentials, repository tokens or secret values. The native Pi `database_query` tool consumes prepared database references through the existing `SlateDatabase.query` RPC; shared resource resolution and provisioning own database setup. Derive its input and structured output declarations from the shared database schemas, preserving direct model and Code Mode calls and the unchanged SQL result. Toolkit must always come from the validated declaration. Keep assignment persistence in `slate-connections.server.ts` and configuration assembly in `slate-resource-configuration.server.ts`; execution consumers must not independently resolve assignments or Owners. Do not reconstruct HTTP authentication inside a job.

### Hosted agent runtime

Use native Cloudflare `Agent` plus `RoutedAgents` for the stable slate/agent/actor scope and a separate top-level job namespace for execution. Each catalog entry must own an independent job object and fresh Pi conversation. Install `PiHarness` from `agents/harness/pi` through the job's Lifecycle and open Pi Durable over the supplied SQLite storage. Pi owns execution state, submissions, transcripts and results; the SDK owns durable wakeups and the catalog. Keep each prepared run on its job, with only the resource references its implemented capabilities consume and no secret values. Use native Pi AI provider credentials loaded from Doppler's literal `value.raw` inside trusted execution, with authored instructions rendered through a native Pi prompt section and prompt as separate user input. Do not introduce a second execution ledger or translate Pi results into Think vocabulary.

Keep catalog creation, job lookup and initial submission inside the stable Agent’s native `blockConcurrencyWhile` admission boundary. Release it when the job returns its persisted Pi receipt so discovery cannot expose a job whose operation has not been admitted. If initial submission fails, delete the new entry and execution object through native `RoutedAgents.delete()` before releasing the gate, then propagate the failure. This serializes requests in that slate/agent/actor scope during initialization and inherits Cloudflare’s 30-second callback limit; do not hold the gate while waiting for job completion.

Attach a native Cloudflare container to each job Agent and install Pi's native `CodingTools` extension for `read`, `write`, `edit` and `bash`. Supply `RemoteExecutionEnv` through the native env factory, with one cached daemon connection per job and a new environment at each use; keep filesystem and shell semantics in Pi rather than implementing a second environment. The container stream transport starts the matching Pi environment daemon in the job's Linux image. Keep provider credentials and Worker bindings in the trusted Worker. Observe native harness idle from the outer harness context to close the connection without relying on result polling. Use native ten-minute inactivity retention, reapplying it when a Durable Object restarts with a running container. Register computer disposal before PiHarness so reverse Lifecycle disposal closes Pi before destroying the container. Files persist only while that job's container runs; API and cron jobs must share this same fresh-computer creation path.

Install native `createCodemodeExtension` in the job's existing registry with a per-instance `createInlineCodemodeSandbox` from `@earendil-works/pi-codemode/cloudflare`. Reuse registered tools, including the same `CodingTools` and `RemoteExecutionEnv`, and native `searchTools`, `describeTool` and `describeNamespace`; do not create a parallel discovery catalog or standalone `tool_search`. Keep the inline interrupt budget at 50,000 polls; it is not a duration. The sandbox exposes registered capabilities, not ambient Worker bindings, network or filesystem access. Durable execution uses `sandbox.start()`, so its deadline comes from the script's native `@options` `timeout_ms`, not the sandbox constructor's `timeoutMs`, which applies to `execute()`. A timed script uses the native first line `// @options: {"timeout_ms": 60000}`; Pi persists that deadline across replay. Register sandbox disposal before PiHarness so reverse Lifecycle disposal closes Pi first; native execution owns individual VM disposal. Use the Cloudflare package entry's compiled WASM through the existing build, without another Worker or binding.

Build agent connection tools only from the prepared run's connection references. At admission, use shared `createConnectionSession` with native `direct_tools`, disabled connection management and disabled Composio sandbox; keep Owner, toolkit and assigned account fixed by the helper. Persist each native session ID in the job's `connectionSessions` map keyed by connection slug, alongside run and receipt. Restore SDK sessions with `composio.sessions.use()` and install tools through the same registration operation on fresh submission and harness reconstruction. Publish through the live Pi registry after prepared state exists; a newly created job may open Pi before its start RPC supplies that state. Register flat `<connectionSlug>__<COMPOSIO_ACTION_SLUG>` names with native namespace prefixes, unchanged action input schemas, `callers: ["tools"]` and `deferred: true`. Obtain schemas from the scoped session's raw tool catalog and execute through that same session. Preserve Composio's result fields through Pi structured output. Derive the envelope declaration from Composio's exported session-response schema; resolve the catalog output schema with Composio's reference resolver before selecting its data property for successful results. Retain the native envelope for errors and tools without a declared data schema. Do not copy the catalog's successful wrapper into the session result or maintain an application-owned envelope schema. Keep Composio credentials in the Worker, and leave loader/action Tools authority and billing unchanged.

### Agent job and inspection API

Expose agent job and schedule operations through Zod/OpenAPI and shared domain functions. Reuse `requireAuth` and central `requireSlateViewing`; reject public slates on the jobs route group. `POST /api/slates/{target}/agents/{name}/jobs` accepts only the prompt and returns HTTP 202 with `{job, receipt}` and a `Location` for the created catalog entry. Let Pi generate its operation ID and persist its native receipt on the job. Use that receipt's operation and session identifiers for operation inspection, waiting, and abortion; the routed job ID remains the catalog identity. Callers must not choose a conversation or physical instance address. Create immutable native catalog metadata from the prepared actor and trusted API or schedule trigger, including both native schedule ID and authored name for scheduled jobs. Preserve native receipt fields (`operationId`, `session`, `accepted`) and keep the root-session string local to its job object; the local string `"1"` can recur in different jobs. Scheduled provenance must retain source identity across reprovisioning.

Return native catalog entries from `GET /jobs/{id}` and `{jobs: [...]}` from `GET /jobs`, ordered by creation time descending and ID descending. Resolve only app/current-user scopes available to the authorized caller, and apply the optional `schedule` filter to authored-name provenance. Catalog reads must not load job state.
